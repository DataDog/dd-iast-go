# fasthttp — IAST Sources & Sinks

- **Module:** `github.com/valyala/fasthttp`
- **Version researched:** `v1.58.0`
- **Reference:** https://pkg.go.dev/github.com/valyala/fasthttp
- **Built on `net/http`:** NO — its own request/response types (`*fasthttp.RequestCtx`, `*fasthttp.Request`, `*fasthttp.Response`, `*fasthttp.Args`, `*fasthttp.URI`, `*fasthttp.RequestHeader`/`ResponseHeader`). Substrate for fiber (see `fiber.md`). IMPORTANT: accessors mostly return `[]byte` zero-copy over buffers that are reset and reused across requests/connections — a central taint-lifetime hazard (see Instrumentation notes).

## Overview

A `fasthttp.RequestHandler` is `func(ctx *RequestCtx)`; the server pools and reuses one `*RequestCtx` (and its embedded `Request`/`Response`) per worker goroutine across many requests, resetting it between calls. fasthttp ships no router (routing is layered on top, e.g. by fiber); path/query parsing, header parsing and args parsing are all done directly against reusable byte buffers rather than allocating `string`s. Most getters return `[]byte` "valid until your request handler returns" — copy (`string(b)` / `append([]byte(nil), b...)`) before retaining or handing off to another goroutine.

## Instrumentation notes

- Prefer instrumenting at the **accessor return point** (`Args.Peek*`, `URI.Path/PathOriginal/QueryString`, `RequestHeader.Peek*/Cookie*`, `RequestCtx.PostBody/FormValue`, `RequestHeader.RawHeaders`) rather than at call sites, since these are the funnel points through which all request data flows regardless of caller.
- **Buffer-reuse hazard (critical):** almost every source above returns a `[]byte` that aliases memory owned by `RequestCtx`/`Request`/`Args`/`URI`/`RequestHeader`, all of which are pooled (`sync.Pool`-backed `RequestCtx` pool in `server.go`) and `Reset()` + reused for the *next* request on the same worker goroutine as soon as the current handler returns. Any taint metadata attached to such a `[]byte` (or a `string` derived via zero-copy `b2s`) must either (a) be scoped to the lifetime of the request/handler invocation, or (b) trigger a copy-on-taint so the tracked value has independent backing storage. Otherwise: taint sticks to a buffer that a subsequent, unrelated request will silently reuse and refill, producing both false positives (stale taint on new, clean data) and false negatives (if the copy race clears taint metadata prematurely). This is the single most important hazard to document for reviewers/maintainers of the fasthttp aspects.
- `RequestCtx.FormValue`/`MultipartForm` mix zero-copy `Args` values with heap-allocated `string`s from `mime/multipart` (stdlib) parsing — taint propagation must handle both representations at this join point.
- `b2s`/`s2b` (`b2s_new.go`, `s2b_new.go`) are fasthttp's internal unsafe string↔[]byte conversion helpers used pervasively (e.g. in `RedirectBytes`, `ServeFileBytes`); any conversion at these helpers should propagate taint without needing to reallocate.
- Hot-path concern: `Args.VisitAll`, `RequestHeader.VisitAll`/`VisitAllCookie` invoke a user callback per key/value pair on every parsed request — these are prime candidates for restricting instrumentation overhead to only the values actually returned/consumed by the callback, not the whole header/arg parse loop, given fasthttp's explicit high-throughput design goals.
- Sink instrumentation for `ResponseHeader.Set/Add/SetCookie` and `URI`/`Redirect` should hook on the **argument** (`value []byte`/`string` being written), not the return value, since these are void or side-effecting methods.
- `RequestCtx.SendFile`/`ServeFile`/`FS.PathRewrite` path-traversal checks should key off whether the `path`/`PathRewriteFunc` result argument carries taint derived from `ctx.Path()`, `ctx.UserValue(...)` (set by an external router), or any `Args`/header source — `FS.Root` jailing in `fsHandler.pathToFilePath` mitigates but does not eliminate risk when `PathRewrite` returns attacker-influenced sub-paths containing `..` segments before jailing is applied.
- `fasthttpadaptor.ConvertRequest` (used by `NewFastHTTPHandler`/`NewFastHTTPHandlerFunc`) is a bridging join point, but it is **not** a safe re-materialization boundary: the resulting `*http.Request` is a fresh struct, but most of its string/byte fields (`Method`, `Host`, `RequestURI`, header values, and `Body`'s backing `bytes.Reader`) are `b2s` zero-copy views over the *same* pooled `RequestCtx`/`Request` buffers, not independent copies (the lone exception is the `Cookie` header, which is `strings.Clone`d). Taint attached at this join point inherits the identical buffer-reuse lifetime hazard described above, and callers are explicitly warned the resulting `*http.Request` "must not be used after the fasthttp handler has returned".
