# fx-store-concurrency-F1: verification of store-concurrency-F1 / crash-deadlock-F1 (stale owner handle publishing into a reused slot)

Verdict: both findings CONFIRMED — one root cause. `Store.Acquire` recycles a Dead owner slot (generation bump + Active store) without `lifecycleMu`, and `beginWrite`/`alive()` validate a stale handle with two independent atomic loads, so a finished request's handle can publish bindings or writer provenance into the next request's tables. Reproduced deterministically with my own seam reproducer and naturally on unmodified code.
Scope covered: `internal/taint/store/{owner,binding,writer,lookup}.go` re-read at HEAD 2e23b46; callers `internal/taint/request/{owner,reader,http,lookup}.go`, `internal/taint/propagation/writer.go` audited for raw-handle escapes; private-copy reproduction (natural stress + deterministic seam).

## Verdict per finding
- **store-concurrency-F1 (High, cross-request): CONFIRMED.** Mechanism real at HEAD: `Acquire` (owner.go:21-64) takes `ownerMu`+`writersMu` but never `lifecycleMu`, and does `record.generation.Add(1)` (:53) … 14 atomic stores … `record.state.Store(stateActive)` (:59). `beginWrite` (owner.go:131-149) checks `o.gen != generation.Load()`, `lifecycleMu.TryRLock()`, then `alive()` (owner.go:127-129) loads `generation` and `state` as two separate atomics. `BindObject`/`BindObjectValue` (binding.go:80-107), `UpdateWriter` (writer.go:152-232), `AdoptBufferWriter` (writer.go:117-149), `TruncateWriter` (writer.go:291+), `ResetWriter` (writer.go:266-289) never re-check the generation after `beginWrite`, and `bind` (binding.go:168-207) has no re-check at all. If `Acquire`'s Dead→Active window lands between the two loads of a stale handle's `alive()`, the write lands in the successor's tables. Note: ref-derived paths (`OwnerRef.Handle`/`WriterRef.Handle` → `beginWrite`) are closed by `beginWrite`'s first generation check; the vulnerable surface is raw `*Owner` handles.
- **crash-deadlock-F1 (High, provenance): CONFIRMED — duplicate of store-concurrency-F1, same root cause** (same seam, same code lines; its reproducer is structurally identical to the store-concurrency one).

## Reachability
- Default configuration, Go 1.26.6: reachable, with a very narrow window. Raw `*Owner` handles escape the revalidation layers at `request/reader.go:23-25` (`BindReader`), `request/http.go:74`, and inside `Analysis` methods via `slot.owner.Load()`; any hook running on a goroutine other than the request's (async body read, reader bind, writer sync) after `Analysis.Finish` while the next request acquires the slot can hit the seam. All accesses are atomic — this is a logical race, not a Go-memory-model data race, so it cannot panic or corrupt memory; the damage is bounded provenance corruption in the successor (wrong/false-positive source attribution, foreign object bindings, wiped writer state).
- Not a documented limitation: the README "Propagation coverage" staleness note covers missed propagation edges, and 01-design-intent.md's deliberate trade-offs do not cover cross-request bleed. It breaks product rule 4 (accurate provenance, no cross-request taint bleed).

## Adjusted severity
- Both findings: **High** (unchanged). Per the brief: "wrong provenance on a SUPPORTED path … taint bleeding across requests or owners". Not Critical: no crash/panic/deadlock and no Go-memory-model data race; impact is a bounded, low-probability provenance violation.

## Root cause
- `internal/taint/store/owner.go:21-64` (`Acquire` reactivates a Dead slot without `lifecycleMu`); consumed by `owner.go:127-149` (`alive`/`beginWrite` two-load validation) with no later re-check in `binding.go:80-107,168-207` and `writer.go:117-335`. The same load-order pattern exists in `lookup.go:152-164` (store-concurrency-F2) and is closed by the same fix.

## Minimal fix
In `Acquire`, take `record.lifecycleMu.TryLock()` before the reset and the `state.Store(stateActive)`, skipping the slot on failure (mirroring the existing `writersMu.TryLock` handling) so a slot is never observed Dead→Active by a handle that passed the generation check. Defense in depth: in `alive()` (and `lookup.go:152`), load `state` before `generation` — under a held RLock, an Active observed from a new `Acquire` forces the subsequent generation load to see g+1. Add the natural stress test as a regression test.
