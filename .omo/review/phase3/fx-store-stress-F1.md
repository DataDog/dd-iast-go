Verdict: store-stress-F1 is **CONFIRMED** (High, unchanged). The torn `alive()` window in `beginWrite` is real, I reproduced the cross-request publication with my own independent store-level reproducer, and the production entry paths exist — but the per-operation trigger probability through full woven entry points is low (my 2×300 s realistic-surface runs did not hit), which bounds, not refutes, reachability.

## Verdict per finding

### store-stress-F1 — CONFIRMED, High (unchanged)

**Mechanism verified in code.** `Acquire` (owner.go:30-66) bumps `record.generation` (l.53) and stores `stateActive` LAST (l.59), holding only `ownerMu` and `writersMu` — never `lifecycleMu`. `beginWrite` (owner.go:131-149) checks generation (l.134), takes `lifecycleMu.TryRLock`, then calls `alive()` (owner.go:127-129), which loads generation THEN state as two separate atomic loads. A stale handle (gen g) passes when both generation loads occur before the reuse bump and the state load after the reuse's `stateActive` store — i.e. the goroutine is descheduled between `alive()`'s two loads while Finish+Acquire complete. This interleaving is consistent with Go's sequentially-consistent atomics (L_gen < bump < stateActive-store < L_state violates neither program order), so it is not a compiler/CPU reordering issue but a genuine check-then-act hole. Consumers with no second revalidation write straight into the new owner: `BindObjectValue` (binding.go:84-101) binds the finished request's object into the new request's table; `UpdateWriter` (writer.go:141-200) creates writer state in the new owner carrying the old request's owner-local source IDs and charges the new request; `AdoptBufferWriter` and `claimMutation` (mutation.go:79-88, which can CAS the new owner's roots because per-record root generations restart at 1) sit behind the same `beginWrite`. `putWindow`'s second `alive()` (value.go:146-148) does cover root/window publication, as the finder stated.

**Reproduction.** Three runs, commands and full output in `.omo/review/evidence/fx-store-stress-F1/`:
1. Finder's reproducer re-run in my private copy (`fx-finder-rerun.out.txt`): `STALE_BUDGET=60s GOTOOLCHAIN=go1.26.6 go test -race -run '^TestReviewStale(HandleBinds|HandleWriter)' -count=1 -v ./internal/taint/store` — bind bleed at iteration 505, writer bleed at iteration 362 (`B charged=64`, `SourceID:7` = A's owner-local ID), within 6.5 s.
2. **My own minimal store-level reproducer** (`fx_stale_min_test.go`, `fx-min-store-level.out.txt`): `FX_BUDGET=60s GOTOOLCHAIN=go1.26.6 go test -run 'TestFXStaleOwnerPublishesIntoReusedSlot' -count=1 -v ./internal/taint/store` — independent design (no 63-slot pre-filling: on a fresh store slot 0 is deterministically the first reuse candidate), raw `*Owner` handle as `request.Analysis` holds: `iteration 1390: object bound only through FINISHED request A (gen 2781) is bound to NEW request B (gen 2782, id 2782)` in 46 s, plain build.
3. **My realistic-surface reproducer** (`fx_stale_test.go`, `fx-realistic-surface.out.txt`): drives the exact woven-hook entry functions — `request.Begin`/`Scope.Finish`, `request.BindReader`/`PropagateReader` (iobridge-registered), `Analysis.TaintString`, `propagation.UpdateStringWriter` — with default-like config (`MaxConcurrentRequests=2`, so B reuses slot 0), 32 spinner goroutines of the finished request, 300 s per path. No bleed observed. A woven `orchestrion` build of an HTTP testapp would only lower the attempt rate further (same code path behind more frames), so I did not spend a heavy build on it.

**Reachability.** Not a documented limitation: README "Propagation coverage" and phase1/01-design-intent.md say nothing about stale handles; the architecture map asserts the opposite invariant ("A stale owner handle or root generation cannot publish into a reused slot"), and `Finish`'s doc comment claims it cannot affect a later generation. Two production exposure classes:
- **Raw-`*Owner` holders — the request package itself**: `Analysis.storeOwner()` (request/owner.go:119-130) hands the raw owner to `TaintString`/`TaintBytes`/`adoptBodyBytes`, and `request.BindReader` (reader.go:20-26) passes it into `store.BindObjectValue`. A customer goroutine still draining the body (`io.ReadAll`, JSON decode, `ParseForm` — all woven) while its request scope finishes races exactly the scenario my store-level reproducer demonstrates. This class is *confirmed empirically*.
- **Handle()-mediated paths** (`propagation/writer.go:110-132` `updateWriter`; `request/reader.go:30-38` `PropagateReader`): `Handle()` legitimately returns a live owner before Finish; the torn window is in the subsequent `beginWrite`. Mechanically identical (no structural blocker — I verified the code path), but a full woven-entry operation spends only ~2 ns of a ~µs call inside the window, ~1000× less exposure than the tight-loop repro. My 2×300 s runs did not hit, so production hits need: an app goroutine doing taint work concurrent with its request's Finish + preemption inside the nanosecond gap + slot reuse during the stall. Rare per event, non-zero over a process lifetime under sustained traffic.
Default config favors the trigger: with `DD_IAST_MAX_CONCURRENT_REQUESTS=2` (default), the just-finished slot 0 is the first reuse candidate every Acquire — immediate reuse is the common case, not a saturation edge case.

**Adjusted severity: High (unchanged).** Confirmed cross-request provenance bleed (A's object bindings and writer state, carrying A's owner-local source IDs, charged to and resolved against B) on supported propagation surfaces; the brief rates cross-request taint bleed as High, and it violates product rule 4. The low probability is a mitigation consideration, not a downgrade ground under this scale.

**Root cause.** `internal/taint/store/owner.go:127-149` (torn generation/state validation in `alive()`/`beginWrite`) combined with `owner.go:53-59` (`Acquire` performs the generation bump and `stateActive` store non-exclusively, never under `lifecycleMu`). The same load order appears in `OwnerRef.Handle` (binding.go:53-54), `WriterRef.Handle` (writer.go:52-53) and `Entry.Handle` (lookup.go:35).

**Minimal fix.** Best: pack generation+state into one `atomic.Uint64` (state in low bits, generation above) validated with a single load and a single CAS in both `Acquire` and `Finish` — this also closes the related F3 stale-`Finish` hole and the `Handle()` torn windows. Alternative, sufficient under Go's sequentially-consistent atomics: load state BEFORE generation in `alive()`/`Handle()` (a false pass would then require state-load-after-reuse-store and gen-load-before-bump, which program order + SC forbid); `Finish` (owner.go:157-162) still needs the packed word or a `lifecycleMu`-guarded transition. `Acquire` taking `lifecycleMu.TryLock` around the transition (skipping the slot on failure, as it already does for `writersMu`) also works.

**Duplicates:** only one finding was supplied; no duplicate assessment needed.
