Observation: without Orchestrion weaving, the `+` operator in both benchmarks is
plain Go string concatenation. config.Enabled/request.Begin have no effect because
the operator advice that would call into internal/taint/propagation was never woven
in. Inactive and ActiveClean measure the same 38ns/24B/1alloc (the cost of a plain
4-operand string concat), not "IAST overhead when active vs inactive" as the names
imply. BenchmarkOperatorConversionsInactive/BenchmarkOperatorSlicesInactive have the
same structural dependency on weaving. Unlike TestOperatorEvaluationAndPanicSemantics
in the same file, which calls `built.WithOrchestrion` and skips when unwoven, these
benchmarks have no such guard: plain `go test -bench=. ./...` from repo root silently
"passes" and reports a near-zero number that looks like a legitimate low-overhead
result.
