# perf-allocs-matrix: allocation matrix for every benchmark, woven vs plain

Verdict: taint propagation is allocation-neutral everywhere it is exercised (every benchmark in the root module and in all three nested testapps has identical allocs/op plain and woven, and the untainted/inactive paths allocate exactly what uninstrumented Go allocates), but the non-taint crypto sinks are not gated by any cheap check: `md5.Sum` inside one sampled request costs 119 ns/0 allocs plain versus 6.8-9.4 us/28 allocs/9.8 KB woven while the request publishes exactly one finding, and a sampled-out request still allocates a 3200-byte annotation.

Scope covered: every `Benchmark*` in the repository (5 Go modules, 56 benchmark rows) run plain (`go test`) and woven (`go tool orchestrion go test`) with `-benchmem -benchtime=2000x -count=1` on `GOTOOLCHAIN=go1.26.6`, `GOFLAGS=-p=4`; plus the repository's own control-vs-IAST runner (`benchmarks/overhead/runner`) at sampling 100 and 0; plus env variants (`DD_IAST_ENABLED=false`, `DD_IAST_REQUEST_SAMPLING=0`, `DD_IAST_STACK_TRACE_ENABLED=false`) on the woven binary. Code read: `internal/vulnerability/report.go:30-105`, `internal/model/event.go:35-64`, `internal/spans/annotation.go:26-35,167-213,224-232`, `internal/spans/vulnerability.go:17-34`, `iast/crypto/hash/hash.go:17-26`, `benchmarks/overhead/{overhead,buffer,instrumentation}_test.go`, `benchmarks/overhead/runner/main.go:500-545`.

Full matrix: `.omo/review/evidence/perf-allocs-matrix/allocations-matrix.md` (plain vs woven for all 5 modules; control vs IAST under identical weaving; sampled-out table; env-variant table). Raw outputs: `root.*.txt`, `overhead.*.txt`, `sqlapp.*.txt`, `execapp.*.txt`, `integapp.*.txt`, `runner/`, `runner-sampling0/`.

Timing columns are indicative only. The machine is shared, root-module packages ran in parallel, and the woven root run measured *faster* than the plain run on most rows purely because of ambient load. Allocation counts are the signal; they were stable across every repeat run.

## Findings

### perf-allocs-matrix-F1: weak-hash/weak-cipher sinks run the full report path on every call, after the finding is already recorded
- Severity: High
- Category: perf
- Location: internal/vulnerability/report.go:56-105; internal/model/event.go:47-64
- Claim: `vulnerability.Report` has no gate between `config.Enabled` and the expensive work. On every single call it generates a UUID (`uuid.NewString`), captures a dd-trace-go stack trace, builds a `model.Vulnerability` with evidence and location, and only then takes the annotation lock and asks `CanAddVulnerability`, which drops the report either on the per-request quota (default 2) or on the event-local hash comparison. 1000 `md5.Sum` calls inside one request span publish exactly **one** `WEAK_HASH` vulnerability, yet all 1000 pay the full path: `md5.Sum` of a 30-byte payload goes from 119.0 ns/op, 0 B, 0 allocs (plain) to 6767-9380 ns/op, 9825 B, 28 allocs (woven, `DD_IAST_REQUEST_SAMPLING=100`) - a 57-79x regression whose result is discarded. The dropping branches also emit a telemetry log record with `slog.Any("vulnerability", vuln)` per dropped call. `DD_IAST_STACK_TRACE_ENABLED=false` only halves it (322.8 ns/op at the default sampling), because the UUID, the location capture and the model build remain. This is the same `Report` as at merge-base `1135a291`, so it is pre-existing rather than branch-introduced code.
- Evidence: `.omo/review/evidence/perf-allocs-matrix/repro/zz_repro_weakhash_test.go` and `repro/zz_repro_quota_test.go` (copy both into `benchmarks/overhead/`). Commands, from `benchmarks/overhead`: `DD_IAST_REQUEST_SAMPLING=100 go tool orchestrion go test -run '^$' -bench 'BenchmarkReproWeakHashQuotaExhausted$' -benchmem -benchtime=20000x -count=1 .` -> `repro-weakhash.woven-sampling100.txt`: `20000  6767 ns/op  9825 B/op  28 allocs/op`; same benchmark with plain `go test` -> `repro-weakhash.plain.txt`: `20000  119.0 ns/op  0 B/op  0 allocs/op`. `DD_IAST_REQUEST_SAMPLING=100 go tool orchestrion go test -run TestReproWeakHashQuotaDiscardsWork -v -count=1 .` -> `repro-quota.txt`: `span "repro.request" iast.enabled=1 payload_len=360 WEAK_HASH_count=1` for 1000 `md5.Sum` calls. Allocation attribution in `repro-weakhash-inrequest.pprof-top.txt`: `uuid.NewRandomFromReader` 11%, `stacktrace.NewEvent` 7.6%, `telemetry.Log` 10.7%, `model.(*Event).CanAddVulnerability` 7.3%, all under `vulnerability.Report` (97% cumulative).
- Fix: compute the vulnerability hash from type + evidence + call-site before the expensive capture, and early-return when the annotation's event is already full or already holds that hash (a `func (a *Annotation) WouldDrop(hash) bool` read under `RLock`). That keeps the first report identical and removes UUID, stack capture, model build and telemetry logging from every subsequent call.

### perf-allocs-matrix-F2: sampled-out requests allocate a fresh 3200-byte annotation instead of the existing shared sentinel
- Severity: Medium
- Category: perf
- Location: internal/spans/annotation.go:198-213 (`BindScope`); sentinel at internal/spans/annotation.go:27-29
- Claim: when a request is not sampled, `BindScope` still calls `store.LoadOrCompute` with `&Annotation{Sampled: active}`, allocating a full 3200-byte `Annotation` (it embeds `model.Event` plus `sourceIndex [512]uint16` and `eventSourceIndexes [256]int`) only to record one bit - "not sampled" - and then returns `nil` to its caller. The package already owns an immutable `nonSampledAnnotation` sentinel for exactly this state and returns it from three other sites (`annotation.go:120,144,175`). Measured against the control build with the same weaving toolchain, a sampled-out HTTP round trip costs +9 allocs/op and +3976 B/op (control 414 allocs / 34001 B; IAST at `-sampling=0` 423 allocs / 37977 B), and `spans.BindScope.func1` is the single largest IAST allocation site in the sampled-out profile at 15.05 MB, 8.09% of all bytes allocated by the benchmark. This is branch code (`87ecf02 fix(iast): retain negative sampling decisions`); retaining the decision is deliberate, allocating 3200 bytes to hold it is not required by that goal.
- Evidence: `.omo/review/evidence/perf-allocs-matrix/runner-sampling0/{control.txt,iast.txt}` from `go run ./runner -count=1 -benchtime=2000x -cpu=1 -sampling=0 -bench 'BenchmarkHTTPRoundTrip|BenchmarkRequestProcessing$|BenchmarkHealth'`; profile `http-sampled-out.pprof-space.txt` line `15.05MB 8.09% ... internal/spans.BindScope.func1` from `DD_IAST_REQUEST_SAMPLING=0 go tool orchestrion go test -run '^$' -bench 'BenchmarkHTTPRoundTrip$' -benchmem -benchtime=4000x -memprofile=...`; struct size from `repro/zz_size_test.go` -> `annotation-size.txt`: `sizeof(Annotation)=3200 bytes`.
- Fix: in the `LoadOrCompute` closure, return `nonSampledAnnotation` when `!active` instead of a freshly allocated struct. The negative decision is still retained in the map and still consumes the same map slot, at zero allocation.

### perf-allocs-matrix-F3: the orphan vulnerability span is created and finished before any sampling check
- Severity: Medium
- Category: perf
- Location: internal/vulnerability/report.go:44-52; internal/spans/vulnerability.go:17-19
- Claim: `Report` calls `spans.NewOrphanVulnerabilitySpan()` (a real `tracer.StartSpan` with `defer span.Finish()`) *before* `AnnotationForContext` decides whether anything will be reported. A weak-hash or weak-cipher call outside any span therefore starts and finishes a tracer span on every invocation even when IAST sampling is 0, so the span carries no IAST payload at all. Measured: with `DD_IAST_REQUEST_SAMPLING=0`, 100 `md5.Sum` calls emit 100 finished spans, 0 of which carry `_dd.iast.json`. On the same woven binary `BenchmarkWeakHashNoActiveSpan` is 4 allocs/128 B per `md5.Sum` at both default sampling and sampling=0 (0 allocs in the control build and 0 allocs with `DD_IAST_ENABLED=false`), and `BenchmarkWeakCipherNoActiveSpan` is 5 allocs/256 B versus 1 alloc/128 B in control. Beyond the allocations this adds one span per call to the customer's trace volume on a path where IAST was explicitly sampled out. (Orphan *reporting* itself is a documented design choice; producing empty orphan spans when sampling is off is not.)
- Evidence: `.omo/review/evidence/perf-allocs-matrix/repro-orphan.txt` from `repro/zz_repro_quota_test.go`, command `DD_IAST_REQUEST_SAMPLING=0 go tool orchestrion go test -run 'TestReproOrphanSpanWhenSampledOut' -v -count=1 .`: `DD_IAST_REQUEST_SAMPLING=0: 100 md5.Sum calls emitted 100 spans, 0 carrying an IAST payload` (and `...=100: ... 100 spans, 100 carrying an IAST payload`). Allocation columns in `runner/control.txt` vs `runner/iast.txt` and in `overhead.woven.{,disabled,sampling0}.txt`; profile `weakhash-noactive.pprof-top.txt` shows the 4 allocations as `tracer.Tag` + `orchestrion.WrapContext` under `spans.NewOrphanVulnerabilitySpan`.
- Fix: resolve the annotation/sampling decision first and only materialize the orphan span once a report will actually be produced, i.e. move the `NewOrphanVulnerabilitySpan` call below the `ann.Sampled` check (using `NewOrphanTaintedSpan`-style construction that already pairs span and annotation).

### perf-allocs-matrix-F4: full-analysis request cost, recorded as a baseline
- Severity: Info
- Category: perf
- Location: benchmarks/overhead/overhead_test.go:317-347
- Claim: with the same weaving toolchain and sampling=100, a full HTTP round trip costs 510 allocs/40904 B versus control 414 allocs/33988 B, i.e. +96 allocs (+23%) and +6.9 KB per analyzed request. `Health`, `RequestProcessing` and `RequestProcessingParallel` are allocation-identical to control (19/47/47 allocs), so the delta is the request-source tainting path, not fixed weaving overhead. Recorded as the reference number for future regressions.
- Evidence: `.omo/review/evidence/perf-allocs-matrix/runner/{control.txt,iast.txt,metadata.txt}` (`go run ./runner -count=1 -benchtime=2000x -cpu=1`).
- Fix: none required; keep as a tracked baseline.

### perf-allocs-matrix-F5: the overhead runner cannot run outside a git checkout
- Severity: Low
- Category: quality
- Location: benchmarks/overhead/runner/main.go:532-536
- Claim: `writeMetadata` runs `git rev-parse HEAD` in the repository directory and propagates the failure, so the whole benchmark run aborts after both variants have already been built and validated (`overhead benchmark: run git: exit status 128`). Running the harness from an exported, vendored or rsync'd tree - which is exactly what an isolated benchmarking environment does - wastes the full build and produces empty `control.txt`/`iast.txt`.
- Evidence: `.omo/review/evidence/perf-allocs-matrix/runner.log` (first run, before `git init` in the private copy): `Building control benchmark binary with Orchestrion... / Validating benchmark variants... / PASS / PASS / overhead benchmark: run git: exit status 128`.
- Fix: treat the revision as optional metadata - record `unknown` and continue when the `git` call fails.

## Checked and found correct
- Allocation neutrality of propagation: all 27 root-module benchmark rows, all 3 nested testapp rows (`BenchmarkStmtExecContextInactive` 3 allocs, `BenchmarkCommandStartErrorInactive` 28 allocs, `BenchmarkJSONUnmarshalClean`/`ActiveClean` 12 allocs) and all 30 overhead rows other than the four crypto-sink rows and `HTTPRoundTrip` report byte-identical `allocs/op` and `B/op` plain versus woven.
- Inactive/untainted paths allocate nothing beyond the host operation: `BenchmarkPropagationActiveUntainted/*` (an *active, sampled* request performing `TrimSpace`, `Split`, `Clone`, `ToLower` on untainted values) matches the control build exactly on all six subtests, including 0 allocs for the two window cases; `Operator*Inactive`, `OperatorOptimizedConversionExcluded`, `Report*Inactive`, `ReportActiveClean` (SQL and exec), `Literal*`, `HasValuesClean`, `CollectStringMiss`, `MappedPattern` and `StringLookup/{miss,no-active}` are all 0 allocs woven.
- The kill switch is clean: `DD_IAST_ENABLED=false` on the woven binary restores control allocation counts exactly (`WeakHashNoActiveSpan` 4 -> 0, `WeakCipherNoActiveSpan` 5 -> 1, `HTTPRoundTrip` 447 -> 416 vs control 414).
- Tainted `bytes.Buffer` copy tracking costs +1 alloc and +48 B per operation versus control (`BytesBufferCopies/read` 1->2 allocs, `/write` 1->2 allocs, `/active-unrelated` 0->0). That is the documented writer-state cost on an actively tainted receiver, and the unrelated-writer case stays allocation-free.
- Woven build peak RSS stayed at or below 0.43 GB for every module (`/usr/bin/time -l`, `*.time.txt`), far under the 4 GB threshold; the slowest woven build was the root module at 345 s.

## Not covered / open questions
- Timings are not comparable: the machine was shared and root-module packages ran with `-p=4`, so several woven rows measured faster than plain. Any real latency claim needs the runner on a quiet machine with `-count>=10`.
- F1's cost is measured on `md5.Sum` of a 30-byte payload. For a heavier sink operation the relative regression shrinks; the absolute ~6.7 us of discarded work per call does not.
- F2 notes that unsampled annotations occupy entries in the bounded annotation store (`trimStore`, `MaxConcurrentRequests` default 2). Whether unsampled requests can crowd out sampled ones and suppress reporting is a correctness question for the span-lifecycle node, not measured here.
- `-benchtime=2000x -count=1` is a single sample per row; allocation counts are deterministic enough for this purpose, but `B/op` rows with amortized growth (for example `AnalyzeSQL/typical` 1680 vs 1682) vary by a couple of bytes between runs.
- Compile-time and binary-size overhead were out of scope, as was the `-sampling` sweep between 0 and 100.
