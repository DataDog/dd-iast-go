# perf-hotpath: inactive and clean-value hook costs
Verdict: Two High performance regressions (an inactive iterator allocation and excessive clean-writer work), one Medium pre-gate linear scan; the other sampled advice paths retain allocation-free taint gates relative to their native operations.
Scope covered: All 125 aspects in `iast/propagation/orchestrion.yml`, the HTTP, URL, bufio, io, JSON, SQL, command and weak-crypto advice definitions; non-test `iast/**/*.go` wrappers; `internal/taint/{http,io,url,json,operator,writer,scope,sql,command}bridge/bridge.go`, `internal/taint/propagation/propagation.go` and its immediate named-operation callers, `request.ActiveStore`, `store.MayContain` and writer lookup. Benchmarks and Go 1.26.6 escape/inlining analysis ran in a private copy.

## Findings

### perf-hotpath-F1: Lazy string iterators allocate a wrapper with no owner
- Severity: High
- Category: perf
- Location: iast/propagation/strings.go:75-119
- Claim: `StringsSplitSeq`, `StringsSplitAfterSeq`, `StringsLines`, `StringsFieldsSeq` and `StringsFieldsFuncSeq` always create `stringWindowSeq`'s capturing closure *before* checking whether any taint owner or value exists. When the returned sequence escapes, the extra closure is a 32-byte heap allocation on the no-owner path (native `strings.SplitSeq`: 64 B/op, 2 allocs/op; wrapped: 96 B/op, 3 allocs/op). Consuming the sequence immediately can let Go inline/stack-allocate it, so this finding is specifically about returning/storing the sequence. No provenance lookup is necessary without an owner.
- Evidence: Reproducer `.omo/review/evidence/perf-hotpath/hotpath_review_test.go`, captured output `.omo/review/evidence/perf-hotpath/bench.txt` and `.omo/review/evidence/perf-hotpath/inlining.txt`. Copy the reproducer into the private copy as `iast/propagation/hotpath_review_test.go`; run `GOTOOLCHAIN=go1.26.6 go test -run "^$" -bench "^BenchmarkHotPathReview/(no-owner|active-clean)/(join-empty|split-seq)" -benchtime=100ms -count=1 -benchmem -timeout=15m ./iast/propagation`. The no-owner native/hook `split-seq` results were **2/3 allocs/op**. `-gcflags=-m` confirms both `StringsSplitSeq` and `stringWindowSeq` can inline; inlining does not remove the extra escaping closure.
- Fix: Check the cheap active-values counter *before* constructing the wrapper; return the stdlib sequence directly when zero. Preserve the callback on the active-value path.

### perf-hotpath-F2: Clean writer writes scan owner slots without taint or writer state
- Severity: High
- Category: perf
- Location: iast/propagation/writer.go:29-35,104-129
- Claim: `WriterActive()` tests whether *any analysis* exists, not whether a value or writer state exists (`internal/taint/propagation/writer.go:21-25`). With one active but wholly untainted owner, every `BuilderWriteString` gathers a before/after view and calls `UpdateStringWriter`; every `BufferWriteString` additionally calls `PrepareBufferWriter`, `expectBufferMutation` and `bufferView`. `store.LookupWriterValue` (`internal/taint/store/writer.go:75-113`) walks **64 owner slots** even when there are zero writer states; Buffer calls this lookup at least twice. The benchmark's clean, repeatedly reset 64-byte writer showed native versus wrapper **52.44 versus 1006 ns/op** (Builder) and **58.47 versus 992.8 ns/op** (Buffer). Those wall-clock figures are illustrative on this noisy host; the unnecessary 64-slot walk and absence of added heap allocations (both 64 B/op, 1 alloc/op from the native write) are deterministic.
- Evidence: Reproducer `.omo/review/evidence/perf-hotpath/hotpath_review_test.go`, captured output `.omo/review/evidence/perf-hotpath/bench.txt` and `.omo/review/evidence/perf-hotpath/inlining.txt`. Copy the reproducer into the private copy as `iast/propagation/hotpath_review_test.go`; run `GOTOOLCHAIN=go1.26.6 go test -run "^$" -bench "^BenchmarkHotPathReview/(no-owner|active-clean)/(split-seq-consumed|builder|buffer)/" -benchtime=100ms -count=1 -benchmem -timeout=15m ./iast/propagation`. The active-clean rows above use an acquired owner with **no source/value inserted**, and benchmark the identical native write/Reset/String operation against the wrapper.
- Fix: Before gathering views, return the native writer operation if both the process value counter and writer-state counter are zero. For an owner with unrelated taint values, a cheaper input possible-hit check plus a tracked-writer-state check could avoid the 64-slot scan when both are false. Retain writer invalidation whenever either state can matter.

### perf-hotpath-F3: Empty-separator Join rescans every element before activity gate
- Severity: Medium
- Category: perf
- Location: internal/taint/propagation/string_exact.go:21-48
- Claim: `JoinString` walks the entire `elements` slice when `separator == ""` to find a unique nonempty alias **before** `request.ActiveStore()`. On 4,096 empty elements with no owner, the native join returns an empty string without allocating, while the wrapper performs another 4,096-element pass. The wrapper also does this when an active owner exists but none of these values is tainted. This is an O(n) pre-gate operation, not a fixed-cost check; the shared-host wall-clock numbers (175382 versus 565912 ns/op in one no-owner run) are not treated as a stable ratio.
- Evidence: Reproducer `.omo/review/evidence/perf-hotpath/hotpath_review_test.go` and captured output `.omo/review/evidence/perf-hotpath/bench.txt`; command `GOTOOLCHAIN=go1.26.6 go test -run "^$" -bench "^BenchmarkHotPathReview/(no-owner|active-clean)/(join-empty|split-seq)" -benchtime=100ms -count=1 -benchmem -timeout=15m ./iast/propagation` in the private copy. Both empty-join variants report **0 allocs/op**.
- Fix: Move the active-store check before the special alias scan; native `strings.Join` already returned the result, so a no-owner call can return it immediately.

## Checked and found correct

For the matrix below, `A=1/2` means one atomic pointer load before manager initialization, two loads (manager pointer plus active-owner bitset) once initialized with no owner. `P` means a possible-hit check: hash/key construction, one fixed-shard `TryRLock` and up to 64 fixed slots; it is **not** a Go map lookup. The native operation's own allocations and calls are excluded from the *added* column. On an active owner with zero values, `P` is still reached by named string/byte operations unless a size/alias check exits first; for an active owner with other tainted values, `P` similarly filters clean operands. On a no-owner path, `P` is never reached.

| Advice family (all aspect variants) | Before cheap gate; no owner / active clean | Added allocs and map lookups on clean path |
| --- | --- | --- |

| `strings.Clone/Cut/CutPrefix/CutSuffix/Split/SplitN/SplitAfter/SplitAfterN/Fields/FieldsFunc/Trim*/Join/Repeat/Replace*/ToLower/ToUpper/ToTitle/Map/ToValidUTF8`, `Replacer.Replace` | Native call, then one internal propagation call, `A=1/2`, then 0-16 `P` depending on operation; `Cut` makes two `StringWindow` calls. The primary named-operation and operator gates inline under `-gcflags=-m` (captured in `inlining.txt`); the fixed-store `MayContain` uses shard locks/probes only after owner activity is observed. The shadow research's disabled-mode CHECK is not equivalent to no-owner woven mode: without Orchestrion there is no advice, whereas the measurements above deliberately invoke the woven wrappers. Reported limitations (unsupported direct-call shapes, mutable aliases and writer stack escape) were not filed as new defects.

## Not covered / open questions
- No instrumented end-to-end timing campaign was run; timings from the shared host are illustrative, and representative wrapper benchmarks only prove allocations for their measured argument shapes. The actual `encoding/json.Unmarshal` "native" row in the broad exploratory benchmark was optimized away and is explicitly excluded from comparisons.
- Benchmarks for every individual one of the 125 aspect spellings were not run. The table counts operations by shared implementation/gate, including the pointer/value and named-function variants; allocation claims beyond the measured shapes are static inspection rather than measured `allocs/op`.
