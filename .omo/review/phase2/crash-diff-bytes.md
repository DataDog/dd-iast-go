# crash-diff-bytes: woven differential fuzzing of bytes.* and bytes.Buffer/strings.Builder op sequences
Verdict: No behavior divergence. Woven `bytes.*` calls, `bytes.Buffer` and `strings.Builder` method sequences, byte slicing, and `string([]byte)` all returned exactly what native twins returned: results, errors, panics, aliasing, internal state, and callback traces. I checked this across 1,083,943 random writer scopes and 3,763,280 (58,355,255 calls) random bytes-function scopes, and plain and woven builds produced byte-identical digests. Writer provenance was exact on every supported sequence (0 false or misattributed ranges). The one real provenance defect is the known unanchored `strings.Builder` view (High, reproduced again here with ordinary idioms). There are also two Low documentation gaps (Join coarse fallback, capacity-based writer bound).

Scope covered: `iast/propagation/writer.go` (all 15 writer wrappers, `builderView`/`bufferView`/`writerView`), `iast/propagation/bytes.go` (28 wrappers), `iast/propagation/orchestrion.yml:805-1055` (bytes calls), `1057-1519` (writer `pointer-only`/`value-only` aspects), and `1553-1680` (native Buffer invalidation hooks). I also read `internal/taint/propagation/writer.go`, `internal/taint/propagation/bytes_exact.go:17-110`, and `internal/taint/store/writer.go:1-470`. I ran a woven test package `iast/internal/zzdiffbytes` in the private copy on Go 1.26.6 with the pinned orchestrion.

## Method
- **Woven side** (`ops.go`): direct calls, so orchestrion rewrites them. Hooked writer methods run in both receiver forms: `h.B.WriteString(s)` (value-only aspect, `&h.B`) and `p.WriteString(s)` (pointer-only aspect).
- **Native twin** (`ops_native.go`): method values (`f := p.WriteString; f(s)`) and package-level function values (`nSplit = bytes.Split`), which the join points do not match. Both twins get identical inputs.
- **Compared per op**: every return value, error text, and recovered panic value (`E:`/`S:`), plus the byte offset of aliasing results inside the internal backing. I also compared the complete internal state through `unsafe`: Buffer `buf` len/cap/content, `off`, `lastRead`, `Len`/`Cap`/`Available`; Builder `addr`==self, `buf` len/cap/content. For bytes functions I compared nil-ness, len, cap, content, and alias class (which input, at which offset), plus predicate and mapper call traces.
- **Buffer ops (28)**: Write, WriteString, WriteByte, WriteRune, Grow (including negative and 70,000), Reset, Truncate (including out of range), String, Read, Next, ReadByte, ReadRune, UnreadByte, UnreadRune, ReadBytes, ReadString, ReadFrom, WriteTo, Bytes, a mutation through the `Bytes()` alias, AvailableBuffer+append+Write, Peek, a mutation through a `Peek` alias, the self-writes `Write(b.Bytes())` and `WriteString(b.String())`, Len/Cap/Available, value copy + write to the copy, and nil-receiver calls for every hooked method.
- **Builder ops (13)**: the same set where it applies, including the copied-builder `copyCheck` panic and nil receivers.
- **bytes functions (31)**: all 28 wrapped functions, plus `x[a:b]`, `x[a:b:c]` (random bounds into capacity and out of range), and `string(x)`. Inputs include nil, empty, invalid UTF-8, case-changing runes (`İ ß Σ ﬀ`), tainted sources, tainted windows at random offsets with and without spare capacity, 0-19 `Join` parts, and counts of -3..5, 40, and overflow.
- **Provenance oracle**: a per-byte model (clean or source index) built from the ranges the system reports on each *input*. After every op, each range reported on an output must lie on model-tainted bytes and carry the model's source value; anything else is FALSE TAINT or WRONG SOURCE. Window outputs map back to the aliased input offset; `Clone`/`Join`(<=16 parts)/`Repeat`/`string()` get exact models; coarse transforms get a source-membership check. Losses are counted separately. Each scope runs 1-3 sequences within one request, with `runtime.GC()` between sequences to provoke address reuse.
- **Cross-build check**: fixed-seed tests hash every woven-side result and state. Plain `go test` and woven `go tool orchestrion go test` produced the same digests: writers `61dbec8fe9aa6537`, bytes functions `ad3db86df207a8b1` (`woven-deterministic-run1-go1.26.6.txt`, `plain-deterministic-go1.26.6.txt`). This also covers the stdlib-internal Buffer hooks, which both twins share inside a single build.

## Findings
### crash-diff-bytes-F1: Unanchored `strings.Builder` writer view revives stale request taint on clean content (independent reproduction of store-identity-gc-F1 / life-cross-request-F2)
- Severity: High
- Category: false-positive
- Location: iast/propagation/writer.go:202-205 (`builderView`: no `Anchor`); internal/taint/store/writer.go:23-27 ("builders do not"), 234-259 (`SnapshotWriter` matches on view only), 448-462; internal/taint/propagation/writer.go:191-230
- Claim: `builderView` returns `{Pointer: StringData(b.String()), Length, Capacity}` with no anchor, and Builder has no native hook. After a woven `w.sb.WriteString(body)`, an ordinary `*w = rowWriter{}` leaves the writer record alive. The old backing becomes garbage. A clean row written with `fmt.Fprintf(&w.sb, "%s", clean)` goes through the `io.Writer` interface and is not wrapped. When the allocator hands back the freed address with the same len/cap, the woven `w.sb.String()` matches the stale view, and `publishWriterString` adopts the body source's ranges over bytes that are all clean. A SQL/exec sink would then report a false vulnerability with the wrong source. Every idiom used is common customer code, and none is a documented unsupported operation for Builders: README:39-50 says indirect calls "do not propagate", not that they can create taint.
- Evidence: `.omo/review/evidence/crash-diff-bytes/harness__iast__internal__zzdiffbytes__repro_builder_test.go`; `GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -count=1 -v -run TestReproBuilderStaleTaintRealistic ./iast/internal/zzdiffbytes` → `repro-builder-stale-woven-go1.26.6.txt`:
  ```
  iteration 0: FALSE POSITIVE: clean value "cccccccc"... (len 16, all 'c') tainted with range start=0 len=16 source=http.request.body:body value="abcdefghijklmnop"
  size=16 iterations=40 backingAddressReused=1 falsePositives=1
  size=48 iterations=40 backingAddressReused=1 falsePositives=1
  iteration 6: FALSE POSITIVE: clean value "cccccccc"... (len 40000, all 'c') ... source=http.request.body:body
  size=40000 iterations=40 backingAddressReused=4 falsePositives=4
  ```
  Conditional on address reuse, the false positive fired 6/6 times. A method-value `Reset` variant also fires (`probe-builder-methodvalue-woven-go1.26.6.txt`, iteration 0).
- Fix: anchor the builder backing in `builderView` as `bufferView` does (`Anchor = unsafe.StringData(value)`, `Backing = pointer`). A tracked address then cannot be reused while its record exists. Records are already bounded at 8 per owner, and capacity is already charged.

### crash-diff-bytes-F2: `bytes.Join` with more than 16 elements is coarse, which README does not state
- Severity: Low
- Category: doc
- Location: internal/taint/propagation/bytes_exact.go:17-18, 38-51; README.md:34
- Claim: When `len(elements) > maxInputs`, `joinBytesHit` looks only at elements 0-14 plus the separator. It then taints the whole result under the first intersecting source, clean parts included, and ignores taint in later elements. The fuzzer observed 40/40 whole-range over-taints, all with 17-19 parts and none with 16 or fewer. The code comment documents this. The README table lists `Join` as an exact byte copy without the caveat. The reported vulnerability is still real, because tainted bytes are present, but the evidence ranges are wrong, and taint in a late element is lost.
- Evidence: `woven-deterministic-run1-go1.26.6.txt` has 39 lines like `fn.Join.A: FALSE TAINT at byte 0 (range [0,+165) ...` plus 1 WRONG SOURCE. A rerun with the parts count in each trace showed that every failure had 17-19 parts. After the oracle exempted more than 16 parts, the rerun passed (`woven-bytesfn-after-join-oracle-fix-go1.26.6.txt`).
- Fix: state the 16-element exact bound and the coarse, prefix-only fallback in README, or include the separator and all elements in the coarse source set.

### crash-diff-bytes-F3: The writer bound is on capacity, so a reused Buffer that once exceeded 64 KiB is blind for good
- Severity: Low
- Category: doc
- Location: iast/propagation/writer.go:219-224 (`writerView` invalid when `capacity > MaxRootBytes`); README.md:72
- Claim: Tracking depends on capacity, not on the bytes written. After one `Grow`/write past 64 KiB, every later tainted write through that writer is dropped. `bytes.Buffer.Reset` keeps the capacity, so a `sync.Pool` buffer that ever served a large payload never propagates taint again. README says "64 KiB of charged visible capacity", which is accurate but does not describe this consequence.
- Evidence: `TestDiffWritersSupportedOnly` (README-supported ops only). With a 10% chance of `Grow(70000)`: `buffer.String.lost.len>=2 1188` of 8,352 and `builder.String.lost.len>=2 726` of 7,570, and every logged loss trace contains `k4/n70000` (`supported-only-with-grow70000-lost-log.txt`). The same RNG stream with `DIFF_NO_BIG_GROW=1` gives 0 losses at len>=2. The remaining 60 and 75 losses are all 1-byte values, the documented refusal (`supported-only-no-big-grow.txt`).
- Fix: document the capacity semantics and the effect on pooled buffers, or charge or anchor only the visible prefix for Buffer views.

## Checked and found correct
- **No behavior change**: 0 divergences across all runs. That covers deterministic runs (3,000 writer scopes and 3,000 bytes-function scopes, plus 3,000 supported-only scopes), a 7-minute random writer run (**1,083,943 scopes**, seed 1790169214688848000, PASS), and the random bytes-function run (7-minute run: 3,763,280 scopes, 58,355,255 calls, seed 1790169828709928000, PASS; `random-bytesfn-7m-pass-go1.26.6.txt`). Panic identity matched for Grow(-n) (`bytes.Buffer.Grow: negative count`, `strings.Builder.Grow: negative count`), `Truncate` out of range, the Builder copy check, `Repeat` negative and overflow, out-of-range and inverted 2/3-index slices, and nil-receiver calls (nil `*Buffer.String()` returns `"<nil>"` in both forms). No panic originated in IAST code.
- **Plain vs woven digests are identical**, so the stdlib-internal `invalidate-*` prologues in `bytes.Buffer` do not change semantics either (including `UnreadByte`/`UnreadRune` after writes, `ReadFrom` growth, and `WriteTo`).
- **Receiver forms**: value-only (`&h.B`) and pointer-only rewrites evaluate the receiver once and behave identically. Self-aliasing writes `b.Write(b.Bytes())` and `b.WriteString(b.String())` match native and propagate the duplicated ranges exactly.
- **Writer provenance**: 0 FALSE TAINT and 0 WRONG SOURCE on Buffer/Builder outputs across about 1.09M writer scopes. That includes `Bytes()`/`Peek()` alias mutation, AvailableBuffer append writes, Buffer value copies (the transferred entry, README:53-59), Truncate, Reset, and GC between sequences in one request. The Buffer anchor plus native hooks prevent the F1 pattern for `bytes.Buffer`.
- **Supported-path loss** is fully explained by the documented bounds: 1-byte roots, the 64 KiB capacity (F3), and the 10-range limit (`over-range-limit` stats). In the default mix, Buffer read/exposure ops drop state as documented (README:40-43).
- **bytes functions**: window outputs (`Cut*`, `Split*`, `Fields*`, `Trim*`, slicing) keep the exact input offset and exact taint. Exact models held for `Clone`, `Join` (<=16 parts), `Repeat`, and `string()`. Coarse transforms never introduced a source absent from their inputs.
- Build memory: the woven test build peaked at 316 MB RSS (`/usr/bin/time -l`), well under 4 GB.

## Not covered / open questions
- Only Go 1.26.6. The woven Go 1.27 build is blocked by the known encoding/json break (phase1 base-test-127), so Go 1.27 `bytes.CutLast` and the Buffer internals were not diffed woven.
- Concurrency (shared buffers across goroutines, writerbridge 128-slot saturation) was out of scope. All sequences are single-goroutine.
- Method expressions were not exercised as calls because they break the woven build (hooks-fidelity-bytes-F1).
- One harness false alarm was fixed mid-run: a reslice into capacity past `len` inherits the root's real source bytes, which is correct provenance (`random-run1-writers-pass-bytesfn-harness-falsealarm.txt`).
