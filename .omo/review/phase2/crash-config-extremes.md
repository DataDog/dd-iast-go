# crash-config-extremes: internal/config under extreme/malformed DD_IAST_* values, plus a woven sample

Verdict: `internal/config` (parser, loader, config) never panics on any extreme or malformed `DD_IAST_*` value tested, always clamps numeric values to their documented bounds or falls back to the documented default with a warning, and the woven request/SQL-sink pipeline behaves correctly (bounded, no panic, no data race) when driven with the post-clamp values those extremes resolve to. One documentation gap was found (undocumented hard upper bound on `DD_IAST_VULNERABILITIES_PER_REQUEST`); no Critical or High defects were found.

Scope covered:
- Read: `internal/config/config.go`, `internal/config/init.go`, `internal/config/loader/loader.go`, `internal/config/parser/parser.go`, and their existing `*_test.go` (all pre-existing tests pass unmodified), `internal/model/truncation/truncation.go`, `internal/model/truncatedside.go`, `internal/taint/ranges/ranges.go`, `internal/taint/redaction/source.go`, `internal/spans/annotation.go`, `internal/taint/request/scope.go`, `internal/model/event.go`, `README.md` (Runtime Configuration table).
- Ran: `go test ./internal/config/...` (pre-existing suite, baseline), `go test ./internal/... -timeout 300s` (26 packages, baseline), a purpose-built `cmd/configdump` harness driving `internal/config`'s real `init()` across 57 environment combinations covering the full brief matrix (`DD_IAST_MAX_RANGE_COUNT`, `DD_IAST_TRUNCATION_MAX_VALUE`, `DD_IAST_VULNERABILITIES_PER_REQUEST`, `DD_IAST_MAX_CONCURRENT_REQUESTS`, `DD_IAST_REQUEST_SAMPLING`, invalid/unterminated regexes for both redaction patterns and their compatibility aliases, `DD_IAST_REDACTION_ENABLED`, `DD_IAST_ENABLED`), and a new woven end-to-end test file (`iast/integration/testapp/config_extremes_test.go`) exercising 9 scenarios through `go tool orchestrion go test -race` against the real HTTP-\>SQL-sink path.

## Findings

### crash-config-extremes-F1: `DD_IAST_VULNERABILITIES_PER_REQUEST`'s hard upper bound of 64 is undocumented
- Severity: Medium
- Category: doc
- Location: `README.md:117` (documented range) vs `internal/config/config.go:34,75` (enforced range)
- Claim: `README.md:117` documents `DD_IAST_VULNERABILITIES_PER_REQUEST` as "Integer greater than or equal to `1`" with no stated upper bound. `internal/config/config.go` actually clamps it to `[1, MaxVulnerabilitiesPerRequest]` where `MaxVulnerabilitiesPerRequest = 64` (`config.go:34,75`). `README.md:95-96` documents a *different*, narrower nuance (`VULNERABILITIES_PER_REQUEST` limits each orphan event but not the total findings from a request) but never states the 64 hard cap that the loader enforces for every value, including the documented example of `1000000` from the review matrix. This violates the `internal/config/AGENTS.md` instruction that "the documentation must accurately describe every available environment variable, including its accepted values". Confirmed with the reproducer: setting `DD_IAST_VULNERABILITIES_PER_REQUEST=1000000` resolves to `64` with a warning (`configdump_matrix_results.json`, case `vuln_per_request=1000000`), and the woven end-to-end reproducer confirms the same hard cap holds under real sink load (`TestConfigExtremesVulnerabilitiesPerRequestHardMaxSixtyFour`).
- Evidence: `.omo/review/evidence/crash-config-extremes/configdump_matrix_results.json` (case `vuln_per_request=1000000`, `.omo/review/evidence/crash-config-extremes/README.md` section 1) + `.omo/review/evidence/crash-config-extremes/config_extremes_test.go` (`TestConfigExtremesVulnerabilitiesPerRequestHardMaxSixtyFour`) + `.omo/review/evidence/crash-config-extremes/woven_run2_race_pass.log` (PASS). Command: `GOTOOLCHAIN=go1.26.6 go build -o /tmp/ddiast-review/configdump ./cmd/configdump && DD_IAST_VULNERABILITIES_PER_REQUEST=1000000 /tmp/ddiast-review/configdump` -> `"vulnerabilities_per_request": 64, "warnings": ["invalid value for DD_IAST_VULNERABILITIES_PER_REQUEST (expected integer between 1 and 64): 1000000"]`.
- Fix: add the upper bound to the README row, e.g. `Integer from 1 to 64`, matching the `DD_IAST_MAX_CONCURRENT_REQUESTS`/`DD_IAST_MAX_RANGE_COUNT` rows' style.

## Checked and found correct

- **No panic across the full extreme/malformed matrix.** A 57-combination harness (`cmd/configdump`, evidence `configdump_main.go` + `configdump_matrix_results.json`) drove real process `init()` runs of `internal/config` with `DD_IAST_MAX_RANGE_COUNT` = `1,64,0,-5,abc`; `DD_IAST_TRUNCATION_MAX_VALUE` = `0,1,huge,` a uint64-overflowing number, and exactly `math.MaxUint64`; `DD_IAST_VULNERABILITIES_PER_REQUEST` = `1,1000000,0,-1,abc`; `DD_IAST_MAX_CONCURRENT_REQUESTS` = `0,64,1000,-1,abc`; `DD_IAST_REQUEST_SAMPLING` = `0,100,150,-1,abc`; six malformed regex bodies (unterminated group, unterminated class, invalid repetition, unterminated named group, a bare backslash, unbalanced close-parens) against both canonical redaction env vars and their compatibility-alias fallbacks; and 8 boolean spellings against `DD_IAST_REDACTION_ENABLED`/`DD_IAST_ENABLED`. All 57 processes exited 0 with no panic.
- **Numeric clamping matches the README table exactly.** `DD_IAST_MAX_RANGE_COUNT=0` clamps to `1` (not `0`) with a warning; `-5`/`abc` fall back to the default `10` (not to `0` or a parse crash), matching `parser.UintFromEnv`'s "invalid input keeps the default" contract before `ClampUnsigned` even runs (`loader.go:60-71`). `DD_IAST_MAX_CONCURRENT_REQUESTS=1000` clamps to `64`; `=0` is accepted verbatim (`0` is in-bounds and documented as "disables request analysis", `README.md:116`). `DD_IAST_REQUEST_SAMPLING=150` clamps to `100`. `DD_IAST_VULNERABILITIES_PER_REQUEST=1000000` clamps to the hard max `64`; `=0` clamps up to `1` (the documented minimum), not down to `0`.
- **Negative numbers and non-numeric strings cannot be misread as valid unsigned values.** `strconv.ParseUint(raw, 10, 64)` (`parser.go:75-83`) rejects a leading `-` and non-digit input outright (`err != nil`), so `-5`/`-1` fall back to the *default*, not to a huge two's-complement-wrapped `uint64`. Verified directly for every negative-number case in the matrix (`max_range_count=-5`, `vuln_per_request=-1`, `max_concurrent_requests=-1`, `request_sampling=-1`), and separately by the pre-existing `parser_test.go` (`TestUintFromEnv/negative_falls_back`).
- **`DD_IAST_TRUNCATION_MAX_VALUE` has no documented or enforced upper bound, and this is intentional and safe.** `internal/config/config.go:80` calls `loader.UintFromEnv` (unbounded) rather than `UintFromEnvBounded`, and `README.md:122` documents the type as "Non-negative integer" with no stated ceiling, so code and doc agree. Setting it to `math.MaxUint64` (verified in the matrix) does not create unbounded memory: `truncation.String` (`internal/model/truncation/truncation.go`) only ever returns the input unchanged or a bounded clone of it, and the value it is applied to is already capped upstream by independent, unrelated bounds (32 KiB SQL/command analyzer input, 256 KiB evidence snapshot workspace, 25,000-byte encoded event -- architecture doc, "Bounds and enforcement"). Confirmed end-to-end with `TestConfigExtremesTruncationMaxValueHuge` (woven, PASS) and `=0` truncating a source value to the empty string without dropping the vulnerability report (`TestConfigExtremesTruncationMaxValueZero`, PASS).
- **`DD_IAST_MAX_CONCURRENT_REQUESTS=0` cleanly disables analysis end-to-end**, confirmed via the woven reproducer (`_dd.iast.enabled` span tag reads `0`, zero vulnerabilities reported) and via package-init ordering: `internal/spans/annotation.go:31,34` compute `2 * config.MaxConcurrentRequests` and `max(config.MaxConcurrentRequests*3/4, 1)` as package-level var initializers, which Go guarantees run only after the imported `internal/config` package (including its `init()` that resolves the env var) has fully finished initializing -- so there is no zero-value/race window where `spans` reads `config.MaxConcurrentRequests` before it is resolved.
- **Saturation under a clamped `DD_IAST_MAX_CONCURRENT_REQUESTS=1000` (-\> 64) drops analysis rather than blocking, crashing, or racing.** 256 concurrent real HTTP requests (four times the clamped ceiling) against one woven server all completed and were captured by the tracer with `go test -race`, with no panic and no race report.
- **Invalid regexes for `DD_IAST_REDACTION_NAME_PATTERN`/`DD_IAST_REDACTION_VALUE_PATTERN` (and their `_KEYS_REGEXP`/`_VALUES_REGEXP` fallback aliases) fall back to the built-in default pattern with a warning, never a nil pattern or a panic.** Verified for six different malformed bodies against both variables and both aliases (12 cases total in the matrix); Go's `regexp` package (RE2) has no catastrophic-backtracking pathway, so an adversarial pattern string cannot cause a ReDoS-style hang even before the fallback applies. `loader.FromEnvWithFallback`'s documented contract ("canonical takes precedence even when it is invalid") was also verified directly.
- **Boolean parsing (`DD_IAST_ENABLED`, `DD_IAST_REDACTION_ENABLED`) never crashes and always falls back safely.** `yes`, `no`, and empty string are all rejected by `strconv.ParseBool` and fall back to the default (`true`) with a warning; `0`/`1`/`true`/`FALSE`/`false` all parse as expected case-sensitively per `strconv.ParseBool`'s accepted forms.
- **`internal/config`'s own pre-existing unit-test suite (parser, loader, config) passes unmodified**, and the whole `internal/...` tree (26 packages, including `internal/taint/ranges`, `internal/taint/request`, `internal/taint/redaction`, `internal/spans`, `internal/model`) passes with 0 failures.

## Not covered / open questions

- The woven scenarios were driven by directly assigning `internal/config` package variables to the exact post-clamp values the environment matrix resolves to, not by re-executing the woven test binary once per `DD_IAST_*` environment combination. This is because `iast/integration/testapp`'s existing test package always overrides `internal/config` in its own `init()` (see `e2e_test.go:36-45`), so environment variables set before the test process starts would be immediately clobbered regardless; the config-parsing layer itself (parser/loader, which does react to real environment variables) was separately proven correct by the 57-combination `configdump` harness. A from-scratch woven test package without that override, re-executed per environment combination via `go test -c` + subprocess, would be a stronger (but much slower) version of the same check; it was judged not worth the extra machine time given the parsing layer and the downstream consumers were each independently verified.
- `DD_IAST_TELEMETRY_VERBOSITY`, `DD_IAST_DB_ROWS_TO_TAINT`, `DD_IAST_STACK_TRACE_ENABLED`, and `DD_IAST_DEDUPLICATION_ENABLED` were not in the brief's matrix and were not separately fuzzed; `DD_IAST_TELEMETRY_VERBOSITY`'s parser (`parser.ParseLogLevel`) is a plain exact-match switch with a default fallback and was inspected but not driven through extreme inputs beyond what the pre-existing `parser_test.go` already covers.
- The full woven suite (`go tool orchestrion go test -shuffle=on ./...`) was not run end-to-end under any of the extreme configs; only the new targeted `config_extremes_test.go` file (9 scenarios) plus the pre-existing `internal/config`/`internal/...` suites were run, per the brief's "run the woven integration tests under a few of these" (not all).
