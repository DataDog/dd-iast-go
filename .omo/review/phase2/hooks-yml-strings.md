# hooks-yml-strings: strings join points and replacement advice
Verdict: One Critical compile break: valid strings method expressions are mistaken for direct method calls; the tested direct function calls preserve results, types, and provenance.
Scope covered: `iast/propagation/orchestrion.yml:12-715,1057-1250,1473-1552`; `iast/propagation/{strings,coarse,writer}.go`; `internal/taint/propagation/{propagation,string_exact,string_coarse}.go`; `iast/internal/propagationtest/strings.go`; `iast/propagation/strings_test.go`; pinned Orchestrion's `internal/injector/aspect/join/{expression,method_call}.go` and `advice/call.go`; README propagation coverage. Executed Go 1.26.6 plain and woven tests in a private copy.

## Findings
### hooks-yml-strings-F1: Method expressions match direct method-call advice and fail to compile
- Severity: Critical
- Category: compile-break
- Location: iast/propagation/orchestrion.yml:1089-1103,1521-1535
- Claim: The `strings.Builder.WriteString.pointer` and `strings.Replacer.Replace.pointer` pointcuts match calls of the valid method-expression forms `(*strings.Builder).WriteString(&builder, value)` and `(*strings.Replacer).Replace(replacer, value)`. The pinned Orchestrion `methodCall.Matches` checks the resolved type of `selector.X` but does not distinguish a type expression from a receiver value. The advice consequently substitutes the *type* for the receiver and treats the actual receiver as the first data argument. Woven valid customer code fails to compile; the same code compiles without weaving. The same mechanism applies to the other pointer-receiver strings method-call aspects.
- Evidence: `.omo/review/evidence/hooks-yml-strings/zz_review_strings.go` and `.omo/review/evidence/hooks-yml-strings/method-expressions.out.txt`. Place the source in `iast/internal/propagationtest/` of the private copy. From its root, `GOTOOLCHAIN=go1.26.6 go test -timeout 15m -count=1 -run TestReviewReplacerReceiverAndArgumentEvaluateOnce -v ./iast/propagation` passes compilation; `GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -timeout 15m -count=1 -run TestReviewReplacerReceiverAndArgumentEvaluateOnce -v ./iast/propagation` fails with `(*strings.Replacer) (type) is not an expression`, `cannot use strings.NewReplacer(...) ... as string ... ReplacerReplace`, `(*strings.Builder) (type) is not an expression`, and `cannot use &builder ... as string ... BuilderWriteString`. The exact test file is also preserved at `.omo/review/evidence/hooks-yml-strings/zz_review_strings_test.go`.
- Fix: In the pinned Orchestrion `method-call` matcher, reject selector receivers that denote types (method expressions) before applying any of these advice templates. Keep direct receiver calls eligible, including addressable value receivers. Add a woven compile regression for pointer method expressions and a direct-call positive control.

## Checked and found correct
- The `strings.Clone`, `Cut*`, `Split*`, `Fields*`, `Trim*`, `Lines`, `Join`, `Repeat`, `Replace*`, `To*`, and `Map` function-call pointcuts resolve a package-qualified symbol and replace only the callee, retaining argument expressions, evaluation order, variadic markers if present, and multiple result positions. The wrapper signatures read in `strings.go`/`coarse.go` match these stdlib functions; the `function-call` matcher checks the import path rather than an unrelated method of the same name.
- Direct named-string conversions and generic `T ~string` calls to `strings.TrimSpace` and `strings.Cut` preserved taint; both `Cut` returns were observed. Direct `(*strings.Replacer)` receiver and data expressions were each evaluated once, with the expected output and taint. Woven command and results: `.omo/review/evidence/hooks-yml-strings/direct-calls.out.txt`. This test was run before adding the compile-failure method expressions.
- The five iterator wrappers produced the same yielded strings as native functions. In the no-owner allocation probe, native and wrapped iterator factory allocations were equal for all five operations (2 or 3 allocations/call in that probe); this does not establish general performance parity.
- Indirect function calls are a documented safe miss; the existing `TestIndirectStringCallIsUnsupported` checks `strings.Clone` through a function value. For method *values*, the pinned matcher needs a `CallExpr` whose `Fun` is a selector, so calling a stored method value does not match it.
