# crash-fuzz-engine: long fuzz campaigns for the propagation engine (FuzzEngineSequence, FuzzOwnerLifecycle)
Verdict: No crasher, oracle mismatch, panic, or leak was found in 18.3M fuzz executions (15m per target, -parallel=4, go1.26.6), and the engine's store charge, value counts, and heap return to baseline. Both campaigns, however, cover only the exact-operation subset of the engine: coarse, drop, case, UTF-8, fan-out, concat, JSON, and writer paths stay at 0% coverage, so the clean result says nothing about them.
Scope covered: internal/taint/propagation/{sequence_fuzz_test.go, owner_lifecycle_fuzz_test.go, sequence_fixture_test.go, sequence_oracle_test.go, sequence_operations_test.go, sequence_replace_test.go, sequence_property_test.go}. Ran both fuzz targets. Replayed the resulting corpus (366 + 73 entries) with -coverpkg over propagation/store/ranges. Ran a heap-growth probe over 200k iterations of each harness body. Propagation code was read only as far as needed to map coverage (propagation.go:33-40, string_exact.go:17,50-63).

## Findings
### crash-fuzz-engine-F1: The engine fuzzer is built so it never reaches the exact-to-coarse, drop, or non-exact paths
- Severity: Medium
- Category: test-gap
- Location: internal/taint/propagation/sequence_operations_test.go:18,131,138; internal/taint/propagation/sequence_replace_test.go:26-31; target code internal/taint/propagation/string_exact.go:17,50-63, propagation.go:33-40
- Claim: FuzzEngineSequence can generate only 6 operations: Copy, Window, Repeat, Join, Replace, and BytesToString. The harness also limits each operation so that the budget-exceeding and coarse-fallback branches can never execute:
  - Join always receives exactly 2 elements (`elements := []string{first.text, second.text}`, lines 131 and 138), so the >16 `maxInputs` coarse/reserved-separator branch (string_exact.go:53-63) is unreachable.
  - Replace always uses a 1-byte `old` (`old := input.valueBytes()[oldIndex : oldIndex+1]`, line 26), so the empty-pattern path is unreachable.
  - Replace `count` is drawn from `{1,2,3,-1}`, and `-1` is rewritten to `3` whenever matches exceed 32 (lines 27-31). So `maxReplaceMatches = 32` (string_exact.go:17) is never exceeded and the exact-to-coarse transition never runs.

  In the replayed corpus from both 15-minute campaigns, the following have 0.0% statement coverage: CoarseString, CoarseBytes, coarseMatch, coarseAccumulate, CaseString, CaseBytes, ValidUTF8Bytes, StringWindows, ByteWindows (the 32-window fan-out), Concat2-16, JSONString, AdoptStringCopy, CoarseFormat*, all of writer.go, and both `recordCoarse` and `recordDropped`. `mapReplaceSegments` and `mapReplaceByteSegments` reach only 55.3%. These paths are architecture risk area #7 ("exact-to-coarse range transitions under truncation and multibyte transforms"). Fixed-input unit tests cover them (for example TestReplaceStringHandlesEmptyPatternAndCoarseLimit, TestCoarseTransitionHonorsSixteenInputInspectionBound, and TestCaseStringUsesExactASCIIAndCoarseUnicodeRanges). No property-based oracle cross-checks them against random multi-owner, multi-range inputs, so the "no crash / oracle agrees" result does not cover them.
- Evidence: `.omo/review/evidence/crash-fuzz-engine/fuzz-corpus-coverage.func.txt`. Produced by copying the fuzz cache into `testdata/fuzz/` in the private copy, then `go test -count=1 -run '^(FuzzEngineSequence|FuzzOwnerLifecycle)$' -coverpkg=./internal/taint/propagation,./internal/taint/store,./internal/taint/ranges -coverprofile=... ./internal/taint/propagation/` followed by `go tool cover -func`. Key lines: `propagation.go:326: CoarseString 0.0%`, `string_coarse.go:20: CaseString 0.0%`, `bytes_exact.go:244: ValidUTF8Bytes 0.0%`, `propagation.go:220: StringWindows 0.0%`, `telemetry.go:11: recordCoarse 0.0%`, `telemetry.go:12: recordDropped 0.0%`, `string_exact.go:191: mapReplaceSegments 55.3%`, total 34.8% of propagation+store+ranges.
- Fix: Extend `applySequenceOperation` with Coarse{String,Bytes} (oracle: first contributor per owner with mark intersection, as already encoded in TestCoarseTransitionUsesFirstContributorAndMarkIntersectionPerOwner), Case{String,Bytes}, ValidUTF8Bytes, String/ByteWindows, and ConcatN. Let Join take 1-20 elements, let Replace take 0-3-byte `old` including empty, and add counts of 0 and unclamped `-1`, with the oracle switching to the coarse expectation above 32 matches or 16 inputs.

### crash-fuzz-engine-F2: FuzzOwnerLifecycle fuzzes only data; the lifecycle sequence is fixed and single-threaded
- Severity: Low
- Category: test-gap
- Location: internal/taint/propagation/owner_lifecycle_fuzz_test.go:30,45-129
- Claim: The fuzz input chooses the string bytes, the single range position, the marks, the number of cycles (1-8), and whether a sibling exists. The operation order is always the same: acquire → adopt string → CopyString → one-byte drop → optional sibling → Finish → stale adopt → acquire (same slot) → stale CopyString → Finish. Only string roots and CopyString are used. No byte roots, windows, joins, or mutations touch a stale owner, and nothing runs concurrently. The fuzzer therefore cannot explore the lifecycle interleavings the architecture ranks riskiest (#2 and #3: Finish racing lookup/publish, and root-generation claims versus value reservations). The corpus plateaued at 73 entries (36 new) after 10.7M execs, which is consistent with a nearly parametric test. Race coverage exists only in two fixed goroutine tests (propagation_test.go:850 and bytes_exact_test.go:370).
- Evidence: `.omo/review/evidence/crash-fuzz-engine/fuzz-OwnerLifecycle-15m.log` (final line `execs: 10749080 ... new interesting: 36 (total: 73)`); code structure at the lines cited.
- Fix: Drive the lifecycle from the cursor, with an operation byte that picks acquire/finish/adopt{String,Bytes}/window/copy/join/publish-mutation against any live or finished owner handle. Add a variant that runs one operation stream per goroutine against shared roots, under `-race`.

## Checked and found correct
- There were no crashes, panics, or oracle mismatches in 7.6M FuzzEngineSequence executions. The oracle strictly compares per-owner ranges and per-byte attribution with native results, across 2 owners and 8 steps (sequence_oracle_test.go:143-218). So the six exact operations preserve native values and exact ranges on random mixed-UTF-8, invalid-UTF-8, and multi-owner inputs within the 10-range limit.
- There were no failures in 10.7M FuzzOwnerLifecycle executions. Across every fuzz input and cycle, process charge and value count returned to their baseline (owner_lifecycle_fuzz_test.go:34-39). After Finish, a finished owner never admitted a root, a slot was reused with an advanced ID/generation, a stale-owner CopyString published nothing, and one-byte roots were deterministically dropped with the counter incremented.
- No heap growth came from engine state. With `review_probe_heap_test.go`, 200k runEngineSequence iterations after warm-up gave a HeapInuse delta of 0 with charged=0 and values=0, and 200k lifecycle cycles without `t.Cleanup` also gave a delta of 0 (`heap-probe-lifecycle-nocleanup.log`). The variant that keeps the harness's `t.Cleanup(owner.Finish)` grows about 1.4 KB per cycle (`heap-probe-with-cleanups.log`). That growth is `testing.common.Cleanup` storing a `runtime.Callers` PC array for each registration on a long-lived `T`. It is a harness artifact with no effect under fuzzing, where each input gets a fresh `T`. The one fuzz worker whose RSS grew from 160 MB to 256 MB during the campaign fits GC variance and not a leak.
- Before fuzzing, the baseline `go test ./internal/taint/propagation/` (go1.26.6) passed.

## Not covered / open questions
- Coarse, case, UTF-8, fan-out, Concat, JSON, and writer propagation were not fuzzed (see F1). A follow-up node should add a generator for those operations and run it.
- Only go1.26.6 was used. go1.27.0 was not fuzzed.
- The fuzz targets run without `-race`, and neither is concurrent. Concurrency safety is left to the dedicated race nodes.
- The corpus was seeded from the shared GOCACHE fuzz cache (327 baseline entries for FuzzEngineSequence), so some starting corpus came from earlier runs on this machine. This affects only how efficient the run was, not the negative result.
