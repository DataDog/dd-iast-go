# store-api-misuse: store caller contract audit
Verdict: No Critical or High store API misuse found; two limited caller-side contract violations remain.
Scope covered: All production imports of `internal/taint/store` under `internal/taint/request`, `internal/taint/propagation`, `internal/taint/evidence`, `iast/propagation`, `iast/os/exec`, and `internal/spans`; exported declarations and supporting implementation in `internal/taint/store/{store,owner,root,value,lookup,mutation,binding,writer,limits}.go`; direct wrapper callers in `iast/propagation/{strings,bytes,coarse,writer}.go`, JSON callback in `iast/encoding/json/json.go`, request scope and reader paths. Plain store, request, and propagation tests were run in the private copy with Go 1.26.6.

## Findings

### store-api-misuse-F1: Unbounded alias scan before the active-store gate
- Severity: Medium
- Category: perf
- Location: internal/taint/propagation/string_exact.go:24-44
- Claim: `JoinString` examines **every** element of a `strings.Join` result when the separator is empty, before checking `request.ActiveStore()`. This runs even for disabled or sampled-out requests, although the same function promises to inspect at most sixteen elements for provenance and the native join has already traversed them. A very large clean join pays an additional unbounded pass solely to look for an alias that can be relevant only when a store is active. This violates the caller's cheap-gate/bounded-work contract, not the store's memory bound.
- Evidence: static reasoning only (NEEDS-REPRO): lines 24-40 loop across `elements` without an admission bound; the active-store check is at line 42. The wrapper invokes this after native `strings.Join` at `iast/propagation/strings.go:107-111`. No timing claim is made.
- Fix: Put the active-store gate before the alias scan, and avoid a full alias-discovery pass when the element count exceeds the documented inspection bound.

### store-api-misuse-F2: JSON reports publication after failed store adoption
- Severity: Medium
- Category: quality
- Location: internal/taint/propagation/json.go:42-69
- Claim: `JSONString` documents its boolean as indicating that a managed clone **was published**, but `jsonStringHit` creates a clone and returns `true` even if every `owner.AdoptString` fails (for example, a full root quota or a contended store lock). `iast/encoding/json/json.go:39-42` then replaces the decoded string despite no store entry for that clone. The native value's bytes stay the same, but the callback does needless allocation and reports a false success at precisely the bounded-drop boundary.
- Evidence: static reasoning only (NEEDS-REPRO): `clone` is set at lines 56-57, `owner.AdoptString`'s `(RootRef, bool)` is ignored at line 60, and lines 64-69 test only whether `clone` is nonempty. Store adoption can fail at `internal/taint/store/root.go:251-267`.
- Fix: Set the returned publication flag only after at least one `AdoptString` returns `ok`, and return the original result when every adoption fails.

## Checked and found correct

- **Key and lookup contracts:** `StringKey`/`BytesKey` require nonempty values fitting `uint32`; every production key user checks `ok`, or deliberately uses a zero key only as a gate (`stringKey` in `string_coarse.go:201-204`). `MayContain` is only a candidate test; the propagation, request, and sink paths use `Lookup`/`VisitString` for actual provenance. `Lookup` requires a valid key and nonnil snapshot and clears a valid-key snapshot before reporting a lock miss. All production lookups use fresh snapshots; the ignored lookup boolean in `propagation/writer.go:99` therefore leaves an empty snapshot on contention, not stale input. `Snapshot.Len` and `At` guard bounds, and their callers iterate over `Len` and test `At`'s boolean.
- **Owner lifecycle and source transactions:** `Store.Acquire` always returns a handle (possibly disabled); `Manager.Acquire` tests `Disabled` and releases its permit on rejection. `Scope.Analysis` excludes sampled-out, capacity-dropped, and finished requests before calling source methods. `TaintString`, `TaintBytes`, `TaintSourceString`, `TaintSourceBytes`, and `AdoptSourceBytes` all require a live owner and two or more bytes, with a 64 KiB root bound, byte-capacity bound, and metadata charge where appropriate. Request callers hold `sourceMu`, check publication success before committing source metadata, and return the original value on failure. `Finish` releases the owner and permit once. The only `RecordBytesDrop` call is on a revalidated bound owner after oversize rejection.
- **Roots and mutable views:** `AdoptString` requires a complete allocation-base string and a valid range set; its production calls use a fresh clone, a `strings.Clone` result, a decoded result, or the audited byte-to-string conversion. `AdoptBytes` requires a complete base and bounded capacity; the byte wrappers use native fresh results, while `ReadAllBytes` checks both length and capacity before adopting `io.ReadAll`'s result and `CloneReaderBytes` makes its own exact-capacity allocation. `Derive` requires a live root reference and a contained key; all production calls take `Entry.Root` from a snapshot, revalidate via `Entry.Handle`, and first check the returned substring/subslice aliases the input. `PublishBytesMutation` has no production caller; its post-mutation generation contract is not exercised by this caller audit. Ignored adoption/derivation booleans elsewhere only drop taint while retaining the host result.
- **Bindings and writers:** `BindObjectValue` accepts only a nonnil dynamic pointer and a live owner; eager HTTP and reader binding failures are safe misses. `LookupObjectValue` bounds its result by the caller's four-element array, and `OwnerRef.Handle`/`Identity` validate generation before use. `LookupWriterValue` is similarly bounded; all writer wrappers supply receiver and captured before/after views, and `WriterRef.Handle` is checked before adoption, update, reset, truncation, or snapshot. `UpdateWriter` requires valid views and written length not exceeding input length; the wrapper checks negative/oversize counts. Ignored writer update results drop provenance, while failed writer locks dirty the owner state. `InvalidateBuffer` and `InvalidateWriterPointer` are guarded against inactive/nil stores and zero pointers.
- **Initialization and ancillary exports:** `BindWriterActive`, `BindOperatorActive`, and `ActiveValues` are called only on the nonnil store created by `defaultManager`, before `processManager.Store`. Counters/health accessors (`ProcessCharged`, `ProcessValues`, `AcquireDrops`, `Stats`, `Owner.Charged`, `Values`, `Counters`, `ID`, `Generation`, `Index`, `Disabled`, `HasWriterStates`) do not feed unvalidated provenance; the production owner index and generation consumers check their `ok`/active status. `New` supplies the fixed store; no production caller depends on a caller-held store lock.
- `GOTOOLCHAIN=go1.26.6 go test -timeout 8m ./internal/taint/store ./internal/taint/request ./internal/taint/propagation` passed in `/tmp/ddiast-review/wt/store-api-misuse`.

## Not covered / open questions

- Neither Medium performance overhead nor JSON saturation behavior has a standalone reproducer; both findings rest on the cited control flow. No Critical or High issue was suspected, so no Critical/High reproducer is outstanding.
- Other nodes own the store's internal accounting, compiler weave, and overall sink reporting correctness. This audit checked store calls and their immediate source/propagation/writer boundaries, not all instrumented customer programs.
