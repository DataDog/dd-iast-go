# hooks-fidelity-bytes: differential fidelity of bytes and writer wrappers vs stdlib
Verdict: All 28 `bytes.*` wrappers, the 6 byte-slice operator wrappers, `BytesToString`, and all 15 `strings.Builder`/`bytes.Buffer` wrappers return results that match the stdlib byte for byte. That includes panics, predicate side effects, result aliasing (offset, len, cap), mutation through results, and writer state, across 708k randomized comparisons on Go 1.26.6 and Go 1.27.0. However, the writer `method-call` advice breaks compilation of valid customer code that uses method expressions (Critical). `Builder.String` also clones tainted results by design (Low).

Scope covered: `iast/propagation/bytes.go` (all 28 wrappers), `iast/propagation/writer.go` (all 15 wrappers plus `builderView`/`bufferView`), the `BytesSlice*`/`BytesToString` operator wrappers in `operators.go:198-304`, and `iast/propagation/orchestrion.yml:805-1055` (bytes function calls), `1057-1519` (writer method calls), and `1553-1680` (native `bytes.Buffer` invalidation hooks). I also read `internal/taint/propagation/{propagation.go:420-720, writer.go}` and orchestrion `internal/injector/aspect/join/method_call.go` and `aspect/context/context.go:302-340` at the pinned rev `23afa71d6dcb`. I compared stdlib `bytes/buffer.go`, `strings/builder.go`, and `bytes/bytes.go` between Go 1.26.6 and Go 1.27.0. All runs used the private copy `/tmp/ddiast-review/wt/hooks-fidelity-bytes`.

## Findings

### hooks-fidelity-bytes-F1: Writer advice breaks compilation of method-expression calls such as `(*bytes.Buffer).WriteString(&b, s)`
- Severity: Critical
- Category: compile-break
- Location: iast/propagation/orchestrion.yml:1057-1071, 1089-1103, 1121-1135, 1153-1167, 1185-1199, 1217-1231, 1249-1263, 1281-1295, 1313-1327, 1345-1359, 1377-1391, 1409-1423, 1441-1455, 1473-1483, 1497-1507 (every `match: pointer-only` writer aspect). The root cause is in orchestrion `internal/injector/aspect/join/method_call.go` (`Matches`: `recvType := ctx.ResolveType(selector.X)`) at `23afa71d6dcb`.
- Claim: `methodCall.Matches` resolves the type of `selector.X` through `typeInfo.Types`. That map also records *type* expressions. In the method-expression call `(*bytes.Buffer).WriteString(&b, s)`, `X` is the type expression `(*bytes.Buffer)`, so it resolves to `*bytes.Buffer` and matches `pointer-only`. The template `iastpropagation.BufferWriteString({{ .AST.Fun.X }}, {{ index .AST.Args 0 }})` then produces `BufferWriteString((*bytes.Buffer), &b)`. That code passes a type as a value, drops the real argument `s`, and puts `&b` in the string slot, so the build fails. This is valid Go that customers do write. Method expressions are common in table-driven code and generic helpers. Any root-module package that contains such a call fails to build under Orchestrion. Unwoven builds are unaffected. The value-only aspects cannot hit this because `bytes.Buffer.M` is not a valid method expression for pointer methods. The `strings.Replacer.Replace.pointer` aspect (orchestrion.yml:1521-1535) uses the same matcher and template shape, so it breaks the same way (static reasoning; its fixture belongs to the strings node).
- Evidence: fixture `.omo/review/evidence/hooks-fidelity-bytes/iast__internal__zzfid__methodexpr__methodexpr.go` with test `..._methodexpr_test.go`. It was installed at `iast/internal/zzfid/methodexpr/` in the private copy. `GOTOOLCHAIN=go1.26.6 go test ./iast/internal/zzfid/methodexpr` gives `ok` (PASS). `GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -count=1 ./iast/internal/zzfid/methodexpr` fails with exit status 1 (full output in `woven-methodexpr-go1.26.6.txt`, unwoven control in `plain-methodexpr-go1.26.6.txt`). I could not isolate this on Go 1.27.0: the woven build stops earlier on the known encoding/json JSON-v2 break (phase1 base-test-127; `woven-methodexpr-go1.27.0-blocked-by-json.txt`). The matcher logic does not depend on the toolchain version:
  ```
  methodexpr.go:12: (*bytes.Buffer) (type) is not an expression
  methodexpr.go:12: cannot use &b (value of type *bytes.Buffer) as string value in argument to __orchestrion_iastpropagation.BufferWriteString
  methodexpr.go:18: (*strings.Builder) (type) is not an expression
  FAIL	github.com/DataDog/dd-iast-go/iast/internal/zzfid/methodexpr [build failed]
  ```
- Fix: in orchestrion `methodCall.Matches`, reject a receiver that is a type expression, for example by checking `typeInfo.Types[astX].IsType()`. Alternatively, have the join point match only `*types.Selection` of kind `MethodVal` using `typeInfo.Selections[sel].Kind()`. That second check also cleanly excludes `MethodExpr`. Add a woven fixture with method-expression calls for every hooked receiver (Builder, Buffer, Replacer) to `iast/internal/propagationtest`. Then bump the orchestrion pin.

### hooks-fidelity-bytes-F2: Wrapped `strings.Builder.String` returns a fresh clone instead of the builder-aliasing string whenever the builder carries taint state
- Severity: Low
- Category: perf
- Location: internal/taint/propagation/writer.go:190-200, 222-225 (`publishWriterString(..., clone=true)` then `strings.Clone(result)`), called from iast/propagation/writer.go:278-284
- Claim: Native `Builder.String()` is O(1) and allocation-free. It returns `unsafe.String(unsafe.SliceData(b.buf), len(b.buf))`, which aliases the builder buffer. When the builder has tracked writer state, the wrapper returns a copy (2 to 65,536 bytes) on every call. Content, length, and all Go-visible semantics are identical because strings are immutable. Only `unsafe.StringData` identity and allocation behavior differ, so I rate this below Critical despite the aliasing focus. This is the documented design: the plan says to "clone a tainted `String` result to a managed root" (`_docs/plans/taint-tracking-net-http-sqli-cmdi.md:569`, `propagation-coverage-matrix.md:429`). The cost is real, though. A loop that calls `b.String()` after each write in a tracked request becomes O(n²) in copied bytes, bounded at 64 KiB per call. The clone is also made before `AdoptString` can fail on a saturated budget, so saturated requests still pay the copy without gaining provenance.
- Evidence: `TestFidelityBuilderStringIdentityAndAllocs` and `TestFidelityWritersDifferential` in `.omo/review/evidence/hooks-fidelity-bytes/iast__propagation__zz_fidelity_bytes_test.go`. Output is in `plain-diff-go1.26.6.txt`: `wrapped ptr==native ptr: false`, `allocs/op for String() on a 6000-byte tainted builder: native=0.0 wrapped=1.0`, and identity divergence `inactive=0 active-clean=0 tainted=3971 foreign-owners=4144` with content always equal.
- Fix: optional. Adopt the builder buffer prefix directly. It starts at its allocation base, and Builder never rewrites written bytes. Alternatively, check root budget and owner admission before cloning so saturated requests do not pay for a copy they cannot publish.

### hooks-fidelity-bytes-F3: Go 1.27 `bytes.CutLast`/`strings.CutLast` are unhooked although README advertises `Cut*` windows
- Severity: Low
- Category: doc
- Location: README.md:30,33; iast/propagation/orchestrion.yml:832-857 (only `Cut`, `CutPrefix`, `CutSuffix`)
- Claim: Go 1.27.0 adds `CutLast` to both `bytes` (`bytes.go:1430`) and `strings` (`strings.go:1295`). It returns windows of its input. No aspect wraps it, so `before`/`after` lose taint on Go 1.27. That is a safe miss with no behavior change, but README's `Cut*` wording claims support. Go 1.27 is the machine default and is expected at customers.
- Evidence: static. `grep -c CutLast iast/propagation/orchestrion.yml` gives `0`. The Go 1.27 stdlib declarations are quoted above.
- Fix: add `bytes.CutLast`/`strings.CutLast` aspects behind a Go 1.27 build constraint (window derivation identical to `Cut`), or narrow the README wording.

## Checked and found correct
- **Byte function results (28 wrappers plus 6 slice operators plus `BytesToString`)**: I ran a randomized differential run with 3,000 iterations × 35 ops × 4 modes (inactive, active-clean, tainted, foreign 3-owner) on Go 1.26.6 and Go 1.27.0. That is 420,000 comparisons per toolchain with 0 failures (`plain-diff-go1.26.6.txt`, `plain-diff-go1.27.0.txt`). Inputs sit at random offsets inside larger backing arrays, with and without spare capacity, and include nil, empty non-nil, invalid UTF-8, multi-byte case-changing runes (`İ`, `ǅ`, `ß`, `ﬀ`, `Σ/ς`), 0–19 join elements (beyond `maxInputs=16`), and counts of -3..5, 40 (beyond the 32-match limit), and overflow. The harness compares nil-ness, len, cap, content, and alias class plus the byte offset against every input's backing array for every returned slice, including each `Split*`/`Fields*` element and the outer slice's len/cap. It also compares panic type and message (negative/overflow `Repeat`, out-of-range slicing, panicking `Map` mapping) and predicate/mapping call counts.
- **Tainted paths actually ran**: 77,323 of 77,323 (tainted) and 77,443 of 77,443 (foreign) primary inputs of length ≥2 were tainted. Wrapper results were observed tainted for every op (for example `Split:22329 Clone:4390 SliceFull:2908`). Scopes are renewed per case so budgets never saturate. An earlier draft saturated budgets and exercised only 31 tainted inputs, so this guard matters.
- **Mutation through results**: on independent identical inputs, I XOR-wrote `r[0]` and appended into spare capacity of every result, then compared every input's full `[:cap]` backing and every result. They were identical for all ops and modes. Wrappers never mutate inputs (full-cap snapshot check).
- **Writer state**: I ran 3,000 iterations × 12-op random sequences per mode, 288,000 comparisons per toolchain with 0 failures. Sequences mix wrapped `Write`/`WriteString`/`WriteByte`/`WriteRune`/`Grow`/`Reset`/`Truncate`/`String` with native `Next`/`ReadByte`/`ReadRune`/`UnreadRune`, self-aliasing `buf.Write(buf.Bytes()[i:])`, `AvailableBuffer` append-then-write, repeated 200× payloads, invalid runes (`-1`, `0x110000`, surrogate), and `NewBuffer`/`NewBufferString` seeds. After each op the harness compares return values and errors, `Len`, `Cap`, `Available`, `cap(Bytes())` (encodes the read offset), `cap(AvailableBuffer())`, content, and `UnreadByte`/`UnreadRune` results on value copies (encodes `lastRead`). `bufferView`'s calls to `Bytes`/`Len`/`Cap` do not disturb `lastRead`.
- **Edge cases** (`TestFidelityWriterEdgeCases`, inactive and tainted): nil `*Buffer` and nil `*Builder` for every wrapper give an identical nil-deref panic, and `BufferString(nil)` returns `"<nil>"`. A copied non-zero Builder gives an identical `"strings: illegal use of non-zero Builder copied by value"` panic for Write/WriteString/Grow. `Grow(-1)` and `Truncate(-1|>len)` give identical panic messages, and `lastRead` is identical after ReadRune/ReadByte followed by wrapped String/Write/Truncate/Grow.
- **Woven call-site forms** (`iast/internal/zzfid/forms`): value and pointer receivers, `(*p).M`, `(&b).M`, struct value/pointer fields, promoted methods through embedded `bytes.Buffer`/`*strings.Builder` (not matched, so no compile break), type aliases (not matched), array element with side-effecting index/argument (evaluation order logged), map-of-pointer receiver, function-call receiver, nested `b.WriteString(b.String())`, `if n, err := ...` init, method values (unhooked), `defer`/`go` of hooked calls, nil-buffer `String`, a named `[]byte` argument, a multi-value argument `bytes.Cut(two(v))`, and a hooked call in `defer`. The transcript is byte-identical between unwoven and woven Go 1.26.6 runs, both inactive and with tainted inputs (`woven-forms-go1.26.6.txt`, `plain-forms-go1.26.6.txt`).
- **Race**: the differential harness under `-race` (150 iterations, Go 1.26.6) passed (`race-go1.26.6.txt`).
- Go 1.26.6 and Go 1.27.0 `bytes.Buffer`/`strings.Builder` differ only in comments. `bytes.go` differences (asciiSet table, `min`) do not alter results, as confirmed by the Go 1.27 run.

## Not covered / open questions
- Native `bytes.Buffer` invalidation hooks (`orchestrion.yml:1553-1680`) were exercised only indirectly, through woven forms and native ops in the sequences, under the woven run. I did not run a full woven randomized sequence differential. The plain harness calls wrappers directly with unwoven stdlib.
- `strings.Replacer.Replace` method-expression breakage (same root cause as F1) was not compiled here. It is left to the strings node or the fix.
- Taint provenance *correctness* (ranges) was out of scope. Only fidelity and "active path executed" were asserted. A woven buffer read after `ReadRune` is untainted, which is the documented exposure invalidation.
- No SQL/exec sink was invoked. I did not test concurrency of wrapped writers on a shared receiver beyond `-race` on the harness.
