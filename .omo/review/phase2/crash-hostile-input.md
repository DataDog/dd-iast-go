# crash-hostile-input: Woven HTTP app under hostile inputs (panics, memory, leaked secrets)
Verdict: Hostile inputs caused no panics, no data races, no status or behavior changes, and no heap growth. Every size limit dropped provenance instead of retaining memory. One redaction gap leaks secrets from SQL comments in the canonical exploit shape (Critical). Sink analysis also still runs after the reporting quota is full, which makes each tainted query cost several times more than necessary (High).

Scope covered: I built a woven executable app at `iast/integration/testapp/cmd/hostile` (private copy, `GOTOOLCHAIN=go1.26.6 go tool orchestrion go build`), a `-race` woven build, and a plain (unwoven) control build. The app uses mocktracer spans, a fake `database/sql` driver, and `os/exec` sinks. It exercises headers, `URL.Query`/`FormValue`, `ParseForm`, `ParseMultipartForm` (values and file names), `io.ReadAll`, `json.Decoder`/`json.Unmarshal`, `Cookies`/`Cookie`/`CookiesNamed`, and string/bytes/fmt/strconv/url/Builder/Buffer/concatenation propagation. A raw-socket driver (`driver.py`) sends 58 hostile cases (the last two are the added SQLi-exploit requests). It makes one serial pass with heap, RSS, and goroutine readings after each case, then runs 3 concurrent rounds (8 workers), plus a 40-round soak on the woven and plain builds. Code read: `internal/taint/request/{http,lazy,reader,owner,table}.go`, `internal/taint/jsonbridge/bridge.go`, `internal/taint/propagation/json.go`, `iast/encoding/json/*`, `iast/net/http/orchestrion.yml`, `internal/taint/redaction/{source,sql,command,analyzer}.go`, `internal/spans/{orchestrion,payload,tainted}.go`, `internal/vulnerability/tainted.go`, `iast/database/sql/sql.go`, `internal/taint/sqlbridge/bridge.go`, and `internal/taint/store/{limits,root}.go`. I read `phase1/research/shadow.md`. `phase1/research/00-digest.md` does not exist.

Config for the runs: `DD_IAST_ENABLED=true DD_IAST_REQUEST_SAMPLING=100 DD_IAST_MAX_CONCURRENT_REQUESTS=64 DD_IAST_VULNERABILITIES_PER_REQUEST=64 DD_IAST_DEDUPLICATION_ENABLED=false`, with default redaction patterns. The quota timing run used the default quota (2) and default dedup.

## Findings

### crash-hostile-input-F1: SQL comment bodies are never redacted, so literals after an injected `--` or inside `/* */` leave the process in clear
- Severity: Critical
- Category: redaction
- Location: internal/taint/redaction/sql.go:83-100 (`sqlSensitiveToken` has no case for comment tokens). The existing test pins the behavior at internal/taint/redaction/analyzer_test.go:30 (`SELECT column -- secret` is expected unredacted).
- Claim: `AnalyzeSQL` marks only STRING, INCOMPLETE_STRING, DOLLAR_QUOTED, NUMBER, BOOLEAN, and NULL tokens as sensitive. The `go-sqllexer` COMMENT and MULTILINE_COMMENT tokens fall to `default: return Interval{}, false`. In the classic exploit `' OR TRUE --`, everything after `--` becomes a comment, including application-owned literals such as a password hash. That tail is emitted verbatim as evidence. The same holds for tainted data or secrets inside `/* ... */`. The shared cross-tracer corpus (dd-trace-js `evidence-redaction-suite.json`: "SQLi exploited", "Query with line comment", "Query with block comment") and the dd-trace-java `SqlRegexpTokenizer` (LINE_COMMENT and BLOCK_COMMENT patterns) redact comment bodies. Go leaks exactly what those tracers hide, which breaks the "sensitive data leaving the process unredacted" rule.
- Evidence (unit): `.omo/review/evidence/crash-hostile-input/hostile_comment_repro_test.go`. Command: `go test -count=1 -run TestHostileSQLCommentBodiesAreRedacted -v ./internal/taint/redaction/`. Output (`redaction-comment-test.log`): `status=0 intervals=[{40 4}]`, followed by `visible evidence: "... OR **** --' AND password = '81dc9bdb52d04dc20036dbd8313ed055' AND deletedAt IS NULL"` and `--- FAIL`. Both comment cases fail with `intervals=[]`.
- Evidence (end-to-end, woven app): `hostile-main.go` handler `/exploit` with request `GET /exploit?param=%27%20OR%20TRUE%20--`. The span `_dd.iast.json` in `spans-woven.json` (excerpted in `leak-excerpts.txt`) contains `{"value": "' AND password = '81dc9bdb52d04dc20036dbd8313ed055' AND deletedAt IS NULL"}` and `{"value": " /* token='tok_live_SECRETBLOCK' */"}`. A tainted `RequestURI` placed after `--` also emits source `{"origin":"http.request.uri","value":"/h?password=hunter2SECRETPW&x=1"}`, even though the same secret was redacted in the `http.request.query` source of the same event.
- Fix: in `sqlSensitiveToken`, treat `sqllexer.COMMENT` and `sqllexer.MULTILINE_COMMENT` as sensitive, redacting the body after `--`/`#` and between `/*` and `*/`. Replace the `analyzer_test.go:30` expectation with the shared-corpus expectations.

### crash-hostile-input-F2: Sink analysis, evidence building, and stack capture run for every tainted query after the request's vulnerability quota is full
- Severity: High
- Category: perf
- Location: iast/database/sql/sql.go:34-49; internal/vulnerability/tainted.go:57,76,83; internal/spans/tainted.go:69 (`CanAddVulnerability` is checked only inside `TryCommitTainted`)
- Claim: `sql.Report` always runs `evidence.CollectString`, then `redaction.AnalyzeSQL` (6 dialect lexings of up to 32 KiB), then `ReportTainted`. `ReportTainted` does `BuildWithSensitive`, then `CaptureLocationSkipWhile` (a stack walk), then dedup, and only then checks the per-request quota at `spans/tainted.go:69`. The default quota is 2 vulnerabilities per request. After 2 reports, every further tainted sink call in the request pays the full pipeline for a result that is always discarded. With deduplication enabled, repeated reports from the same location are also discarded, but only after the stack capture. Java's overhead controller checks quota before sink analysis. Any sampled request that builds many tainted queries (for example, a loop over form values) pays this cost per call.
- Evidence: `quota-timing.log`, from the woven versus plain binaries at the default quota and dedup (7 requests each, median). `mp_40_parts` (40 multipart values of 30 KB, each reaching an SQL sink) took woven=142.3 ms versus plain=5.9 ms (about 24x), with `max_vulns_per_event=1`, so almost all of the work was discarded. `readall_64k` took 26.3 ms versus 2.0 ms. `analyzesql-bench.log` shows `BenchmarkHostileAnalyzeSQL30KB` at about 0.8 ms/op for the analyzer alone. The machine is shared, so timings are noisy, but a 24x gap is far beyond that noise.
- Fix: add a cheap `annotation.CanAddVulnerability` / quota-full check (for example, an atomic "full" flag on the annotation, or the scope-level count) before `CollectString` and `AnalyzeSQL` in the SQL and command sinks. Consider computing the dedup hash from the location before running the analyzer.

### crash-hostile-input-F3: Retroactive source redaction builds patterns from byte length, so a pattern can exceed the 250-character truncation limit by up to 4x
- Severity: Low
- Category: memory-bound
- Location: internal/spans/tainted.go:264
- Claim: `redactSourceOccurrence` sets `Pattern = strings.Repeat("*", len(parts[index].Value))`. `Value` was truncated to 250 runes (`redaction/source.go:230`), not 250 bytes. After a transform that turns invalid UTF-8 into U+FFFD (for example, `strings.ToUpper`), the value is multibyte, so the pattern reaches 3-4x `DD_IAST_TRUNCATION_MAX_VALUE`. The payload stays under the 25,000-byte cap, so the only effects are a truncation inconsistency and a byte-length side channel.
- Evidence: `spans-woven.json` holds valueParts with `"pattern"` lengths of 640, 656, and 639 `*` characters, all marked `"truncated":"right"`, from cases `readall_64k`, `readall_invalid`, and `prop_hdr_invalid`. Invariant scan: `max_part_len=656` while `max_src_len=250`.
- Fix: use `utf8.RuneCountInString(parts[index].Value)` (or clamp to `config.TruncationMaxValue`) when building the pattern.

## Checked and found correct
- **No panics or races.** All 58 cases × (serial + 3 concurrent rounds), plus 40 soak rounds, produced no `panic` in any app log. The `-race` woven build reported `WARNING: DATA RACE` count 0 (`app-race.log`). The app stayed alive in every run.
- **Behavior parity.** HTTP status codes are identical between the woven and plain builds for every case (`status diffs: {}`). These outcomes all come from Go itself and match the plain build: the 400s (invalid header name bytes, cookie header with control chars), the connection resets on `mp_5k_parts` (Go's 1000-part multipart limit, "message too large") and `json_deep12000` (Go's JSON max depth), and the handler errors.
- **Heap bounded.** Woven heap_inuse went from 17.5 MB at baseline to 19.8 MB at peak during the serial pass, and was about 18.0 MB after the concurrent rounds. That held through 1 MB headers, 10k/20k query params, a 9 MB form, 50 MB `io.ReadAll`, a 5 MB JSON string, 10k-element JSON arrays/maps, and 5k cookies. Over the 40-round soak, drift was +458 KB and +759 objects woven versus +450 KB and +725 objects plain, so the drift is identical and not IAST-owned. RSS growth (to about 350 MB) tracks the host's own 50 MB body buffers, and the plain build reaches about 285 MB.
- **Limits drop provenance instead of growing memory.** A header value or query value of exactly 65,536 bytes is tainted, and anything larger is not (`MaxRootBytes`). `q_huge_value` (1 MB) and `readall_50mb` produced untainted sinks. `hdr_32x30k` tainted 9 of 86 sinks once the 2 MiB request root budget was exhausted. More than 32 header names or more than 64 values skips eager rebuild (`hdr_2000_names`, `cookie_multi_header`). More than 48 query/form names skips map management (`q_10k_params`, `form_10k`). JSON documents over 64 KiB are not cloned (`json_huge_str`, `json_escapes`). The 10k-deep JSON and deep objects decode with the stdlib result unchanged.
- **Redaction of normal cases.** The `Authorization` bearer header (name pattern) was redacted, and `SECRETBEARER` never appears. Command arguments after argv[0] are redacted (`SECRETCMD` absent). SQL string literals are redacted (`SECRETLITERAL` absent). Retroactive per-event source redaction works: `http.request.query` was redacted in every vulnerability once one vulnerability found it sensitive.
- **Event invariants.** Across 60 events and 846 vulnerabilities: every `source` index is in range, source values and patterns are at most 250 characters, and the maximum JSON payload is 19,541 bytes (≤ 25,000). Events that overflow correctly degrade to `MAX_SIZE_EXCEEDED`, with sources dropped.
- **Invalid UTF-8.** Invalid UTF-8 in headers, query, form, multipart, JSON, cookies, and propagation transforms (ToUpper, ToValidUTF8, Map, Quote, Unquote, QueryUnescape, Builder, Buffer, 16-operand concatenation) produced no crash and no out-of-range parts. The JSON fallback encoder replaces invalid bytes with U+FFFD.

## Not covered / open questions
- The msgpack `meta_struct` path (real tracer) was not exercised because mocktracer rejects `SetMetaStruct`, so the JSON fallback was used. Invalid UTF-8 would be sent raw in msgpack strings. Backend acceptance is unverified.
- Woven baseline heap before any request is about 15.8 MB versus 1.3 MB plain. I did not attribute this between IAST fixed arrays and the woven dd-trace-go/appsec initialization. The design claims a 22.6 MB IAST envelope, and another node should verify it with a heap profile.
- Full-string `http.request.uri` and `http.request.query` sources carry every parameter, including `password=` values, in clear whenever the source is not otherwise sensitive. The other tracers behave the same way, so this is not filed. It does compound F1.
- HTTP/2, h2c, and slow-body (permit exhaustion) attacks were not run. Permit exhaustion only reduces coverage by design.
- Timing numbers come from a shared machine and are indicative only.
