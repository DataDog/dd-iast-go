# prop-semantics-parity: propagation semantics against Java, JavaScript, Python and Orchestrion research
Verdict: Three reproducible High provenance defects on supported direct calls; exact Go windows and bounded replacement are otherwise sound in the inspected paths, while several common Go composition APIs remain intentionally uncovered.
Scope covered: README.md:26-75; iast/propagation/{strings,bytes,coarse,operators,writer}.go and orchestrion.yml; internal/taint/propagation/{propagation,string_exact,string_coarse,bytes_exact,conversion}.go; internal/taint/ranges/operations.go; iast/database/sql/sql.go; relevant propagation tests and fixtures; phase1 architecture, design-intent, research digest and shadow checks; sibling dd-trace-java StringModuleImpl/CodecModuleImpl, dd-trace-py aspects and split/helpers, and dd-trace-js taint-tracking methods/tests. Reproducers ran with the pinned Go 1.26.6 toolchain and Orchestrion in the private copy.

## Findings

### prop-semantics-parity-F1: fmt.Sprintf misses tainted Stringer struct fields
- Severity: High
- Category: false-negative
- Location: internal/taint/propagation/string_coarse.go:115-145,203-219
- Claim: The supported root-application `fmt.Sprintf` hook examines only the format and top-level string/`[]byte` arguments; `formatArgumentKey` discards a struct implementing `fmt.Stringer`. `fmt.Sprintf("SELECT * FROM %v", parityTable{Name: tainted})` calls its `String()` and produces the SQL query `SELECT * FROM users WHERE 1=1 --`, yet the result has no provenance and SQL collection returns `StatusNone` (0). Ordinary struct/map `%v` formatting has the same argument-inspection gap. Unlike Go, Java's `String.format` mapper attempts placeholder attribution (`dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/StringModuleImpl.java:489-556`) and Python's format mapper reconstructs substituted spans (`dd-trace-py/ddtrace/appsec/_iast/_taint_tracking/aspects.py:443-524`).
- Evidence: `.omo/review/evidence/prop-semantics-parity/parity_repro_test.go` (`TestParitySprintfStructFieldKeepsTaint`) and `.omo/review/evidence/prop-semantics-parity/parity_repro.out.txt`; from the private copy run `GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -timeout 8m -count=1 -run '^TestParity' -v ./iast/propagation`. Output: `query="SELECT * FROM users WHERE 1=1 --" tainted=false sql_collection=0`, then `Should be true`. `iast/database/sql/sql.go:34-48` uses precisely this SQL collection result to decide whether to report.
- Fix: Attribute the output fragments emitted by formatting string/byte arguments and `Stringer` results in the single formatting pass, without calling user `String`/`Format` methods a second time; document any intentionally unsupported aggregate types explicitly.

### prop-semantics-parity-F2: fmt.Sprintf taints an argument that emitted no bytes
- Severity: High
- Category: false-positive
- Location: internal/taint/propagation/string_coarse.go:115-130,175-197
- Claim: Formatting taint comes from *all* inspected input arguments, regardless of whether their output appears. `fmt.Sprintf("SELECT 1%.0s", tainted("ATTACK"))` produces byte-for-byte clean `SELECT 1` but marks the entire query tainted; SQL collection returns `StatusCollected` (1). A byte-identical literal remains clean. Java and Python format implementations track emitted placeholders rather than automatically marking the whole output (`dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/StringModuleImpl.java:489-556`; `dd-trace-py/ddtrace/appsec/_iast/_taint_tracking/aspects.py:443-524`).
- Evidence: `.omo/review/evidence/prop-semantics-parity/parity_repro_test.go` (`TestParitySprintfZeroPrecisionLeavesCleanSQL`) and `.omo/review/evidence/prop-semantics-parity/parity_repro.out.txt`; same bounded woven command as F1. Output: `query="SELECT 1" tainted=true clean_control_tainted=false sql_collection=1`, then `Should be false`.
- Fix: Associate provenance only with bytes actually emitted by an argument; omit zero-width/zero-precision arguments while preserving format-literal taint, the native result, and single evaluation of formatter methods.

### prop-semantics-parity-F3: strings.Map retains taint after deleting all tainted runes
- Severity: High
- Category: false-positive
- Location: iast/propagation/coarse.go:36-38; internal/taint/propagation/propagation.go:326-425
- Claim: `strings.Map` is advertised as supported but always gives a nonaliasing result the first contributing source across the *whole* output. A mapping that removes every `X` from `"SELECT 1 "+tainted("XXXX")` yields the clean constant `SELECT 1 `, yet the result is tainted and SQL collection returns `StatusCollected` (1). The byte-identical clean constant is untainted. This challenges the **documented coarse-transform trade-off** in `.omo/review/phase1/01-design-intent.md`: it creates false provenance, contrary to the product's accuracy invariant, when all tainted input is removed. By contrast, Go's `bytes.ToValidUTF8` already composes surviving and replacement ranges exactly (`internal/taint/propagation/bytes_exact.go:258-350`).
- Evidence: `.omo/review/evidence/prop-semantics-parity/parity_repro_test.go` (`TestParityMapDeletingTaintedSuffixLeavesCleanSQL`) and `.omo/review/evidence/prop-semantics-parity/parity_repro.out.txt`; same bounded woven command as F1. Output: `query="SELECT 1 " tainted=true clean_control_tainted=false sql_collection=1`, then `Should be false`.
- Fix: Capture the input-rune/output-byte correspondence during the *single* native `Map` callback invocation and compose only surviving contributions; never invoke an application callback twice merely to reconstruct ranges.

## Checked and found correct

- **Windows, trim and split:** Go `Cut*`, `Split*`, `Fields*`, `Lines`, `Trim*`, slice operations and byte equivalents derive aliases by position and intersect source ranges (`iast/propagation/strings.go:25-125,158-219`; `bytes.go:39-159`; `internal/taint/propagation/propagation.go:196-259,428-539`). Existing woven partial-range tests cover trim and the 32-result boundary (`iast/propagation/strings_provenance_test.go:18-135`). Python also clips/offsets split and strip ranges (`dd-trace-py/ddtrace/appsec/_iast/_taint_tracking/aspects/aspect_split.cpp:43-138`, `aspects.py:1495-1612`); Java substring/trim clip ranges but Java `split` coarsens each token (`dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/StringModuleImpl.java:227-249,429-462,634-692`). JS trim survival is tested, but its inspected tests do not establish partial-range positions (`dd-trace-js/packages/dd-trace/src/appsec/iast/taint-tracking/taint-tracking-impl.js:139-144`).
- **Copies and combination:** Go `Clone`, 2-16 operand `+`, `Join` (including separator), `Repeat`, and `Replace*` map exact byte positions; replacements use exact segments through 32 matches, then intentionally coarsen (`internal/taint/propagation/string_exact.go:21-241`; `bytes_exact.go:25-252`; `internal/taint/ranges/operations.go:25-172`). Existing provenance tests check separator and replacement source IDs (`iast/propagation/strings_allocating_test.go:18-110`). Java similarly shifts join/repeat ranges but its general replace call sites are experimental (`dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/StringModuleImpl.java:102-168,252-294,722-826`).
- **Case and encoding:** Go preserves exact positions on unchanged aliases and equal-length ASCII case changes, conservatively coarsening changed non-ASCII cases; Java and Python also propagate case, with different character/byte indexing and length-change handling (`internal/taint/propagation/string_coarse.go:20-85`; `bytes_exact.go:356-412`; `dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/StringModuleImpl.java:297-314`; `dd-trace-py/ddtrace/appsec/_iast/_taint_tracking/aspects.py:696-729`). Go URL escape/unescape and `strconv.Quote*`/`Unquote` coarsen and preserve native errors; Java URL codecs also coarsen, while Python `repr` can offset ranges into quotes (`iast/propagation/coarse.go:63-107`; `dd-trace-java/dd-java-agent/agent-iast/src/main/java/com/datadog/iast/propagation/CodecModuleImpl.java:29-39`; `dd-trace-py/ddtrace/appsec/_iast/_taint_tracking/aspects.py:527-550`). JS inspected tests show case/trim taint survival, not enough evidence to assert exact position parity.
- **Conversion and owners:** Supported `[]byte` to string conversion copies byte ranges when lengths match (`internal/taint/propagation/conversion.go:15-50`); owner-separated coarse publication keeps request-local source IDs distinct (`internal/taint/propagation/propagation_test.go:682-752`). The three failing cases above were reproduced under real woven advice, not a hand-called wrapper.

## Not covered / open questions

- Explicitly *unsupported*, not separate defects under this brief: `strings.NewReplacer` propagates input through `.Replace` but loses **tainted replacement terms** (`iast/propagation/strings.go:150-155`); `text/template.Execute` composing tainted data into a writer, `path.Join`/`filepath.Join` composing a tainted command path, `regexp.ReplaceAllString`, and indirect function/method calls have no matching supported root-call advice. `fmt.Sprintf("%v", struct/map)` is F1 because README advertises direct `fmt.Sprint*` without an aggregate qualifier. These are likely SQLi/CMDi detection gaps in real Go code; prioritize coverage expansion separately from the proven wrong-provenance fixes.
- The 32-window and 16-input caps, one-byte fresh-root restriction, mutable-alias writes (`append`/`copy`/index writes), dependency-created fresh allocations, and cross-request retention are documented safe misses; research checks S8-S11, S28-S32 identify useful future regression cases, not additional findings here. The S11 stale-byte-alias and S28 address-reuse scenarios were not run in this node.
- The reviewed JS rewrite-method table (`dd-trace-js/packages/dd-trace/src/appsec/iast/taint-tracking/csi-methods.js:3-21`) does not establish complete split, format, URL or quote behavior. No claim of global JS absence or exact-range equivalence follows from that table.
