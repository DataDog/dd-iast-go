# life-cross-request: taint bleeding between requests through memory reuse
Verdict: Once a request has finished, its taint is isolated correctly. But while request A is still in flight, memory it recycles (through a `sync.Pool` or any free list) can hand A's provenance to a concurrent request B. I reproduced this end to end on three paths. Each time, B's span reported an SQL injection for a constant, clean query and listed A's raw attacker input as the source. The result is 3 High, 1 Medium and 1 Info.

Scope covered: I read `internal/taint/store/{store,owner,lookup,value,root,writer}.go`, `internal/taint/request/{owner,lookup,scope,reader}.go`, `internal/taint/propagation/{writer,conversion}.go`, `iast/propagation/writer.go`, `internal/taint/writerbridge/bridge.go`, the `bytes.Buffer` native-hook aspects in `iast/propagation/orchestrion.yml:1545-1684`, `internal/vulnerability/tainted.go` (span selection) and `iast/database/sql/sql.go`. I also ran a woven two-request harness in `iast/integration/testapp`: real `net/http` server, mocktracer spans, fake-driver SQL sink, Go 1.26.6, pinned Orchestrion. It has 5 tests and 11 subtests, run `-count=3`. Related prior reports (hooks-io-bufio, life-weak-gc F3, crash-stress-app) and the store-identity-gc evidence were cross-checked so that they are not re-reported.

## Findings

### life-cross-request-F1: A pooled `io.ReadAll` body slice gives A's body to a concurrent request that refills it
- Severity: High
- Category: cross-request
- Location: internal/taint/request/reader.go:67-88,119; internal/taint/store/root.go:190-226; internal/taint/store/lookup.go:120-139,142-196; internal/taint/propagation/conversion.go:23-45; internal/vulnerability/tainted.go:110-115
- Claim: `ReadAllBytes` adopts the application's own `io.ReadAll` result without copying it. `AdoptSourceBytes` anchors the backing, sets span `cap`, and publishes the key `(ptr,len)`. The application owns this slice and may recycle it (for example `pool.Put(body[:0])`) while A is still running. Request B then gets the slice, refills it with clean bytes using `append` or `copy` (not hooked, so nothing is invalidated), and converts it with `q := string(buf)`. `BytesToString` looks up the exact key `(ptr,len)`. The key matches whenever B's content length equals the length of any window A registered at that base address. `Lookup` accepts entries from any *active* foreign owner and never checks content. The result string is therefore adopted into A's owner with A's ranges. At the sink, `selectTaintedAnnotation` picks B's span from the context, and `copySources` resolves A's source table, so B's trace receives an SQL_INJECTION whose source is A's full request body. Under the default redaction patterns a non-secret-looking body is emitted verbatim, which puts one user's payload into another user's trace. The documented "`append`/`copy` do not create tracked roots" limitation covers stale ranges *within* one owner. Foreign-owner lookup turns it into a rule-4 cross-request bleed, which the docs do not state.
- Evidence: .omo/review/evidence/life-cross-request/zz_review_crossreq_test.go (`TestReviewPooledReadAllSliceAcrossRequests`), with helpers in zz_review_crossreq.go. Command: `cd iast/integration/testapp && GOFLAGS=-p=4 GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -count=3 -run TestReview -v .`. Output in run1-go1.26.6.log and run2-count3-go1.26.6.log (fails 3 out of 3):
  `B: query="SELECT id FROM customers" tainted=true ranges=[[0,+24) origin=http.request.body name="" value="x' OR '1'='1' --comment!"]`
  `span review.b: ... {"sources":[{"origin":"http.request.body","value":"x' OR '1'='1' --comment!"}],"vulnerabilities":[{"type":"SQL_INJECTION",...` and `CROSS-REQUEST BLEED (concurrent-same-length)`. Controls pass: a different-length refill is clean, and so is a sequential run where A finished first.
- Fix: When a `KindBytes` root or window is published, record a 64-bit fingerprint of its visible bytes. The bytes are at most 64 KiB and already anchored. After a `MayContain` hit on a `KindBytes` key, recompute and compare the fingerprint in `Lookup`. On a mismatch, drop the entry and claim a new root generation. Strings are immutable and need no check. At a minimum, sinks should refuse foreign-owner contributions that descend from mutable byte roots, and the README should state that stale byte provenance can cross requests.

### life-cross-request-F2: A pooled `strings.Builder` with an un-woven reset inherits A's source after GC address reuse
- Severity: High
- Category: cross-request
- Location: iast/propagation/writer.go:202-205; internal/taint/store/writer.go:23-34,448-462; internal/taint/propagation/writer.go:190-237
- Claim: `builderView` records `(data pointer, len, cap)` with no `Anchor`. The comment "builders do not" (`store/writer.go:25`) confirms this. `strings.Builder` has no native invalidation hook, unlike `bytes.Buffer`. Suppose A writes tainted input through woven calls and then a pool helper outside the root module resets the builder (or it is reset with `*b = strings.Builder{}` or a method value). A's writer record survives, and the old backing becomes unreachable and collectable. B gets the builder and formats a clean query with `fmt.Fprintf` (an un-woven `io.Writer` call). The allocator reuses the freed address, and the content length matches. B's direct `b.String()` then matches A's stale view, `SnapshotWriter` returns A's ranges, and the result is adopted into A's owner. B's SQL finding lists A's query parameter. This has the same root cause as the store-identity-gc Builder reproducer, which was single-request plus a unit-level cross-request variant. This run proves the cross-request, cross-trace consequence end to end.
- Evidence: zz_review_crossreq_test.go (`TestReviewPooledBuilderAcrossRequestsAfterGC`), same command, fails 3 out of 3:
  `B: backing 0x17d9b7958918 (len 24 cap 24) reused after 29 clean writes; query="SELECT id FROM customers" tainted=true ranges=[[0,+24) origin=http.request.parameter name="q" value="x' OR '1'='1' --comment!"]` and `span review.b: ..."sources":[{"origin":"http.request.parameter","name":"q","value":"x' OR '1'='1' --comment!"}],"vulnerabilities":[{"type":"SQL_INJECTION"`. The sequential control, where A finished before B, is clean.
- Fix: Anchor the builder backing in `builderView` (`Anchor = unsafe.StringData(builder.String())`, and set `Backing`), the same way `bufferView` does, so a tracked address cannot be reused while the record exists. Records are already bounded at 8 per owner. Alternatively, add the F1 content fingerprint to writer views.

### life-cross-request-F3: `bytes.Buffer` view matching across receivers gives A's writer ranges to B's new Buffer over a recycled slice
- Severity: High
- Category: cross-request
- Location: internal/taint/store/writer.go:448-462,233-263,76-113; internal/taint/propagation/writer.go:202-237; iast/propagation/writer.go:190-217
- Claim: To support Buffer value copies, `writerViewIndexLocked` matches *any* receiver whose `(pointer, len, cap, backing, anchor)` equals a tracked view (lines 453-459). In the common pattern, A does `bytes.NewBuffer(pooled[:0])`, writes tainted input through woven `WriteString`, and returns `pooled[:0]` to the pool. B refills the slice with `append` and reads it through `bytes.NewBuffer(b).String()`. Neither step triggers a native hook: `NewBuffer` and `append` are un-hooked, and the `Bytes()` exposure inside `bufferView` is suppressed as expected. B's view therefore equals A's recorded view. `publishWriterString` adopts B's clean string into A's owner with A's ranges. This path is deterministic and needs no GC and no timing luck, only equal length.
- Evidence: zz_review_crossreq_test.go (`TestReviewPooledSliceNewBufferViewAcrossRequests`), same command, fails 3 out of 3:
  `B: query="SELECT id FROM customers" tainted=true ranges=[[0,+24) origin=http.request.parameter name="q" value="x' OR '1'='1' --comment!"]` and B's span has an SQL_INJECTION finding with that source. The sequential control is clean.
- Fix: Store a fingerprint of the visible bytes in the writer record. The backing is anchored and at most 64 KiB. Verify the fingerprint in `SnapshotWriter`/`AdoptBufferWriter` before a cross-receiver view match, and drop the record on a mismatch. Alternatively, limit view-only matching to receivers first seen by the same owner through a hooked copy.

### life-cross-request-F4: No test covers cross-request memory reuse while the originating request is still active
- Severity: Medium
- Category: test-gap
- Location: internal/taint/store/lifecycle_test.go; internal/taint/request/owner_test.go; iast/integration/testapp/*_test.go
- Claim: The lifecycle and isolation tests cover only reuse *after* Finish (slot reuse, generation checks). No test has two concurrently active requests that share recycled memory, which is exactly the case where foreign-owner lookup meets stale identity. The pooled `bytes.Buffer` scenarios in crash-stress-app passed only because that path has native hooks. The byte, Builder and view paths above were never exercised.
- Evidence: static reasoning. The controls and bleeds are in the R1-R5 harness above.
- Fix: Adopt the two-request harness (`runReviewPair`) as a woven regression suite, with a clean-control and a sequential-control variant for each path.

### life-cross-request-F5: The documented foreign-owner reporting widens every stale-identity limitation into cross-user attribution
- Severity: Info
- Category: doc
- Location: internal/taint/store/lookup.go:142-196; internal/vulnerability/tainted.go:110-127
- Claim: By design, a sink reports taint from any active owner on the sink's own span (01-design-intent). This is correct for values that are genuinely shared. It also means that any documented stale-provenance miss (unhooked byte writes, `bytes.Buffer` historical views, unanchored builders) is attributed to a different user's request and source while the originating request is in flight. The README limitations describe these misses as single-request effects.
- Evidence: static reasoning, together with F1-F3.
- Fix: Document the interaction. Consider tagging foreign-owner findings so they can be triaged, and consider stricter validation (content fingerprints) on the foreign-owner path.

## Checked and found correct
- Reuse after Finish is isolated. Lookup requires `stateActive` and the matching `ownerGen` (`store/lookup.go:148-155`). `stale`/`reclaim` reject old generations (`value.go:231-271`). `copySources` revalidates the directory slot, ownerID and generation (`request/lookup.go:135-162`). End to end, R5 had GC reuse A's `io.ReadAll` body address after 1 allocation, and B's same-length clean query stayed clean. The sequential controls for R1, R2 and R4 are clean.
- While the owner is live, strong anchors prevent GC address reuse for store roots and Buffer views (`root.go:190-226`; `bufferView` Anchor). This is consistent with the store-identity-gc evidence (`TestReviewBufferAnchorPreventsReuse`).
- A pooled `bytes.Buffer` is invalidated correctly across requests in every reset style tested: woven `Reset`, un-woven `Reset` plus un-woven `WriteString` (the native `invalidate-header`/`invalidate-backing` hooks fire), and `Truncate(0)` plus `fmt.Fprintf`. All passed 3 out of 3 (R3).
- The exact-key identity means a refill with a different length is clean (R1 `concurrent-different-length`).
- `Analysis.Finish` clears the directory entry and the source table before the store owner is finished, and releases the permit last (`request/owner.go:259-273`). No window was found in which a reused analysis slot resolves the previous request's sources.

## Not covered / open questions
- Pooled `bufio.Reader` owner leakage is already High in hooks-io-bufio, and the dd-trace-go span-pool bleed is life-weak-gc F3. Neither is re-reported here. I did not exercise `json.Decoder` slot reuse across requests (see life-json-decoder).
- Suppose B's sink runs with a context that carries no span or scope (for example a background goroutine). `selectTaintedAnnotation` then falls back to `ExistingForOwner`, so B's query evidence lands in *A's* trace, which is the reverse direction. I did not reproduce this.
- I did not run the reproducers under `-race` or on Go 1.27.0 (the woven JSON build is broken there per base-test-127). I did not measure field frequency of the equal-length precondition, although fixed-width payloads such as IDs, tokens and records make it common.
