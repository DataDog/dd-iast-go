# crash-stress-app: concurrent tainted HTTP stress of a woven application
Verdict: No panic, deadlock, data race, cross-request taint bleed, store leak or permit leak appeared in 5-minute 256-client runs with and without `-race` (about 127k requests in total). The stress surfaced two High issues outside the crash scope. First, non-analyzed requests' root spans fill the span-annotation map, so an analyzed request loses its SQL injection report. Second, the woven `bytes.Buffer` invalidation hook slows unrelated process code by roughly 9x to 78x while any writer state exists.
Scope covered: A woven stress executable, `iast/integration/testapp/cmd/stress` (private copy, Go 1.26.6, pinned Orchestrion). It serves httptest traffic that flows from sources (query, header, form, cookie, path value, JSON decoder, `io.ReadAll` body) through propagation (slicing, concatenation, `strings`/`bytes`/`fmt`/`strconv`/`url`, `strings.Builder`, pooled `bytes.Buffer`, JSON) to a fake-driver `database/sql` (Query/Exec/Prepare/argument forms) and to `exec` `/bin/true`. Flows also include in-request goroutine fan-out, sinks run after the handler returns, `http.ErrAbortHandler` and plain panics, client cancellations, 70 KB values, more than 300 parameters, 100 headers, and 3,000-derivation loops. Run with `DD_IAST_REQUEST_SAMPLING=100 DD_IAST_MAX_CONCURRENT_REQUESTS=64 DD_IAST_DEDUPLICATION_ENABLED=false DD_IAST_VULNERABILITIES_PER_REQUEST=8`, with an in-process fake agent counting `SQL_INJECTION`/`COMMAND_INJECTION` bytes and a watchdog that writes a pprof goroutine dump whenever an in-flight request exceeds 10 s. Code read: `internal/spans/{annotation,vulnerability,owner,orchestrion}.go`, `internal/vulnerability/tainted.go`, `internal/taint/writerbridge/bridge.go`, `internal/taint/store/writer.go:355-432`, `internal/taint/propagation/writer.go:17-45`, `iast/propagation/orchestrion.yml:1553-1595`, `internal/taint/request/scope.go:1-110`, `iast/net/http/orchestrion.yml`.

## Findings
### crash-stress-app-F1: Non-analyzed requests' spans exhaust the annotation map, so analyzed requests lose their reports
- Severity: High
- Category: false-negative
- Location: internal/spans/annotation.go:182-214,227-236; internal/spans/vulnerability.go:23-35; internal/vulnerability/tainted.go:62-68,110-126
- Claim: `begin` creates a `Scope` for every request, including sampled-out and capacity-dropped ones (`request/scope.go:86-105`). `BindScope` stores an `Annotation{Sampled: active}` for any scope whose span starts (`annotation.go:199-206`). `trimStore` then caps the map at `config.MaxConcurrentRequests`, which is the same number as the analysis permits (`annotation.go:235`), and entries leave the map only when a root span finishes. Live non-analyzed root spans can therefore occupy every slot. An analyzed request that starts its span afterwards gets no annotation (`_dd.iast.enabled=0`), and its reports fall through to `NewOrphanTaintedSpan`. That function starts a `vulnerability` span before checking `trimStore()`, finds no space, and returns a nil annotation. The report is dropped, and an empty `vulnerability` span tagged `_dd.iast.enabled=1` is still emitted. With the defaults (2 permits, 30% sampling), two concurrent unsampled requests with spans are enough to silence the next sampled request.
- Evidence: `.omo/review/evidence/crash-stress-app/annslot_main.go`. Command: `GOTOOLCHAIN=go1.26.6 go tool orchestrion go build -o annslot ./cmd/annslot && DD_IAST_REQUEST_SAMPLING=100 ./annslot`, with the default `MAX_CONCURRENT_REQUESTS=2`. Output is in `annslot.out`. The CONTROL case gives `victim: active=true queryTainted=true`, `span "req" role=victim _dd.iast.enabled=1 iastJSONBytes=535`, `reported: true`. The BUG case adds one capacity-dropped request (`hold3 active=false`) that holds a root span. It gives `victim: active=true queryTainted=true`, `span "vulnerability" _dd.iast.enabled=1 iastJSONBytes=0`, `span "req" role=victim _dd.iast.enabled=0 iastJSONBytes=0`, `=> victim SQL injection reported: false`.
- Fix: Do not consume annotation capacity for non-active scopes. Tag the root with `_dd.iast.enabled=0` without storing the entry, or store it outside the capped set. Alternatively, size the map by `store.MaxOwners` plus a separate orphan budget. In `NewOrphanTaintedSpan`, check capacity before starting the span.

### crash-stress-app-F2: The stdlib bytes.Buffer invalidation hook imposes an owner-table scan on every Buffer mutation in the process
- Severity: High
- Category: perf
- Location: iast/propagation/orchestrion.yml:1553-1595; internal/taint/writerbridge/bridge.go:75-96; internal/taint/store/writer.go:366-432
- Claim: The `bytes.Buffer.invalidate-backing` advice runs in the woven standard library, so it applies to every `Write`/`WriteString`/`WriteByte`/`WriteRune`/`Grow`/`ReadFrom` call by every caller: dependencies, the tracer's own encoders, and goroutines that have no request. Its only gate is the process-wide `activeStates > 0`. Once any request holds any writer state, each call does up to 4 CAS probes (`consume`), then `InvalidateBuffer` loops over all 64 owner records. For each active owner, `writerPresent` performs up to 3 x (2 + 8 x 3) atomic loads, even when the buffer is not tracked. That is about 1,700 atomic operations per `WriteByte` at 64 active owners. No cheap membership filter exists, such as an owners-with-writers bitmask or a tracked-pointer hash.
- Evidence: `.omo/review/evidence/crash-stress-app/wbench_main.go`, output in `wbench.out`. Command: `go tool orchestrion go build -o wbench ./cmd/wbench && DD_IAST_REQUEST_SAMPLING=100 DD_IAST_MAX_CONCURRENT_REQUESTS=64 ./wbench`. It runs `json.Marshal` in a goroutine with no request context, 5 interleaved rounds per configuration. Median ns/op: no request 72,722; 1 active request without writers 66,425; 1 active request with one tracked `bytes.Buffer` 651,813 (x8.96); 64 active requests with writers 5,688,782 (x78). The machine was shared and noisy, but the smallest with-writer sample (191,377) exceeds the largest baseline sample (107,941). The stress dumps also show 9-19 goroutines running `store.writerPresent` under `writerbridge.invalidateSlow` from `encoding/json` encoders (`dump-analysis.txt`). This is a different path from perf-hotpath-F2, which covers the root-application wrapper path.
- Fix: Keep a store-level atomic bitmask of owners with `writerCount > 0` and scan only those owners. Add a small fixed hash filter of tracked receiver pointers and backing ranges that is checked before any owner loop. Skip `consume` when no expectations are outstanding.

### crash-stress-app-F3: trimStore performs a blocking full-map sweep on every span bind once the map passes 3/4 of capacity
- Severity: Medium
- Category: perf
- Location: internal/spans/annotation.go:34,199,227-236; internal/spans/vulnerability.go:25
- Claim: When `store.Size() >= triggerTrimThreshold` (48 at 64 permits), every `BindScope`, `AnnotationFor` and orphan report calls `store.DeleteMatching`. That call takes each xsync bucket mutex in turn. Occupancy comes from live root spans whose weak keys are still reachable, so the sweep usually deletes nothing. Under concurrency above the cap, every span start therefore serializes on a full-map sweep and forms a lock convoy. This hot-path lock blocks.
- Evidence: Stall dumps from the stress runs (`goroutine-dumps.tgz`, summarized in `dump-analysis.txt`). The race run's `goroutines-3.txt` has 48 of 1,412 goroutines blocked in `sync.Mutex.Lock <- xsync.(*Map).DeleteMatching <- spans.trimStore <- spans.BindScope <- iast/net/http.BindStartSpan`. The non-race run's `goroutines-2.txt` has 63 of 1,304 in the same place, which makes it the largest IAST-attributable wait. Both runs logged in-flight requests over 10 s (the non-race maximum was 12.4 s). No request was stuck permanently.
- Fix: Make trimming best-effort and rate-limited: one trimmer through `TryLock`, at most once per interval or GC cycle, with the result cached in an atomic. Keep an atomic occupancy counter instead of calling `Size()`. With F1 fixed, occupancy stays bounded by the number of analyzed requests.

### crash-stress-app-F4: The woven stress app has about 4x lower throughput than the uninstrumented build at 100% sampling
- Severity: Info
- Category: perf
- Location: iast/integration/testapp/cmd/stress (harness); overall instrumentation
- Claim: The same harness served about 1,240-1,540 requests/s uninstrumented (average latency 160 ms, maximum 1.4 s). Woven without `-race`, it served about 290-425 requests/s (average 750 ms, maximum 12.4 s). GC assist (`MakeNoZero` semacquire), the F3 convoy and F2 scans dominate the IAST-attributable waits. The client side of the harness is also woven, and its builder and concatenation calls pay the root-application wrapper costs reported in perf-hotpath-F2. The ratio therefore overstates server-only overhead, and the numbers are noisy on the shared machine.
- Evidence: `run-uninstrumented-30s.log`; `run-norace-5m.log` (rps lines, per-flow averages); `dump-analysis.txt`.
- Fix: None beyond F2/F3. Track this in the overhead benchmarks.

## Checked and found correct
- No crash or deadlock under stress, verified by running it. The `-race` 5-minute run served 38,642 requests with 0 `WARNING: DATA RACE`, 0 panics and 0 fatal errors (`run-race-5m.log`). The non-race 5-minute run served 88,371 requests with 0 panics (`run-norace-5m.log`). The runs included 2,950 and 6,811 intentional handler panics (half `http.ErrAbortHandler`), about 4k client cancellations, and sinks executed after the handler returned (`lateDone` 2,908 and 6,614, all drained). The final "RESULT: FAIL" in both logs comes only from the >10 s in-flight watchdog. The dumps show slowness (CPU and race-detector saturation, GC assist, the F3 convoy) rather than a stuck goroutine. Progress never stopped, and every request and late goroutine completed.
- No cross-request bleed or false taint. Values retained in a global ring from requests whose response had been fully received, and whose `serverHandler` deferred `Finish` had therefore returned, were never reported tainted: 0 of 19,545 checks (race run) and 0 of 52,141 (non-race run). A pooled `bytes.Buffer` reused across requests never produced a tainted clean string, and fresh clean literals were never tainted.
- Store accounting and permits recover. After each run the store drained to `values=0 charged=0`. The 64 serial post-run requests were all `T` (analyzed and tainted), so no admission permit or owner slot leaked through panics, aborts, cancellations or late sinks.
- Reports reach the tracer under load. The fake agent received 7,898 (race) and 57,597 (non-race) `SQL_INJECTION` plus 217/1,653 `COMMAND_INJECTION` occurrences in msgpack payloads.
- Heap after GC returned to 23-24 MiB after both runs. Peak heap during load was 83-238 MiB with no upward trend across 5 minutes.

## Not covered / open questions
- Go 1.27 was not stressed, because the woven build fails to compile (base-test-127-F1).
- Per-flow sink taint rates (from the serial 1-client run, `run-serial-1client-30s.log`) match known or documented misses and were not re-reported. Fan-out goroutines in one request lose most taint even serially, which matches perf-contention-F2. The `body` flow uses `string(b)` inside `append(...)` plus `+=`, both documented conversion-context and `+=` limitations. The `big` flow joins more than 16 inputs (documented `maxInputs`). The pooled Buffer with `fmt.Fprintf` loses taint through documented conservative invalidation. The `derive` flow hits per-root and per-request value quotas.
- The analyzed fraction under 256 clients was 72% (non-race) and 28% (race) of requests with 64 permits. The permit bound explains most of this. The contribution of the ownerMu TryLock drop (perf-contention-F1) was not separated.
- The first race attempt (`run-race-5m-attempt1-interrupted.log`) was killed by a host disconnect after the load phase. It also showed 0 races. Its long tails came from a harness `database/sql` pool limit (64 connections), which was removed before the recorded runs.
