# prop-unicode: range offsets through length-changing transformations
Verdict: No range-offset or out-of-bounds bug was found. A per-byte differential oracle ran 13.2M cases across 3 seeds on both Go 1.26.6 and Go 1.27.0, plus directed boundary cases, with 0 mismatches, and it caught every injected mutation. Exact paths (Replace*, bytes.ToValidUTF8, ASCII case conversion, Repeat, Join, alias windows) map every byte correctly. Out-of-bounds ranges are prevented structurally. The only problems are in the coarse paths, which lose precision and sources: 1 Medium and 2 Low findings.
Scope covered: `internal/taint/propagation/{string_exact,string_coarse,bytes_exact,propagation}.go` (all functions); `iast/propagation/{strings,coarse,bytes}.go` and the `WriteRune` wrappers in `writer.go`; `internal/taint/ranges/{operations,ranges,canonical}.go`; `internal/taint/store/{root,lookup}.go` and `value.go:31-131`; `internal/taint/redaction/source.go`; `internal/model/truncation`; the case, Map, and ToValidUTF8 aspects of `iast/propagation/orchestrion.yml`; and the stdlib `bytes.{ToValidUTF8,Map,ToUpper}` source in the go1.26.6 and go1.27.0 GOROOTs.

## Findings
### prop-unicode-F1: Non-ASCII case conversion collapses the whole value to the first source, even though case mapping is rune-for-rune
- Severity: Medium
- Category: provenance
- Location: internal/taint/propagation/string_coarse.go:49-67; internal/taint/propagation/bytes_exact.go:382-399
- Claim: `exact := len(input) == len(result) && asciiString(input)`. If the input contains any byte >= 0x80, `CaseString`/`CaseBytes` publish one range `[0,len(result))` from `ranges.Coarse`. That range carries only the first contributing source ID and the intersection of the marks. This produces two provenance errors on a supported path (README row "case conversion"). First, the clean template bytes are attributed to user input. Second, every source after the first is dropped from the report. A single accented character anywhere in a query is enough, for example `strings.ToUpper("select ... name = '" + name + "' and org = '" + org + "'")` with `name="josé"`. This is a documented trade-off, according to the code comment and the design intent. I challenge it under rule 4 because an exact mapping is cheap. `unicode.ToUpper`, `ToLower`, and `ToTitle`, as applied through `strings.Map`/`bytes.Map`, are 1-rune to 1-rune maps (invalid bytes become 3-byte U+FFFD). So output offsets can be derived by walking input and output runes in lockstep, including for width-changing runes such as `ı`, `ſ`, K (U+212A), and `Ɐ`.
- Evidence: `.omo/review/evidence/prop-unicode/zz_review_unicode_test.go` (`TestReviewCaseCoarsensWholeQuery`); `GOTOOLCHAIN=go1.26.6 go test -count=1 -run 'TestReviewCase' -v ./internal/taint/propagation/`; output in `directed-go1.26.6.txt`:
  `name="bob"  input ranges=[{34 3 1 0} {50 4 2 0}] -> ToUpper ranges=[{34 3 1 0} {50 4 2 0}] (len=55)`
  `name="josé" input ranges=[{34 5 1 0} {52 4 2 0}] -> ToUpper ranges=[{0 57 1 0}] (len=57)`
  Source 2 disappears, and the 57-byte clean SQL template is attributed to source 1.
- Fix: When `!exact`, build a bounded boundary map by decoding input and result rune by rune (`utf8.DecodeRune` on both, advancing one rune each). Emit `ranges.Segment`s for at most 32 width-change points and publish through `ranges.Compose`, rounding mid-rune range edges outward. Keep `Coarse` only as the fallback when that bound is exceeded or the rune counts diverge.

### prop-unicode-F2: strings.ToValidUTF8 is coarse even though an exact mapper already exists for bytes
- Severity: Low
- Category: provenance
- Location: iast/propagation/coarse.go:38-46 (compared with internal/taint/propagation/bytes_exact.go:240-348)
- Claim: `StringsToValidUTF8` calls `CoarseString(result, value, replacement)`. Any repair therefore makes the whole string one range with the first source, and later sources are lost. `bytes.ToValidUTF8` already uses the exact `mapValidUTF8Segments`, which is proven correct here. The two APIs, both listed in the same README rows, give different provenance for identical data.
- Evidence: `TestReviewToValidUTF8StringVsBytes` in the same file; output in `directed-go1.26.6.txt`:
  `input ranges=[{34 4 1 0} {51 4 2 0}]`
  `strings.ToValidUTF8 ranges=[{0 56 1 0}]`
  `bytes.ToValidUTF8   ranges=[{34 3 1 0} {51 4 2 0}]`
- Fix: Add a `ValidUTF8String` twin of `ValidUTF8Bytes` that reuses the segment mapper (over `unsafe.Slice(unsafe.StringData(s), len(s))` or a string variant), publishes to one exact-length clone, and keeps the existing alias path when no repair was needed.

### prop-unicode-F3: The *Special and Title case-conversion variants are not woven, although the README says "case conversion"
- Severity: Low
- Category: false-negative
- Location: iast/propagation/orchestrion.yml:661-686,1012-1037; README.md:31,34
- Claim: Only `ToLower`, `ToUpper`, and `ToTitle` are woven for `strings` and `bytes`. `strings.ToUpperSpecial`, `ToLowerSpecial`, `ToTitleSpecial`, and `Title`, and the same functions in `bytes`, have no aspect (a grep for `Special|\.Title` under `iast/` finds no matches). The output of a locale-aware case conversion, such as `unicode.TurkishCase` or `AzeriCase`, is therefore silently untainted. This is a safe miss rather than a false positive. The README's unqualified "case conversion" reads as covering these variants.
- Evidence: static reasoning only (the grep result above). Low severity, so no reproducer is required.
- Fix: Weave the `*Special` variants through the same `CaseString`/`CaseBytes` path. The ASCII-plus-equal-length exact rule is still sound for a `SpecialCase` mapping, because it is also rune-to-rune. Otherwise, narrow the README wording to "ToLower/ToUpper/ToTitle".

## Checked and found correct
- **No out-of-bounds range can reach consumers.** `Lookup` slices every root set to the key window (`store/lookup.go:179-182`). `adopt` rejects sets that are not `ValidFor(span)` (`store/root.go:255`). `Compose`, `Slice`, and `Copy` validate their inputs (`ranges/operations.go:25-203`). The harness also checked every observed range against `len(result)` in all 13.2M cases and found no violations.
- **Differential oracle.** The harness (`zz_review_unicode_test.go`, `TestReviewUnicodeDifferential`) builds random inputs from 57 tricky tokens: `ẞ ß İ ı ɐ Ɐ ɑ Ɑ` K Å `ǅ ﬁ ΐ ſ`, U+0345, lone continuation bytes, surrogate encodings, over-range sequences, truncated sequences, `%` escapes, quotes, CR/LF, and NUL. Byte labels come from up to 5 random cuts, often mid-rune, and the replacement can carry its own source. For every result it compares the value with stdlib, compares the per-byte source labels with an independent oracle (the stdlib algorithm replayed with labels, including the 10-range prefix truncation), and checks that coarse results use the first contributing source. Covered ops: `strings`/`bytes` `Replace` (n in {-1,0,1,2,3,40}; `old` can be empty, a token, or a mid-rune substring), `bytes`/`strings` `ToValidUTF8`, `ToUpper`/`ToLower`/`ToTitle` for both, `Map` for both (identity, upper/lower/title, drop with -1, ASCII to 4-byte expansion, shrink, surrogate 0xD800, 0x110000, drop multibyte), `QueryEscape`/`PathEscape`/`QueryUnescape`/`PathUnescape`, `Quote`/`QuoteToASCII`/`QuoteToGraphic`/`Unquote` (with `"`, backquote, and `'` wrapping), `Repeat` (0-3), and `Join`. Results: 3 seeds x 100k iterations x 22 ops, 0 failures on both go1.26.6 and go1.27.0 (`differential-go1.26.6.txt`, `differential-go1.27.0.txt`). Every op has tens of thousands of cases with a non-empty tainted expectation.
- **The oracle can fail.** Each of 4 injected mutations was detected: a `ValidUTF8` width check (9,520 failures), dropping the ASCII condition in `CaseString` (5,678), the empty-`old` rune stepping in bytes (2,270), and the rune stepping in strings (failure lines shown). See `mutation-checks.txt`.
- **Boundaries** (`TestReviewUnicodeBoundaries`, 2,645 cases, 0 failures): 1/31/32/33/40 invalid runs across 4 unit shapes and 4 replacements; `Replace` with n in {-1,31,32,33}, including exactly 32 and 33 matches (exact vs coarse switch); and case conversion at `MaxRootBytes` -1/0/+1 with ASCII and K-sign inputs.
- **The exact segmenters mirror stdlib.** `mapReplaceSegments` matches `strings.Replace`, including the `old==new`, `n==0`, and no-match alias returns, and empty `old` stepping by `DecodeRuneInString`, which is consistent with `RuneCountInString` on invalid bytes. `mapReplaceByteSegments` matches `bytes.Replace`, which always copies and has no `old==new` shortcut. `mapValidUTF8Segments` matches `bytes.ToValidUTF8`: one replacement per maximal invalid run, and a valid-encoded U+FFFD is copied.
- **The ASCII exact case rule is sound.** For ASCII input, equal output length implies a 1:1 byte mapping, because each rune maps to exactly one rune of at least 1 byte.
- **Alias results derive exact windows** (`coarseStringAlias`, `caseStringHit`): unchanged `ToUpper`/`Map`/`QueryEscape`/`QueryUnescape`, and the `Unquote` substring `in[1:n-1]`, which is correctly shifted by 1.
- **Byte results are fresh base allocations.** In both toolchains, `bytes.ToValidUTF8`, `bytes.Map`, and `bytes.ToUpper` (ASCII copy via `append([]byte(""), s...)` or `MakeNoZero`) never alias or return interior slices.
- **`BuilderWriteRune`/`BufferWriteRune` use the actual `written` count**, which is correct for invalid runes that write 3 bytes (`iast/propagation/writer.go:52-59,135-147`).

## Not covered / open questions
- Documented limitation, not filed: results shorter than 2 bytes are never tainted. This matters more after shrinking transforms, for example `ToLower("\u212a")` -> `"k"` or `QueryUnescape("%27")` -> `"'"` (a 1-byte quote), while a 1-byte alias window (`Unquote("\"'\"")`) stays tainted.
- Evidence parts are cut at byte range boundaries. When a valid rune in the final value straddles two ranges, which requires byte-level ops such as a mid-rune `Replace` or concatenating a tainted `"\xc3"` with a clean `"\xa9"`, each `ValuePart.Value` is invalid UTF-8 on the wire. I did not check how the backend handles this.
- The differential ran with a single store owner and default range limit 10. Multi-owner fanout and non-default `DD_IAST_MAX_RANGE_COUNT` were not exercised here (see prop-ranges-fuzz-F1). The wrappers were called directly, not through an orchestrion-woven build.
