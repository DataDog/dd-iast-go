# crash-race-hunt: high-count race and checkptr hunt, plain and woven
Verdict: The internal taint, span and vulnerability machinery ran race-free across more than 1,300 race-enabled package runs and four purpose-built concurrent stress harnesses. Woven builds still contain one reproduced production data race: the `net/http` `ParseForm` advice re-assigns `Request.Form` and `Request.PostForm` on every call. That turns a race-free no-op re-parse into a data race, even when IAST is disabled at runtime (Critical).
Scope covered: Private copy `/tmp/ddiast-review/wt/crash-race-hunt` at HEAD 2e23b46, `GOTOOLCHAIN=go1.26.6`, `GOFLAGS=-p=4`, `GORACE=halt_on_error=0`. Plain `-race -count=20 -cpu=1,4,16` over all 19 packages in `./internal/taint/... ./internal/spans/... ./internal/vulnerability/...`. The one exception is `internal/taint/store`: `-short -count=20 -cpu=1,4,16`, plus the full suite including `TestMillionOperationChurn` at `-count=2 -cpu=1,4,16`. Woven `-race -count=5`: `iast/propagation`, the sql and exec testapps (`-cpu=1,4,16`), and `iast/integration/testapp` (full suite plus a new woven stress). `-gcflags=all=-d=checkptr=2`: plain root module and woven `iast/propagation` / integration (see the Checked section). Code read for concurrency: `store/{owner,value,lookup,writer}.go`, `request/{owner,scope,http,lazy}.go`, `spans/{annotation,owner,orchestrion,tainted}.go`, `vulnerability/tainted.go`, `writerbridge/bridge.go`, `propagation/writer.go`, `iast/net/http/orchestrion.yml`.

## Findings

### crash-race-hunt-F1: `ParseForm` advice writes `Request.Form`/`PostForm` on every call, racing with concurrent form readers (even with IAST disabled)
- Severity: Critical
- Category: race
- Location: iast/net/http/orchestrion.yml:152-162 (deferred `{{ $req }}.Form, {{ $req }}.PostForm = iasthttpbridge.Form(...)`)
- Claim: In Go 1.26.6, `(*Request).ParseForm` on an already-parsed request only reads `r.PostForm`/`r.Form`, since both are non-nil and it returns immediately. Handlers and middleware therefore commonly re-call `ParseForm` defensively while other goroutines read the parsed form (`FormValue`, `PostFormValue`, `r.Form[...]`), and in plain Go that is race-free. The woven advice runs a deferred closure on *every* call. The closure unconditionally stores both map headers back into the request (`r.Form, r.PostForm = Form(ctx, r.Form, r.PostForm)`), even when `Form` returns the identical maps: when the scope is inactive, sampled out, disabled, or already managed. Those plain pointer writes race with every concurrent reader and with other re-parses. Customer `go test -race` suites of woven apps fail as a result, and the Go memory model gives no guarantee for the interleaving. It happens whether or not IAST is enabled, because the assignment does not depend on `config.Enabled`. This is independent evidence for the secondary remark in life-lazy-reader-F1, which is primarily about the `ParseMultipartForm`/`replaceMatchingSuffix` write site. The write site here is distinct and needs its own fix.
- Evidence: `.omo/review/evidence/crash-race-hunt/reproducers/integration_testapp_zz_parseform_race_test.go` (copy into `iast/integration/testapp/`). The handler does one `ParseForm`, then one goroutine re-calls `r.ParseForm()` while another calls `r.FormValue("id")`/`r.PostForm.Get("id")`.
  - Woven: `cd iast/integration/testapp && GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -race -run '^TestRaceHuntParseFormReparse$' -count=3 -v .` fails with 3 `WARNING: DATA RACE` (`logs/woven_parseform_woven.out`): `Write at 0x00c0012d4090 by goroutine 38: net/http.(*Request).ParseForm.func1() <generated>:4 ... runtime.deferreturn()` / `Previous read at 0x00c0012d4090 by goroutine 39: net/http.(*Request).FormValue() .../net/http/request.go:1420`.
  - Woven with IAST off (`config.Enabled=false`, sampling 0): `-run TestRaceHuntParseFormReparseIASTDisabled` logs `woven=true iastEnabled=false`, followed by 3 `WARNING: DATA RACE` (`logs/woven_parseform_disabled.out`).
  - Plain control, same tests: `RACEHUNT_PLAIN=1 go test -race -run TestRaceHunt -count=3 -cpu=4,16 .` exits 0 with `races=0` and `woven=false` (`logs/plain_integ_control.out`).
  - Realistic stress (`reproducers/integration_testapp_zz_racehunt{,_test}.go`): 24 clients send 480 GET/form/JSON requests, and each handler spawns 4 goroutines that do sources, writers, SQL and exec. It produced 10 race reports, and *every one* is `net/http.(*Request).ParseForm.func1()` against `FormValue`/`PostFormValue`/`r.Form` reads or another re-parse (`logs/woven_integ_stress.out`). Once the re-parse is removed (`RACEHUNT_NOREPARSE=1`), the same stress is race-free (see Checked).
- Fix: Assign only on first parse, or only when the maps change. Capture `parsed := r.Form != nil && r.PostForm != nil` at entry and skip the deferred write when `parsed` holds. Also let `httpbridge.Form` report whether it replaced a map, and assign each field only when it did. Apply the same pattern to the `ParseMultipartForm` advice at lines 177-186 (life-lazy-reader-F1).

### crash-race-hunt-F2: Store owner acquisition drops most concurrent request begins on `ownerMu.TryLock` contention even when permits and owner slots are free
- Severity: Low
- Category: false-negative
- Location: internal/taint/store/owner.go:24-27; internal/taint/request/owner.go:84-88; internal/taint/request/scope.go:92-97
- Claim: `Manager.Acquire` wins a permit by CAS and then calls `store.Acquire`, which bails out if the global `ownerMu.TryLock` fails. The request then becomes `DecisionCapacityDropped` although both a permit and a store owner slot were free. Under bursty concurrent request starts, the effective sampling rate therefore falls well below the configured `DD_IAST_REQUEST_SAMPLING`/concurrency limits, and the loss is not attributable to real capacity. Memory and bounds are unaffected and nothing blocks. This matches the design's drop-under-contention policy, but the drop comes from a lock that could be avoided rather than from load.
- Evidence: `reproducers/request_zz_racehunt_acquire_test.go` runs 16 goroutines, below the cap of 64, looping `Begin`/`FinishContext`. Command: `go test -run TestRaceHuntBeginContentionDrops -count=3 -cpu=4,16 -v ./internal/taint/request` (plain, no race). Output (`logs/begin_contention.out`): `begins=32000 active=11817 capacityDropped=20183 (63.1%)` ... `(80.1%)` at cpu=16, and between 39.0% and 63.1% elsewhere. In every case `storeAcquireDrops == capacityDropped`. The store stress also shows all 64 owners `stateDead` (reusable) after the run, with `acquireDrops=39715`. This is a tight-loop upper bound; real handlers space out their begins.
- Fix: Make slot claiming lock-free with a per-slot `state` CAS (`unused/dead -> acquiring -> active`) and drop the global `ownerMu`, or retry `TryLock` a bounded number of times. The critical section is O(64) atomic loads.

### crash-race-hunt-F3: `TestCommitTaintedSkippedDedup` is flaky under repeated runs
- Severity: Low
- Category: test-gap
- Location: internal/vulnerability/tainted_dedup_test.go:138-151
- Claim: The subprocess asserts that telemetry aggregates exactly 2 distinct DEBUG log records with a total count of 3. Whether identical messages are coalesced depends on the telemetry client's heartbeat/flush timing, because a flush between the two `commitTainted` calls splits the aggregation. It failed 1 of 60 runs with `3 occurrences, 3 distinct, want 3/2`. The count is right and only the batching differs. This is timing-dependent, which the repo's test rules forbid.
- Evidence: `logs/internal_vulnerability.out` / `vulnerability-flake-TestCommitTaintedSkippedDedup.out` from `internal_vulnerability.race.test -test.count=20 -test.cpu=1,4,16`: `tainted_dedup_test.go:150: skipped dedup diagnostics = 3 occurrences, 3 distinct, want 3/2; records = [...{Level:"DEBUG", Count:1,...} x3]`.
- Fix: Assert only the total occurrence count, which is 3, and the level. Do not assert the number of distinct aggregated records. Alternatively, sum counts per message text.

## Checked and found correct
- Plain `-race -count=20 -cpu=1,4,16` (60 runs each) passed with `races=0` for commandbridge, scopebridge, sqlbridge, httpbridge, iobridge, urlbridge, jsonbridge, writerbridge, operatorbridge, evidence, redaction, request (17 s), ranges (78 s), spans (36 s), vulnerability (77 s; only F3 failed), vulnerability/dedup, and vulnerability/stacktrace. `internal/taint/propagation` passed 2×`-count=10 -cpu=1,4,16` (60 runs, 66 s + 136 s, `races=0`). For `internal/taint/store`: `-short -count=20 -cpu=1,4,16` passed, and so did the full suite including the million-op churn at `-count=2 -cpu=1,4,16` (228 s). Logs are in `logs/` and `plain-race-summary.txt`.
- Store churn stress (`reproducers/store_zz_racehunt_store_test.go`) ran 60 runs (`-count=20 -cpu=1,4,16`) with 0 races. The workload: 24 workers loop Acquire -> TaintSourceString/Derive/TaintBytes/PublishBytesMutation/BindObjectValue/UpdateWriter/SnapshotWriter/AdoptBufferWriter/Truncate/Reset -> (async) Finish. Alongside them, 6 readers run Lookup/`Entry.Handle`+Derive into foreign owners, LookupObjectValue, LookupWriterValue and InvalidateBuffer/InvalidateWriterPointer, and 4 late goroutines re-use and re-finish stale handles. Per run: up to `acquired=9600 lookupHits=95882 liveHandles=19189`. Every run ended at `charged=0 values=0`, so no counter leaked after all owners finished.
- End-to-end report stress (`reproducers/vulnerability_zz_racehunt_report_test.go`) ran 60 runs with 0 races. The workload: 16 workers × 60 requests via `request.Begin` + `taint.TaintString/TaintBytes`. They cover every internal propagation entry point (Join/Replace/CoarseFormatted/Coarse/StringWindows/Copy/Repeat/Case/CopyBytes/ReplaceBytes/JoinBytes/CaseBytes/BytesToString/JSONString) on own and *foreign, concurrently finishing* requests' values, followed by `evidence.CollectString/CollectJoinedStrings`, `ReportTainted` (span and orphan/owner paths), and `spans.Finished`+`scope.Finish` racing the reporters. The workers committed about 1,400-1,476 reports per run with dedup off.
- Woven `-race -count=5`: `iast/propagation` `-cpu=1,4,16` passed, 196 subtests, none skipped (157 s, go RSS 366 MB). The sql testapp at `-cpu=1,4,16` passed (103 s) and so did the exec testapp at `-cpu=1,4,16` (217 s). The full `iast/integration/testapp` suite including my stress with `RACEHUNT_NOREPARSE=1` passed with `races=0` (117 s). A separate `-v` stress run with no re-parse had 4 runs at `-cpu=4,16`, each producing `spansWithIAST=414..466` of about 496 spans, with 0 races. That shows concurrent woven sources, writers, JSON, SQL, exec and detached post-request goroutines (`URL.Query` + `ExecContext(context.Background())` after the scope finished) are race-free apart from F1. All measured woven build peaks stayed under 0.5 GB for the `go` process, so none crossed the 4 GB threshold.
- `-race` implies `-d=checkptr=1` for all of the above, and no run reported a checkptr failure. I also ran plain `go test -gcflags=all=-d=checkptr=2 -count=2 ./...` on the root module (`logs/plain_checkptr.out`). It found 0 `checkptr`/`fatal error` lines. The only failures were zero-allocation assertions: `TestDynamicObjectBinding` (store_test.go:203), `TestByteExactOpsNoActiveAndUntaintedAreAllocationFree`, `TestHashDoesNotAllocate`, `TestAddDuplicateNoAlloc`, `TestAddFullNoAlloc`, `TestPrepareBytesDoesNotAllocateOnDuplicate`, and `TestManagedLazyMapIsIdempotentAndAllocationFree`. checkptr instrumentation forces `unsafe.Pointer` operands to escape, so these failures are expected, not bugs. Woven `iast/propagation` at `-d=checkptr=2` passed (`logs/woven_prop_checkptr.summary`), and so did the woven full `iast/integration/testapp` suite, including the concurrent stress (`logs/woven_integ_checkptr.summary`). That run skipped only the F1 reproducer and zero-alloc tests, and it found 0 checkptr lines. Its build took 1,278 s under load average of about 70, while the `go` process RSS stayed at 355 MB.
- The lock order `Annotation` -> span mutex in `spans.Finished` is safe: the Finish advice is *prepended* before dd-trace-go takes `s.mu` (`internal/spans/orchestrion.yml:26-30`; dd-trace-go `span.go:1060`).

## Not covered / open questions
- The known race `prop-owner-isolation-F1` (`analysisSlot.index`) did not fire in my woven stress. Detached goroutines in the stress read `URL.Query()` after their request finished, but with 64 permits and 24 clients, slot reuse right after a detached read was rare. I did not re-run that node's targeted reproducer. Multipart re-parse (life-lazy-reader-F1) was deliberately not re-exercised.
- The race detector only sees executed interleavings. Absence of reports is not a proof, especially for the torn-generation windows statically described by store-concurrency-F2/F3 and prop-owner-isolation-F3.
- Woven runs used only Go 1.26.6. Go 1.27 woven builds fail to compile (hooks-compile-matrix-F2), so they were not race-tested.
