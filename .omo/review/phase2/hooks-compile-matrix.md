# hooks-compile-matrix: Weaving dd-iast-go into real-world Go codebases
Verdict: Every real-world codebase compiles, vets, tests and runs identically when woven on Go 1.26.6 with the pinned Orchestrion, and peak build memory stays within 1.0x to 2.2x of a plain build. The matrix still shows three ways valid customer builds break, and one of them can also take down the build host: on Go 1.27.0 the failing JSON advice drives the Orchestrion job server to 17 to 22+ GiB RSS while building golang.org/x/exp, against 0.27 GiB for a plain build (F6). The three breaks are these. First, the customer's `go.mod` can resolve Orchestrion to a released version (for example through dd-trace-go `orchestrion/all` v2.11.0-rc.1), which cannot load dd-iast-go's configuration. Second, every build fails on Go 1.27.0 because of the JSON-v2 advice. Third, a synthetic import-free package crashes the weaver. Weaving also adds heap allocations to allocation-free code even when IAST is inactive.
Scope covered: 8 real-world targets and 1 synthetic idiom module, built with `go tool orchestrion go build ./...` on `GOTOOLCHAIN=go1.26.6`, then on local go1.27.0, then on go1.27.0 with `GOEXPERIMENT=nojsonv2`. The dd-iast-go dependency is a `replace` to a private rsync copy of HEAD 2e23b46 (identical content, without `.git`). The aggregate `github.com/DataDog/dd-iast-go` import is added to each target's `orchestrion.tool.go`, and the targets are wired with `evidence/.../wire.sh`. Build memory was then re-measured serially, one build at a time with a fresh GOCACHE, under `/usr/bin/time -l` plus a process-tree RSS sampler, for 9 woven builds, 8 plain baselines and 5 go1.27 runs (`evidence/.../mem/SUMMARY.txt`).

## Findings
### hooks-compile-matrix-F6: On Go 1.27 the JSON advice failure makes the Orchestrion job server grow to 17-22+ GiB RSS (host / CI OOM)
- Severity: Critical
- Category: memory-bound
- Location: iast/encoding/json/orchestrion.yml:28-47 (trigger); orchestrion@23afa71 internal/jobserver/nbt/nbt.go:161-162,252-253, internal/toolexec/aspect/oncompile.go:174, internal/jobserver/server.go:109 (amplifier)
- Claim: A woven `go build ./...` of golang.org/x/exp (34 packages) on go1.27.0 hits the F2 compile error in woven `encoding/json`. About 35 s into the build, the parent `orchestrion go build` process (the job server that hosts the embedded NATS never-build-twice service) grows from about 1.6 GiB to 17 GiB in 20 s. The build then aborts with `resolving woven dependency on github.com/DataDog/dd-iast-go/iast/database/sql: internal error: nats: maximum payload exceeded`, preceded by many `sending never-build-twice request: exit status 2` lines. A second isolated run reached 22.3 GiB at 49.5 s and was still growing when my 20 GiB kill-switch SIGKILLed it (exit 137). This is the most likely source of the ~40 GB orchestrion process the user saw. My first go1.27 x-exp build ran for 640 s concurrently with 7 other builds, and the growth continues until the build aborts. So on a slower or loaded CI runner the peak is bounded only by available memory, which means OOM-killed runners or a swapping host (this machine has 64 GiB). The inflation is 62x over a plain build (0.27 GiB). The controls isolate the trigger: the same build with `GOEXPERIMENT=nojsonv2` (no JSON advice error) peaks at 0.83 GiB, and every Go 1.26.6 woven build stays at or below 1.33 GiB per process. samber/lo and the system-tests weblog fail on go1.27 the same way but have too few dependent packages to blow up (0.83-0.84 GiB), so the size of the explosion scales with how many packages concurrently fail woven-dependency resolution. Inferred mechanism (not traced in detail): the job server keeps each failed build's error and returns it to every waiter, dependents wrap those errors again when resolving woven dependencies, and the NATS server accepts messages up to its maximum payload size. Error messages therefore fan out and grow until a single message exceeds the payload cap.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/mem/SUMMARY.txt`; `mem/x-exp.woven-iast-127.{log,time,summary.json,timeline.txt}` (`/usr/bin/time -l`: `18301534208 maximum resident set size`; sampler top process `17452 MB orchestrion:go build`; timeline `36.8s 1640MB -> 41.1s 7359MB -> 45.6s 11575MB -> 55.4s 17452MB`); `mem/x-exp.woven-iast-127-rerun.*` (tree peak 22862 MB at 49.5 s, `killed_at_limit`, exit 137); controls `mem/x-exp.woven-iast-127-nojsonv2.*` (0.83 GiB), `mem/x-exp.plain-127.*` (294371328 B), `mem/x-exp.plain-126.*`, `mem/x-exp.woven-iast.*` (Go 1.26.6 woven 0.86 GiB). Command, run alone with a fresh cache: `cd x-exp && GOTOOLCHAIN=local GOCACHE=<fresh> /usr/bin/time -l timeout 1320 go tool orchestrion go build ./...`, with `mem/sampler.py` sampling the process tree's RSS every second (`mem/measure.sh`).
- Fix: Fixing F2 removes the trigger. Separately, dd-iast-go advice that references private stdlib internals must never be able to fail the build (gate it by Go version or experiment). Report the Orchestrion amplifier upstream: failed-build errors are fanned out and re-wrapped without bound, and the NATS payload limit is set to its maximum. Orchestrion should truncate or deduplicate stored errors and fail fast on the first woven-dependency error.

### hooks-compile-matrix-F1: A released Orchestrion (e.g. from dd-trace-go orchestrion/all v2.11.0-rc.1) cannot load dd-iast-go's aspects
- Severity: Critical
- Category: compile-break
- Location: go.mod:14; iast/propagation/orchestrion.yml:21 (and every `string-concat`/`slice-expression`/`type-conversion` join point, e.g. :336,:352,:381)
- Claim: dd-iast-go requires Orchestrion `v1.12.2-0.20260828141217-23afa71d6dcb`. Under semver, that pseudo-version is a *prerelease of v1.12.2*, so it sorts below every released v1.12.2, v1.13.x and v1.14.x. None of those releases contain the operator join points (`git merge-base --is-ancestor 23afa71d6dcb v1.13.0` is false, `git tag --contains 23afa71d6dcb` is empty, and v1.13.0 has no `string_concat.go`). The standard customer setup `github.com/DataDog/dd-trace-go/orchestrion/all/v2 v2.11.0-rc.1` requires `github.com/DataDog/orchestrion v1.13.0`, so MVS selects v1.13.0. Every build then fails before compiling anything, with `yaml.Decode ".../iast/propagation/orchestrion.yml": unknown injection point type "string-concat"`. The same failure follows whenever a customer runs `orchestrion pin` with a current released Orchestrion or `go get -u`. The README only says that consumers must use Orchestrion (README.md:9-11) and names no minimum version. The only workaround is `go get github.com/DataDog/orchestrion@<pseudo>`. That silently downgrades `orchestrion/all/v2` from v2.11.0-rc.1 to v2.11.0-dev.1, which no longer matches the dd-trace-go v2.11.0-rc.1 core. This goes beyond hooks-orchestrion-dep-F5 (a Medium release-risk finding): it is a reproduced build break on the canonical Orchestrion weblog.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/logs/st-golang-app_net-http-orchestrion.build126.log` (go.mod: `targets/st-golang-app_net-http-orchestrion/go.mod`, which shows `orchestrion v1.13.0`). Command: `cd st-golang-app/net-http-orchestrion && GOTOOLCHAIN=go1.26.6 go tool orchestrion go build ./...`. Output: `loading injector configuration: in "github.com/DataDog/dd-iast-go" ... yaml.Decode ".../iast/propagation/orchestrion.yml": unknown injection point type "string-concat"`, exit 1. The first wiring attempt already reported `github.com/DataDog/dd-trace-go/orchestrion/all/v2@v2.11.0-rc.1 requires github.com/DataDog/orchestrion@v1.13.0, not ...23afa71d6dcb` (`logs/wire-nho.log`). The workaround is in `logs/nho-downgrade.log` (`downgraded .../orchestrion/all/v2 v2.11.0-rc.1 => v2.11.0-dev.1`) and `logs/nho-downgrade_net-http-orchestrion.build126.log` (exit 0).
- Fix: Do not ship on a prerelease pseudo-version. Land orchestrion#881 and require a released Orchestrion that is at least the version the current dd-trace-go `orchestrion/all` requires. Document the minimum Orchestrion version, and add a CI lane that weaves dd-iast-go together with the latest dd-trace-go `orchestrion/all`.

### hooks-compile-matrix-F2: Every real-world target fails to build on Go 1.27.0, including targets that never import encoding/json
- Severity: Critical
- Category: compile-break
- Location: iast/encoding/json/orchestrion.yml:28-47 (and the decodeState advice that follows)
- Claim: This confirms base-test-127-F1 and sink-json-sources-F1 on real code. All 7 real targets that build on 1.26.6 fail on go1.27.0 with `dec.r undefined` / `dec.d undefined`. That includes samber/lo and go-sqlite3, whose own code does not use encoding/json: the woven dd-iast-go/dd-trace-go dependency closure pulls in and weaves `encoding/json` anyway (`resolving woven dependency on github.com/DataDog/dd-iast-go/iast/propagation: ... # encoding/json`). So adding dd-iast-go makes any Go 1.27 build fail, whatever the application does. With `GOEXPERIMENT=nojsonv2`, all 7 targets and the idiom module (except F3) build on go1.27.0. The JSON advice is therefore the only Go 1.27 blocker found across roughly 77k lines of real code.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/logs/*.build127.log` (7 files, each `Exit status: 1`, first error `$WORK/b072/orchestrion/src/encoding/json/<generated>:2: dec.r undefined (type *Decoder has no field or method r)`). Command: `cd <target> && GOTOOLCHAIN=local go tool orchestrion go build ./...`. Control: `logs/*.build127nojv2.log` (`GOEXPERIMENT=nojsonv2 GOTOOLCHAIN=local ...`, all `Exit status: 0`).
- Fix: Gate the legacy advice on the JSON implementation that is actually selected. Add JSON-v2 advice, or no advice at all, for Go 1.27 / `goexperiment.jsonv2` builds, so that an unsupported layout means a propagation miss and never a compile error.

### hooks-compile-matrix-F3: Import-free packages crash the weaver (confirmed with realistic helper packages)
- Severity: Critical
- Category: compile-break
- Location: iast/propagation/orchestrion.yml:13-31 (all operator aspects); orchestrion@23afa71 internal/toolexec/aspect/oncompile.go:195
- Claim: This confirms hooks-yml-operators-F3 on realistic package shapes: a generics helper package (`Cat[T ~string]`, `Add[T ~int|~string]`, `Head[T ~string|~[]byte]`), a named-types package, a slicing helper package, and a one-line concat package. Each has no imports, and each makes `go tool orchestrion go build` die with `panic: assignment to entry in nil map` at `oncompile.go:195`. Adding a single unrelated import (`import "strings"; var _ = strings.ToUpper`) makes all four compile, and they then behave identically to plain Go. None of the 7 real codebases contained a matching import-free package, but small import-free generic and type-helper packages are common in customer code.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/idioms/idioms-importfree/` (source), `logs/idioms.build126.log` (per-package: pgeneric, pnamed, pnoimport, pslice `panic: assignment to entry in nil map`, exit 1; the 7 other packages exit 0). Command: `cd idioms && for p in $(go list ./...); do GOTOOLCHAIN=go1.26.6 go tool orchestrion go build -o /dev/null $p; done`. Control: `idioms/idioms-withimports/` + `logs/idioms2.build126.log` (all 11 packages exit 0). Go 1.27 gives the same result: `logs/idioms.build127nojv2.log`.
- Fix: As in hooks-yml-operators-F3, Orchestrion must initialise the importcfg map when a package has no imports, or dd-iast-go must be able to add its first import. Until that lands, add an import-free fixture to CI.

### hooks-compile-matrix-F4: Weaving makes x/exp/slog's own zero-allocation test fail with IAST inactive
- Severity: Medium
- Category: perf
- Location: iast/propagation/orchestrion.yml:12-31 (concat wrappers); internal/taint/propagation/operator_concat.go:9-79
- Claim: This is real-code confirmation of hooks-yml-operators-F4 and prop-concat-conv-json-F2. In a woven `go test` of golang.org/x/exp/slog, no HTTP request and no active owner, `TestTextHandlerAlloc` measures 11 allocations per `Handle` where it expects 0. The plain run passes. The memory profile attributes the allocations to `slog/handler.go:480` `s.appendString(string(*s.prefix) + key)`. Natively, the non-escaping concatenation and the `string(b)` inside the concat use the stack temporary buffer. Once the expression is wrapped in `iastprop.Concat2(...)`, both escape to the heap. So weaving changes hot logging paths from allocation-free to allocating even when IAST is sampled out, and any customer `testing.AllocsPerRun` regression test fails under a woven `go test`. This finding is rated Medium because it duplicates the High in hooks-yml-operators-F4. Its value is the real-code impact evidence.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/logs/x-exp.slogalloc-woven.log` (`text_handler_test.go:151: got 11 allocs, want at most 0`, `FAIL golang.org/x/exp/slog`) vs `logs/x-exp.slogalloc-plain.log` (`--- PASS: TestTextHandlerAlloc`). Commands: `cd x-exp && GOTOOLCHAIN=go1.26.6 go tool orchestrion go test -count=1 -run Alloc -v ./slog/` vs `go test ...`. Allocation site: `logs/x-exp.slog-alloc-pprof.txt` (`10 10 480: s.appendString(string(*s.prefix) + key)`).
- Fix: Make the inactive fast path inlinable so escape analysis runs on the caller's native expression (for example a tiny `if !operatorbridge.HasValues() { return a + b }` body with the slow path out of line), or leave concats in non-escaping argument positions unwrapped.

### hooks-compile-matrix-F5: The aggregate import silently turns on dd-trace-go tracer auto-start
- Severity: Info
- Category: config
- Location: orchestrion.tool.go:26
- Claim: The root `github.com/DataDog/dd-iast-go` integration also imports `dd-trace-go/v2/ddtrace/tracer // integration`. The idiom module imports only dd-iast-go, yet its woven binary starts the Datadog tracer in `main`: it logs the tracer configuration and posts to `localhost:8126`. No other output differs. This is probably intended, since IAST needs spans, but the README does not say that enabling IAST also enables tracing.
- Evidence: `.omo/review/evidence/hooks-compile-matrix/idioms/idioms2.plain-vs-woven.diff` (only additions are the `Datadog Tracer v2.11.0-rc.1 WARN/INFO/ERROR` lines; every program output line is identical).
- Fix: Document it in the README install section, or split the tracer integration from the IAST aggregate.

## Checked and found correct
- Build memory was measured serially after the lead's steering: each run alone, with a fresh `GOCACHE`, under `/usr/bin/time -l` plus a process-tree RSS sampler (`evidence/.../mem/`). The Go 1.26.6 woven vs plain max RSS per process was: overhead 0.92 vs 0.31 GiB, lo 0.90 vs 0.31, x-exp 0.86 vs 0.31, go-sqlite3 0.86 vs 0.81, net-http-orchestrion with orchestrion/all 0.90 vs 0.79, system-tests weblog 0.90 vs 0.80, gin 1.33 vs 1.03, go-dvwa 1.29 vs 0.59. On the small modules, most of the woven peak comes from building the orchestrion tool itself once (compiling `nats-server` takes about 0.75 GiB). The largest weaving-attributable per-package inflation is 2.2x on go-dvwa's generated `modernc.org/sqlite/lib` (0.57 GiB plain compile vs 1.29 GiB orchestrion-toolexec compile). That is below the 3x High threshold. Tree peaks (up to 4.35 GiB for the 10-binary system-tests weblog) come from parallel links, and the plain build shows the same (3.93 GiB).
- On go1.26.6 every real target compiles woven with `go build ./...` (logs `*.build126.log`, all exit 0): the net/http benchmark, gorilla/mux+grpc+pure-Go sqlite, gin, 10 system-tests weblog packages (chi/echo/gin/gqlgen/graphql/graph-gophers/net-http/span-pool/grpc), samber/lo generics, 34 golang.org/x/exp packages, and cgo go-sqlite3. This is also true for the canonical Orchestrion weblog once Orchestrion is forced back to the pinned pseudo-version.
- The operator and call-site advice really applies to real root-module code: the woven `samber/lo` source contains `iastprop.StringsJoin/ToLower/TrimSpace/ReplaceAll/Fields`, `StringSliceLow/High/Bounds`, and `BuilderGrow/WriteRune/String`, in both `go build` and `go test` variants (checked by forcing a recompile with `-work`). The idioms binary links 48 `iast/propagation` symbols, including generic shapes (`Concat10[go.shape.string]`, `StringSliceLow[...]`, `BytesToString[go.shape.[]uint8]`).
- The idiom constructs that compile and behave identically woven are constant concatenation and conversion in `const`, array-length, `case` and typed-const contexts; `T ~string` concatenation returning `T`; `+` on `~int|~string|~float64` type parameters; slicing a `~string|~[]byte` type parameter; `string([]MyByte)`, `string(MyRunes)`, `string(rune)`, `MyBytes[1:2:3]`; promoted `WriteString`/`Write` through embedded `strings.Builder` and `*bytes.Buffer`; struct-field and slice-element builders; dot-imported `bytes`; `fmt.Sprintf(f, xs...)`; `pair(strings.Cut(s, "="))` multi-value forwarding; `return url.QueryUnescape(s)`; function values of `strings.ToUpper`; slicing arrays, `*[N]byte` with `uint8`/`uintptr`/typed-const bounds, map-index and call results; concatenation in goroutine args, `select` cases, `defer` and closures; cgo files with concatenation and `C.GoString`/`C.GoBytes`; and user types whose method names match stdlib ones. Evidence: `idioms/idioms2.plain.out` equals `idioms2.woven.out` except for the tracer lines.
- Woven test suites give the same results as plain: samber/lo (3 packages ok), x/exp slices/maps/constraints/slog subpackages ok, go-sqlite3 ok (with `-vet=off`, because of a pre-existing upstream printf vet error in `sqlite3_test.go:471`), and appsec-go-test-app (the same pre-existing `TestGetProducts` failure in both plain and woven).
- In the runtime smoke test, the woven go-dvwa binary and the plain binary return byte-identical responses (md5) for 7 requests, including SQLi and command-injection payloads. The woven binary does not panic, and its traces contain `_dd.iast.json` with 2 `SQL_INJECTION` and 1 `COMMAND_INJECTION`. The plain binary emits no IAST tags (`smoke/responses.*.txt`, `smoke/traces.*.iast-markers.txt`). The `/products/{category}` gorilla path variable is not reported, which matches the documented out-of-scope framework sources.
- `go vet ./...` is clean on overhead, go-dvwa, gin and the system-tests weblog. The failures on samber/lo (example tests missing from the module zip), x/exp (`stdmethods`) and go-sqlite3 (printf) are pre-existing upstream issues and are unrelated to weaving. `go tool orchestrion go vet` does not weave, so it adds no signal.
- Go 1.25.x rejects the modules because of the `go 1.26.6` minimum. Adding dd-iast-go bumps the customer `go` directive: samber/lo went from 1.18 to 1.26.6, x/exp from 1.25.0 to 1.26.6, and go-sqlite3 from 1.21 to 1.26.6. This is expected given base-test-127-F2.

## Not covered / open questions
- These are not real codebases above about 40k lines, and no vendored (`-mod=vendor`) or `go.work` multi-module customer build was tried. The system-tests `go.work` was not reproduced: each module was built standalone.
- Plugin (`-buildmode=plugin`), `-race`, `-cover` and cross-compiled (linux/amd64) woven builds were not part of this matrix.
- The exact 40 GB process the user saw was not captured live, because it had already ended. F6 reproduces the same process kind (`orchestrion go build` job server) and growth pattern on the same codebase and toolchain alone, reaching 22+ GiB before the kill-switch.
- Runtime smoke was run only for go-dvwa. It asserted markers, not full payload contents or redaction.
- Whether other dd-trace-go contrib modules at v2.11.0-rc.1 also require Orchestrion v1.13.x was only checked in the local module cache: of the cached modules, only `orchestrion/all/v2` requires it.
