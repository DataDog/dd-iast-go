# prop-owner-isolation: taint isolation across request owners and stale-owner safety
Verdict: Provenance isolation between owners holds on every propagation path I exercised. Ranges stay per owner, source IDs never resolve through a foreign or successor owner, and stale values stay clean after slot, permit, root-ID, and source-ID reuse. I found two defects outside the isolation logic itself: a reproduced data race on the analysis permit slot (Critical by the brief's scale), and a reproduced cross-owner budget interference where foreign or unsampled traffic exhausts a live owner's bounded state (Medium).
Scope covered: read `internal/taint/propagation/{propagation,string_exact,writer,operator_concat}.go`; `internal/taint/store/{owner,lookup,value,root,mutation,binding,store}.go` and `writer.go:60-320`; `internal/taint/request/{owner,lookup,scope,http,lazy,reader}.go`; `internal/taint/evidence/evidence.go:97-414`; `internal/vulnerability/tainted.go`; `internal/spans/owner.go`; `iast/propagation/writer.go:1-110`. Ran new reproducers with Go 1.26.6 in the private copy, with and without `-race`, through the real `request.Begin`/`Analysis.TaintString` API and the `iast/propagation` advice functions (`Concat2`, `BuilderWriteString`, `BuilderString`), plus internal `CoarseString`, `CopyString`, and `ReplaceString`.

## Findings

### prop-owner-isolation-F1: Unsynchronized write of `analysisSlot.index` in `Manager.Acquire` races with `analysisForOwner`
- Severity: Critical (brief scale: data race in production code)
- Category: race
- Location: internal/taint/request/owner.go:82; internal/taint/request/http.go:33
- Claim: `Manager.Acquire` does a plain store `slot.index = uint8(index)` on every acquisition of a permit slot. `analysisForOwner` does a plain read of `slot.index` for a slot it loaded from `directory`. The reads come from `ManageURLQuery`, `CloneReaderBytes`, and `ReadAllBytes`, and they can run on any goroutine. The value written is always the same, so builds without `-race` see no wrong behavior. It is still a data race under the Go memory model. This is the trigger: a goroutine that outlives or is detached from request A calls `r.URL.Query()` on a URL with an empty query, or hits `io.ReadAll` or a JSON decode on a bound body without then taking `sourceMu`, while A finishes and request B reacquires the permit. Customer `go test -race` runs of woven code will then report `DATA RACE` inside dd-iast-go.
- Evidence: `.omo/review/evidence/prop-owner-isolation/request_zz_review_owner_isolation_test.go` (copy it to `internal/taint/request/`). Command: `GOTOOLCHAIN=go1.26.6 go test -race -run '^TestReviewAnalysisSlotIndexRace$' -count=1 -v ./internal/taint/request`. It fails on the first run (`slotindex-race.out.txt`):
  - `WARNING: DATA RACE / Write at 0x00c001000018 by goroutine 8: request.(*Manager).Acquire() owner.go:82`
  - `Previous read at 0x00c001000018 by goroutine 9: request.analysisForOwner() http.go:33 / request.ManageURLQuery() lazy.go:37`
- Fix: Make `index` immutable. Set `m.slots[i].index = uint8(i)` once in `NewManager` and delete the write at owner.go:82. Alternatively, derive the permit index from the slot address.

### prop-owner-isolation-F2: Foreign and unsampled traffic that propagates an owner's value consumes that owner's bounded budgets, which drops the owner's own provenance
- Severity: Medium
- Category: false-negative
- Location: internal/taint/propagation/writer.go:123-133 (input-entry owners get `UpdateWriter`); store/writer.go:209-217 (`MaxWriters`); propagation.go:177-193,403-419 and string_exact.go:70-106 (`AdoptString` into every snapshot owner)
- Claim: Suppose request A is live and one of its tainted values is visible to other goroutines, for example lazily initialized config or a tenant header cached in a global. Then every propagation of that value in other requests publishes new state into owner A. That includes requests that are unsampled or capacity-dropped and have no scope at all. The state is charged to A's per-owner limits: 8 writers, 4,096 values, 512 roots, and 2 MiB. A strongly anchors the foreign builder objects and result strings until A finishes. The design documents that foreign-owner taint can be reported, but it does not say that foreign traffic spends the origin owner's budget. When 8 foreign builders take all of A's writer slots, A's own supported `strings.Builder` propagation is dropped for the rest of A's lifetime, which gives a false negative on a supported path. The same mechanism can exhaust A's value and root budgets through `+` and `strings` operations. Impact is bounded, and the trigger needs A-tainted data shared while A is still active, which is why this is Medium. Long-lived requests such as streaming or websocket handlers are the worst case.
- Evidence: `.omo/review/evidence/prop-owner-isolation/iast_propagation_zz_review_owner_isolation_test.go` (`TestReviewForeignTrafficExhaustsOwnerBudget`). Command: `GOTOOLCHAIN=go1.26.6 go test -run '^TestReviewForeignTrafficExhaustsOwnerBudget$' -count=1 -v ./iast/propagation`. Output (`budget.out.txt`):
  - `owner A id=1: foreign builders=8; A's own builder query tainted ranges=[]`
  - `foreign (unsampled) builder result ranges=[{start:30 length:13 source:tenant-from-A ownerID:1}]`
- Fix: Account foreign-created state separately from the owner's own state. For example, allow at most `MaxWriters/2` writer records, and a similar share of values and roots, to be created for an owner from snapshot entries when the receiver is not already bound to that owner. Another option is to create new writer state only for owners already tracking the receiver, plus the owner of the calling request when that owner is known. Add a regression test for the owner's own provenance under foreign load.

### prop-owner-isolation-F3: Read-side generation and state checks are still two loads against a lock-free `Acquire`, so a torn `Lookup` can build a hybrid `Entry`
- Severity: Low
- Category: race
- Location: internal/taint/store/lookup.go:152,183-191; lookup.go:40 (`Entry.Handle`); binding.go:60 (`OwnerRef.Handle`); writer.go:84-93 (`LookupWriterValue`)
- Claim: This has the same root cause as store-stress-F1 (`alive()`), at the read sites. `Acquire` (owner.go:53-59) bumps `generation`, stores `id`, and only then stores `stateActive`, all without `lifecycleMu`. Take a stale window of finished owner A. `Lookup` can load A's generation just before the bump and the successor's `stateActive` just after it. It then reads the successor's root at the same `rootID`/`rootGen` (both restart at 0/1 after `Finish`) and returns `Entry{OwnerGen: gA, OwnerID: idSuccessor, Ranges: successor's}`. Every consumer I found rejects such an entry, because they all validate the triple (index, gen, ID): `copySources` (request/lookup.go:140-146), `Entry.Handle`, `coarseMatch`, `analysisForOwner`, and `ExistingForOwner`. There is no provenance impact today, only a store contract violation (the comment at lookup.go:104 promises "complete live owner contributions") that later callers could trust.
- Evidence: static reasoning only. The probe `.omo/review/evidence/prop-owner-isolation/store_zz_review_lookup_torn_test.go` produced no hybrid in 1,184,024 owner reuses and 183.8M lookups (`lookup-torn.out.txt`: `hybrids=0`).
- Fix: Apply the store-stress-F1 fix: `Acquire` takes `lifecycleMu.TryLock` around the generation and state transition, or packs generation and state into one atomic word. All `lifecycleMu.RLock` read sites are then closed. In `Entry.Handle` and `OwnerRef.Handle`, reload `generation` after the state load.

### prop-owner-isolation-F4: Context-less sinks attribute foreign-owner taint to the foreign owner's span and bypass the sampled-out guard
- Severity: Info
- Category: cross-request
- Location: internal/vulnerability/tainted.go:45,110-127
- Claim: The sampled-out and finished guard (l.45) only fires when the sink's `ctx` carries a scope. Take a request B, unsampled or capacity-dropped, that calls `db.Exec(q)` or runs a background worker, which uses `context.Background()`, with a value tainted by live request A. `selectTaintedAnnotation` then falls back to `ExistingForOwner(A)` and commits the vulnerability to A's root span, with B's stack and location. The data-flow attribution to A's source is correct, but the report lands in another request's trace. This follows from the documented "foreign active owner" model. It should be written down, or restricted to reporting on the sink span only.
- Evidence: static reasoning only.
- Fix: Document the behavior, or drop the owner-span fallback when the sink runs outside that owner's scope. That second option is not detectable without `ctx`, so documenting it is probably the realistic choice.

### prop-owner-isolation-F5: `Analysis.Finish` uses the same check-then-CAS as `Owner.Finish`, but it is unreachable in production
- Severity: Info
- Category: race
- Location: internal/taint/request/owner.go:259-273
- Claim: This answers the open question in store-stress-F3. `Analysis.Finish` checks `generation`, then does `CAS(active true→false)`. A stale second `Finish` that races with reuse of the permit slot could finish the successor analysis: it would clear B's source table, finish B's store owner, and release B's permit bit. The only production caller is `Scope.Finish` (scope.go:214-219). It swaps the handle to zero under `s.mu` before calling, so each analysis is finished at most once. I found no other caller, and no path that calls `Finish` on an `analysisForOwner` handle.
- Evidence: static reasoning only (grep of production `.Finish()` callers).
- Fix: For robustness, pack generation and active into one atomic word and CAS on it.

## Checked and found correct
- Concurrent owners on one value: `Concat2(aVal, bVal)` gives exactly `[0,10) alpha-AAAA owner A` and `[10,10) bravo-BBBB owner B`. A three-write `strings.Builder` gives the same result at offsets 0 and 11. After A finishes, only B's range remains, and after both finish nothing remains (`TestReviewCrossOwnerConcatAndReuse`, `owner-iso.out.txt`).
- Successive reuse: successor C reuses permit 0 and store slot 0, and its first root is again `rootID 0 / gen 1 / source ID 0`, the same coordinates as A's stale slots. Stale A and B values, the concatenated and built results, and new `Concat2`, `CopyString`, `CoarseString`, `ReplaceString`, and `Builder` results over stale A are all untainted. `store.Lookup` returns 0 entries for the stale keys, and C's own value resolves only to C's source.
- Owner ends during propagation: 8-14 late goroutines ran Builder, Concat, and Coarse over values of finishing owners while the only slot was reused continuously (`MaxConcurrentRequests=1`). Every tainted result's resolved source had to equal the tainted bytes. Results: 817,422 owner cycles and 167.9M ops without `-race` (126,373 tainted results, 0 mismatches), and 137,033 cycles and 33.0M ops with `-race` (0 mismatches, 0 `DATA RACE`) (`owner-iso.out.txt`, `owner-iso-race.out.txt`). In the propagation paths, the torn `beginWrite` from store-stress-F1 is caught by the second `alive()` in `putWindow` (value.go:140) and rolled back. Only writer and binding paths lack that second check, and store-stress-F1 already reproduces those.
- Owner ID reuse and ABA: `ownerID` is a process-unique `uint64` (owner.go:54). Every cross-layer handoff compares index, generation, and ID: `Entry.Handle`, `copySources`, `analysisForOwner`, `coarseMatch`, the `bytes_exact`/`string_exact` owner matching, the span `ExistingForOwner` and `finishOwnerSpan`, and the evidence owner identities. Source IDs are only ever resolved through the owner that published them.
- Interned and shared runtime strings: every source is cloned (`strings.Clone` in root.go:40,80,120,162), so interned `textproto` header keys and static strings are never tainted. Lazy `Manage*` hooks skip values that are already tainted, and only managed clones can be tainted.
- Finish ordering: the analysis is deactivated, then the directory entry and source table are cleared, then the store owner finishes, then the permit is released (request/owner.go:259-273). Store `Finish` excludes in-flight writers with `lifecycleMu.Lock` after the `stateFinishing` CAS. In the window between the two, sinks cannot resolve sources (`copySources` fails), so there is no misattribution. `ReportTainted` drops reports whose `ctx` scope is sampled out or finished.

## Not covered / open questions
- Related findings from other nodes that I did not re-report: store-stress-F1 (a torn `alive()` lets writer and binding state reach the successor owner), store-stress-F3 (stale `Owner.Finish`), hooks-io-bufio-F1 (a pooled or reset `bufio.Reader` keeps its original owner's binding, which is a cross-owner bleed), the store-lookup High (stale candidates consume the four-owner snapshot fanout), and life-owner-scope-F1.
- No woven end-to-end HTTP test with two real requests. The reproducers call the request and advice APIs directly. GC address-reuse identity is left to store-identity-gc.
- The torn-writer path of store-stress-F1 was not hit through the `iast/propagation` builder API in 60 s. My workload used fresh builders, which is a weaker trigger than a stale `WriterRef`.
- JSON decoder-slot cross-owner association (`jsonbridge`) and `sync.Pool`-reused `[]byte` adopted by `io.ReadAll` were not exercised. The latter is covered by the documented byte-alias limitation.
