# life-public-api: taint/ public API design and correctness

Verdict: The exported `taint` package (`taint/taint.go`, `taint/orchestrion.yml`) is small, safe against nil/empty/concurrent misuse, and correctly forwards to the internal request-scoped store without leaking internal owner/store identifiers. No Critical or High defect was found. The main gaps are papercuts for the extension authors this package is meant to serve: it currently has zero production callers other than its own tests, one function pair has a Go-generics nil-inference trap, and the aliased `Origin`/`VulnerabilityType` types hide their `String()`/JSON methods from `go doc`.

Scope covered: `taint/taint.go` (full, all 8 exported functions/generic pairs, 5 exported types, all constant re-exports), `taint/orchestrion.yml`; cross-checked against `internal/taint/request/{scope,owner,lookup,table}.go`, `internal/taint/store/{store,root}.go`, `internal/taint/ranges/marks.go`, `internal/model/constants/{origin,vulnerabilitytype}.go`; `taint/taint_test.go` (existing suite, run); `iast/database/sql/sql.go`, `orchestrion.tool.go`, `README.md`, `CONTRIBUTING.md`, `AGENTS.md` for intended-consumer context. Reproducers run from `/tmp/ddiast-review/wt/life-public-api` (rsync copy) with `GOTOOLCHAIN=go1.26.6`; copies under `.omo/review/evidence/life-public-api/`.

## Findings

### life-public-api-F1: `~[]byte` generic functions cannot accept a bare `nil` literal
- Severity: Low
- Category: quality
- Location: taint/taint.go:142 (`TaintBytes`), taint/taint.go:163 (`IsTaintedBytes`), taint/taint.go:182 (`VisitBytes`)
- Claim: `TaintBytes`, `IsTaintedBytes`, and `VisitBytes` are generic over `T ~[]byte`. Go cannot infer `T` from a bare untyped `nil` argument when `nil` is the only source of type information, so the natural call `taint.IsTaintedBytes(nil)` (or `VisitBytes(nil, cb)` / `TaintBytes(ctx, src, nil)`) fails to *compile* with "cannot infer T", even though `IsTaintedBytes([]byte(nil))` and `IsTaintedBytes(someNilByteVar)` both work and behave correctly (return `false` for a nil/empty slice, per `store.BytesKey`'s `len(value)==0` check). This is exactly the kind of rough edge that undermines the "minimal, safe to consume" goal for a package whose whole purpose (per `AGENTS.md`: "expos[e] a simple API that instrumentation will use") is to be called by new, external-to-this-package integrators.
- Evidence: `.omo/review/evidence/life-public-api/nilinfer/main.go` + `.omo/review/evidence/life-public-api/nil-inference-error.txt`:
  ```
  nilinfer/main.go:8:26: in call to taint.IsTaintedBytes, cannot infer T (declared at ./taint/taint.go:163:21)
  ```
  Also reproduced live inside a realistic caller in `.omo/review/evidence/life-public-api/zz_review_public_api_test.go` (original draft failed the same way against `TaintBytes`/`VisitBytes`/`IsTaintedBytes`; see `review-public-api-test.out.txt` for the passing run after switching those three call sites to a typed nil).
- Fix: not fixable inside Go's generic inference rules without an API change; document the requirement to pass a typed `nil` (`[]byte(nil)` or a `[]byte` variable) in the doc comments of `TaintBytes`, `IsTaintedBytes`, and `VisitBytes`, e.g. "value may be nil, but must be a typed []byte (or ~[]byte), not a bare nil literal".

### life-public-api-F2: Undocumented drop condition — invalid/unnamed `Origin` values are silently rejected
- Severity: Low
- Category: doc
- Location: taint/taint.go:126-151 (doc comments for `TaintString`/`TaintBytes`); internal/taint/request/table.go:214-217 (`validOrigin`)
- Claim: `TaintString`/`TaintBytes` doc comments list the drop conditions as: "analysis is inactive, the value or source name exceeds 64 KiB, the value is shorter than two bytes, storage is full, or bounded synchronization is contended." They omit a fifth, real, silent-drop condition: an invalid `Origin` (the unnamed zero value, or a value above `OriginCount`) is rejected by `validOrigin` in `Table.prepareString`/`prepareBytes` with `AddRejected`, and `Analysis.TaintString`/`TaintBytes` (`internal/taint/request/owner.go:139-140,215-216`) treat any non-`AddAdded`/`AddDuplicate` status as a drop. Since `Source.Origin` is a plain exported `Origin` (`uint8`) field, nothing in the public type system prevents an external caller from constructing `taint.Source{Origin: 0}` or an out-of-range value and being surprised that it is silently dropped rather than, say, defaulting to a generic origin.
- Evidence: confirmed both by static reading of `validOrigin` (`internal/taint/request/table.go:214-217`) and by a passing reproducer, `TestReviewPublicAPIInvalidOriginDropsSilently` in `.omo/review/evidence/life-public-api/zz_review_public_api_test.go`, run with `-race`; captured output in `.omo/review/evidence/life-public-api/review-public-api-test.out.txt` (`--- PASS: TestReviewPublicAPIInvalidOriginDropsSilently`). The existing (pre-review) test `TestTaintDropsInvalidAndOneByteSources` in `taint/taint_test.go:98-105` already exercises the same behavior with `taint.Source{}`, confirming this is deliberate, not a bug — only the exported doc comment is incomplete.
- Fix: add "or the source origin is not a recognized [Origin] value" to the `TaintString`/`TaintBytes` doc comments.

### life-public-api-F3: `go doc` on the public package does not surface `Origin`/`VulnerabilityType` methods
- Severity: Low
- Category: doc
- Location: taint/taint.go:20-21 (`type Origin = constants.Origin`), taint/taint.go:44-45 (`type VulnerabilityType = constants.VulnerabilityType`)
- Claim: `Origin` and `VulnerabilityType` are plain type *aliases* to types defined in `internal/model/constants`, which is where their `String()`, `MarshalJSON`/`UnmarshalJSON` (via the `msgp:shim` directive) methods live. Because `go doc` (and by extension pkg.go.dev-style rendering) resolves methods by the package that declares the type, `go doc ./taint Origin` / `go doc -all ./taint` show only the one-line alias and doc comment — no methods — even though `taint.OriginHttpRequestBody.String()` compiles and works (proven by the existing `TestPublicConstantAliases` test). An external reader of the `taint` package's own documentation has no way to discover that these constants stringify or marshal to JSON without already knowing to look at (an unimportable) internal package's source.
- Evidence: `.omo/review/evidence/life-public-api/godoc-taint.txt` — `go doc -all ./taint` output listing `type Origin = constants.Origin` / `type VulnerabilityType = constants.VulnerabilityType` with no method list, contrasted with `taint/taint_test.go:170-173`'s passing `TestPublicConstantAliases`, which calls `.String()` on both successfully.
- Fix: informational; if discoverability matters, add one line to each type's doc comment noting `String()`/JSON marshaling are available (e.g. "Origin implements fmt.Stringer and JSON marshaling; see its String method."), since the methods themselves cannot be moved into `taint` without duplicating the internal enum.

### life-public-api-F4: The public API has no production caller; only its own test exercises it
- Severity: Info
- Category: test-gap
- Location: taint/taint.go (whole file); orchestrion.tool.go:18
- Claim: Every current source (`iast/net/http`, `iast/net/url`, `iast/bufio`, `iast/io`, `iast/encoding/json`) and every current sink (`iast/database/sql`, `iast/os/exec`) calls `internal/taint/request.Analysis.TaintString`/`TaintBytes`/`request.IsTaintedString`/`request.VisitString` etc. directly, not the public `taint.TaintString`/`IsTaintedString`/`VisitString` wrappers. A repo-wide search for `dd-iast-go/taint"` finds only `taint/taint_test.go` and the compile-time-tooling import in `orchestrion.tool.go:18` (`_ "github.com/DataDog/dd-iast-go/taint" // integration`, which never calls into the package at runtime). Per `AGENTS.md`, `taint/` is deliberately "the simple API instrumentation will use" for new, externally-added detections — this is expected today (no third-party detection exists yet) — but it means correctness of this public surface is validated only by its own unit test file, not by any real integration path, so a future internal refactor of `internal/taint/request` could silently break the public contract without any other test noticing until an external consumer appears.
- Evidence: static reasoning only (NEEDS-REPRO not applicable — this is an absence-of-usage observation, not a runtime defect); `grep -rl 'dd-iast-go/taint"' .` on the main checkout returns only `taint/taint_test.go` and `orchestrion.tool.go`.
- Fix: none required now; worth a note in `CONTRIBUTING.md`/`AGENTS.md` that `taint/taint_test.go` is the sole safety net for this contract, so changes to `internal/taint/request`'s public-facing behavior must keep `taint/taint_test.go` green.

## Checked and found correct
- Nil/empty safety: `TaintString`/`TaintBytes` with a `nil` `context.Context`, `IsTaintedString("")`, `IsTaintedBytes` with a nil slice, `VisitString`/`VisitBytes` with a nil `visit` callback or empty/nil input all return the documented no-op result without panicking. Verified by `TestReviewPublicAPINilAndEmptySafety` (evidence: `review-public-api-test.out.txt`) and by reading `store.StringKey`/`BytesKey` (`internal/taint/store/store.go:44-58`, explicit `len(value)==0` guard) and `request.FromContext`/`Scope.Analysis` (`internal/taint/request/scope.go:164-183`, nil-receiver guards).
- Concurrency: 32 goroutines x 200 iterations calling every exported function (including interleaved invalid/degenerate inputs) while repeatedly creating and finishing scopes ran clean under `-race` (`TestReviewPublicAPIConcurrentStress`, evidence: `review-public-api-test.out.txt`). The pre-existing `TestVisitRaceFinishReturnsCompleteSourceOrNothing` (`taint/taint_test.go:126-146`) specifically covers the Visit-vs-Finish race and passed under `-race` as part of the baseline run (`baseline-taint-test.out.txt`).
- Type-preserving generics: `TaintString[T ~string]`/`TaintBytes[T ~[]byte]` correctly round-trip named types (`namedString`, `namedBytes` in `taint/taint_test.go`), so the public API does not force callers to convert to/from plain `string`/`[]byte`.
- No internal identifiers leak through the public surface: `publicRange` (`taint/taint.go:191-201`) copies only `Start`, `Length`, `Source`, `Marks` from the internal `request.ResolvedRange`, deliberately dropping `OwnerID`, `OwnerGen`, `OwnerIndex`, and `RangeOrdinal` — none of the internal store/owner bookkeeping is exposed.
- `Marks.Has` cannot panic or misbehave on out-of-range `VulnerabilityType` values: `ranges.HasMark`/`MarkBit` (`internal/taint/ranges/marks.go:9-20`) explicitly bounds-check (`vulnerability == 0 || uint(vulnerability) > constants.VulnerabilityTypeCount || vulnerability >= 64`) before any bit shift; confirmed with `Marks{}.Has(255)` and `Has(0)` in `TestReviewPublicAPINilAndEmptySafety`.
- Byte-size documentation is accurate: `MaxRootBytes = 64<<10` (`internal/taint/store/limits.go:14`) matches the "64 KiB" claims in both `TaintString`'s and `TaintBytes`'s doc comments, and the capacity-vs-length distinction in `TaintBytes`'s doc (`cap(value) > MaxRootBytes` in `internal/taint/store/root.go:110`) is correct.
- `taint/orchestrion.yml` correctly declares an empty `aspects: []` list (the package has no instrumentation of its own, it is a pure API), and `iast/propagation/orchestrion.yml` consistently excludes `github.com/DataDog/dd-iast-go/taint` from every operator aspect's own-package guard, so the public API cannot recursively re-instrument itself.
- `gofmt -l`, `go build ./taint/...`, `go vet ./taint/...`, and `go tool checklocks ./taint/...` are all clean on `taint/taint.go` (run from the private worktree).
- The existing `taint/taint_test.go` suite (11 tests) passes under `-shuffle=on -race`.

## Not covered / open questions
- Whether a future third-party/internal detection actually adopts `taint.TaintString`/`VisitString` end-to-end (e.g., wired through a new `orchestrion.yml`) was not exercised, since none exists yet on this branch.
- JSON/MessagePack serialization of a value built directly from `taint.Source`/`taint.Range` by an external caller (as opposed to the internal `internal/model.Source`/`internal/model.Evidence` types used by the real report pipeline) was not tested; the public types have no `MarshalJSON`/`MarshalMsg` of their own.
- Whether pkg.go.dev's live rendering of an `internal/` module differs from the local `go doc` behavior reproduced above (e.g., whether it cross-links alias methods) was not tested against the real pkg.go.dev service, since this module is private.
