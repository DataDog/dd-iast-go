# prop-ranges-fuzz: long fuzz campaigns and per-byte oracle property tests for internal/taint/ranges
Verdict: The `internal/taint/ranges` algebra is correct. Across 60.9M fuzz executions and 1.1M oracle cases, every exported operation matched a naive per-byte label oracle, with no panic, wrap, or invariant break. The one real defect sits at the package boundary: coarse and duplicate-body callers stamp `DefaultLimit` into the per-Set limit, which silently overrides `DD_IAST_MAX_RANGE_COUNT` for every value derived afterwards (Medium, reproduced).
Scope covered: `internal/taint/ranges/{ranges,marks,canonical,operations}.go` read in full, plus the existing `fuzz_test.go`, `property_test.go`, and `internal_test.go`. I ran FuzzCanonicalize and FuzzSliceAndCopy for 10 minutes each. I wrote a new 17-way oracle property test (100k cases per seed, 11 seeds) and ran a new byte-steered oracle fuzz target for 10 minutes. I also traced limit plumbing to the callers in `internal/taint/propagation/{propagation,string_exact,bytes_exact,string_coarse}.go`, `internal/taint/request/reader.go`, and `internal/taint/store/root.go`. All work used Go 1.26.6 in a private copy.

The oracle harness is `oracle_review_test.go`. It builds random run-structured label arrays and turns them into input Sets with random limits (0, 1-3, 1-64, and 65-254), so truncated inputs are exercised. Nil (untainted) inputs occur too, and dst is pre-filled with garbage. For each operation, the harness compares the Set against `runsOf(expected labels)` truncated to the normalized limit. It also checks `Outcome.Valid`, `Outcome.Truncated`, `ValidFor(len)`, and `Limit()`, and that no non-destination input was mutated. Random dst aliasing uses dst == source, dst == base, and base == source for Overwrite. Invalid-parameter cases must return `Valid=false`, an empty dst, and the normalized limit. Operations covered: Canonicalize (including 190-194 inputs and five kinds of malformed range), AdoptCanonical (overlap, mergeable-adjacent, unsorted, and out-of-bounds input), Copy, Shift, Concat, Append, Slice, Join (0-6 elements), Repeat, Compose (including the same Set twice), Clear, Overwrite, Write, CopyOverwrite, Coarse, MarkAll, MarkSource, and UnsafeFor (including invalid vulnerability values). Separate tests cover uint32 boundaries, worst-case 2n-1 fragmentation at `MaxCanonicalInput`, and Repeat with count about 1.4e9 on a multi-range source.

## Findings
### prop-ranges-fuzz-F1: The configured range limit is lost after coarse propagation or duplicate body adoption
- Severity: Medium
- Category: config
- Location: internal/taint/propagation/propagation.go:415, internal/taint/propagation/propagation.go:692, internal/taint/request/reader.go:110; inherited at internal/taint/propagation/string_exact.go:72, internal/taint/propagation/bytes_exact.go:58 and every `entry.Ranges.Limit()` call site
- Claim: The effective range cap travels inside each `ranges.Set` (`root.limit = set.Limit()`, `store/root.go:353`). Source roots correctly use `ranges.Limit(config.MaxRangeCount)` (`store/root.go:47,88,128,172,216`). `CoarseString`/`CoarseBytes` (`propagation.go:415,692`) and the duplicate `io.ReadAll` body path (`reader.go:110`) instead adopt with the constant `ranges.DefaultLimit` (10). Every later exact operation takes its limit from the first owner entry it sees (`limit := entry.Ranges.Limit()`). So after one coarse step, the value and everything derived from it are capped at 10 whatever the configuration says, and the result depends on argument order. With `DD_IAST_MAX_RANGE_COUNT=64`, later ranges and their sources are dropped from evidence. With a configured 1-9, values exceed the configured cap by up to 10x, though never the store's hard cap of 64, so memory stays bounded. This is a provenance and config-fidelity bug, not a memory-bound one.
- Evidence: `.omo/review/evidence/prop-ranges-fuzz/zz_review_range_limit_test.go`. Command: `go test -count=1 -run TestReviewCoarseResetsConfiguredRangeLimit -v ./internal/taint/propagation/` (`range-limit-repro.log`). The captured output shows `DD_IAST_MAX_RANGE_COUNT=64 sources=16: direct join ranges=16, join-after-coarse ranges=10` and `DD_IAST_MAX_RANGE_COUNT=2 sources=6: direct join ranges=2, join-after-coarse ranges=6`.
- Fix: At the three sites, pass `ranges.Limit(config.MaxRangeCount)`, or the contributing entry's `Ranges.Limit()`, instead of `ranges.DefaultLimit`. Longer term, make the store clamp to the process configuration on publish rather than trusting a caller-supplied per-Set limit. Add a propagation test for configured limits 2 and 64 across a coarse step, extending `TestConfiguredSourceRangeLimit`, which currently ends at the coarse call.

### prop-ranges-fuzz-F2: The shipped fuzz targets are nearly vacuous, and half the algebra has no oracle coverage
- Severity: Low
- Category: test-gap
- Location: internal/taint/ranges/fuzz_test.go:14-90, internal/taint/ranges/property_test.go:16-139
- Claim: `FuzzSliceAndCopy` always uses one full-coverage range (source 0, marks 0) as its base. It checks only `Valid`/`ValidFor` and never compares against an oracle, so it cannot detect wrong offsets, lost ranges, or a wrong source. `FuzzCanonicalize` never sets `Marks`, so marks-sensitive merging and invalid-mark rejection are never fuzzed, and `valueLen` stays at 255 or below. The existing byte oracles cover Canonicalize, Concat, Slice, Clear, CopyOverwrite, Repeat, and Join. They do not cover Compose, the primitive behind exact `Replace` (`string_exact.go:179`, `bytes_exact.go:168,301`). Coarse, Shift, Copy, MarkAll/MarkSource/UnsafeFor, AdoptCanonical rejection, dst aliasing, and input immutability are also uncovered. No defect was found in these paths (see the campaign table), but a regression there would go unnoticed.
- Evidence: `.omo/review/evidence/prop-ranges-fuzz/fuzz-slicecopy.log` (23.2M execs but only 9 interesting inputs in 10 minutes, against 202 for the new oracle target). The new harness `oracle_review_test.go` covers every gap listed, and `mutation.log` shows it kills 8/8 mutants.
- Fix: Merge `oracle_review_test.go`, or its per-byte oracle plus the byte-steered `FuzzReviewOperationsOracle`, and add marks to `FuzzCanonicalize`.

### prop-ranges-fuzz-F3: `Canonicalize` is exported, unused in production, and needs a 29 KiB stack frame
- Severity: Low
- Category: perf
- Location: internal/taint/ranges/canonical.go:15-45
- Claim: No non-test caller of `ranges.Canonicalize` exists; a grep of `internal/` and `taint/` excluding `*_test.go` finds only its definition. The function holds three `[383]Range` scratch arrays on the stack. The compiler reports a frame of `$29312` bytes, against `$1600` for Concat/Slice and `$1648` for Compose. If a future hot-path caller uses it from a fresh goroutine, every call forces stack growth from 8 KiB. Today it is dead weight that the architecture doc presents as part of the live pipeline.
- Evidence: `go build -gcflags=-S ./internal/taint/ranges` gives `ranges.Canonicalize(SB), ABIInternal, $29312-48` and `ranges.Concat(SB), ABIInternal, $1600-48` (see Checked list). Static otherwise.
- Fix: Either drop `Canonicalize` (keep `AdoptCanonical`), or document that it is a test and reference oracle only. If it stays, use a single scratch buffer, or cap the input at `HardLimit` for any runtime caller.

## Checked and found correct
- Canonicalize implements first-input precedence, sorting, equal-provenance merging, and output-limit truncation exactly as the per-byte oracle does. This holds for 20M+ fuzz executions and about 65k oracle cases at up to 194 inputs, including the malformed-input rejections: zero length, wrap, end past `valueLen`, bit 0, bits above `VulnerabilityTypeCount`, and more than 192 inputs.
- The fragment bound `2*MaxCanonicalInput-1` is tight and sufficient. The endpoints argument holds (at most 2n distinct endpoints), the nested and interleaved worst cases are accepted and match the oracle, and the `acceptedCount+fragmentCount > len(scratch)` reset is unreachable for valid input.
- `orderedBuilder` merges across part boundaries identically to the maximal-run oracle, and truncation keeps the earliest output-order prefix with `Truncated` set exactly when the oracle has more than `limit` runs. Early `break` on truncation in Join, Compose, and Repeat cannot drop a range that would have merged: only the next range can be adjacent, and it is the one that triggered truncation.
- Repeat work is bounded. The full-coverage single-range fast path collapses to one range. Any other source adds at least one new run per copy, so the loop ends within about `limit+1` iterations even with count near 1.4e9 (`TestReviewRepeatHugeCountBoundedAndExact`). Overflow is rejected before the loop.
- uint32 arithmetic holds. `checkedEnd` and `addLength` reject wrap, a range ending exactly at `MaxUint32` is accepted, and Shift, Concat, Join, Repeat, Compose, and Overwrite overflow cases return `Valid=false` with an empty dst (`TestReviewUint32Boundaries`).
- Every operation reads its inputs fully before `*dst = result`, so dst may alias any input, including base == source for Overwrite and the same Set twice in Compose. Inputs are never mutated. There is no panic on nil dst or nil inputs.
- `UnsafeFor` does not need to re-merge, because removing a range only creates gaps. `markWhere` re-merges ranges that become newly equal. `Coarse` matches "first contributing byte's source, marks intersected over all contributing bytes", with untainted bytes not contributing.
- `validMarks`/`MarkBit` are consistent with `VulnerabilityTypeCount` (36), and invalid vulnerability values reset dst with the source's limit.
