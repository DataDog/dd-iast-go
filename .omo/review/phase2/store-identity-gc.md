# store-identity-gc: address-based value identity vs. GC address reuse
Verdict: The value store itself is sound: GC address reuse cannot bring back taint from a finished or foreign owner. Every live slot is backed by a strong root anchor, and finished or stale slots are rejected by owner and root generation checks, which I reproduced. The `strings.Builder` writer state is the exception. It is keyed by an unanchored backing address, so a clean builder value can inherit stale taint, including taint from another request, after GC reuses that address (reproduced, High).
Scope covered: `internal/taint/store/{store,owner,root,value,lookup,mutation,binding,writer,limits}.go`, `iast/propagation/writer.go`, `internal/taint/propagation/{writer,json}.go`, `internal/taint/writerbridge/bridge.go`, `internal/taint/jsonbridge/bridge.go`, `iast/encoding/json/{orchestrion.yml,json.go}`, bytes.Buffer native-hook aspects in `iast/propagation/orchestrion.yml:1570-1680`, `internal/taint/request/lazy.go` (uintptr uses), `taint/taint.go`, and `internal/taint/store/identity_test.go`. I ran reproducers in a private copy with `GOTOOLCHAIN=go1.26.6` using plain `go test`. They call the `iast/propagation` wrappers directly, which are the functions woven call sites invoke.

## Findings

### store-identity-gc-F1: strings.Builder writer views are not anchored, so a freed and reused backing address revives stale or cross-request taint
- Severity: High
- Category: false-positive
- Location: iast/propagation/writer.go:202-205; internal/taint/store/writer.go:21-27,76-111,234-263; internal/taint/propagation/writer.go:215-236
- Claim: `builderView` builds `WriterView{Pointer: StringData(b.String()), Length, Capacity}` without an `Anchor`. The store documents this at `store/writer.go:23-24` ("Buffer views also retain an Anchor ...; builders do not"). The writer record strongly retains only the `*strings.Builder` receiver (`writerRecord.object`), not its `buf`. After a tainted direct write, the builder can drop its backing without going through a woven call. Examples are a zero assignment `b = strings.Builder{}`, a method-value or dependency `Reset`, or growth through `fmt.Fprintf(&b, ...)` or `io.WriteString`. Builders have no native stdlib hook, unlike `bytes.Buffer`, so nothing invalidates the record. GC then frees the old backing. A later clean write can get a new backing at the same address with the same len and cap. When that happens, `LookupWriterValue` (matched by receiver) and `SnapshotWriter` (`record.writers[index].view != view` is false) accept the stale view. `publishWriterString` then adopts the clean result with the old source ranges. The result is false taint with a wrong source value on a supported direct `String()` call that feeds a sink. When the builder is shared, for example through a pool or a global, and the tainting request is still active, a different request's clean value gets the first request's source. That is cross-request bleed. The unwoven reset or write is an allowed miss per the README ("do not propagate input taint"), but the product rules say it must not produce false taint. Hitting it needs GC between the reset and the rewrite plus an exact len and cap match, but the allocator reuses a freed slot within a few allocations.
- Evidence: `.omo/review/evidence/store-identity-gc/zz_review_gc_identity_test.go` (copied into `iast/propagation/` of a private checkout). Command: `GOTOOLCHAIN=go1.26.6 go test -count=1 -run TestReview -v ./iast/propagation/`. Output is in `repro-head.out.txt` (exit=1):
  - `mode=zero-assign: tracked backing 0x52e21cf44640 (len 10 cap 16) freed and reused by clean write after 11 writes; BuilderString="cleanvalue" tainted=true ranges=[{Start:0 Length:10 Source:{... Name:input} Value:attack1234}]`
  - `mode=method-value-reset: ... after 32 writes; BuilderString="cleanvalue" tainted=true`
  - `request B: clean "cleanvalue" after 1 writes carries source [{... Name:reqA} Value:attack1234}] from request A` (cross-request)
  - `TestReviewBuilderStaleViewRealistic`, with default GOMAXPROCS=16, no heap shaping, a `b = strings.Builder{}` plus `fmt.Fprintf` loop, and a GC every 100 iterations: `iteration 3: clean query "SELECT 1;x" reported tainted`. Across 8 separate runs of 20,000 iterations in `repro-realistic.out.txt` it hit once, at iteration 156. It also hit once in 5 earlier unsaved runs, at iteration 556. The deterministic sub-tests failed in 5 out of 5 repeated runs.
  - Control: `TestReviewBufferAnchorPreventsReuse` passes. The anchored `bytes.Buffer` backing was never reused across 50,000 allocations of the same size class.
- Fix: Anchor the builder backing the same way Buffer does. In `builderView`, when `len(value) > 0`, set `view.Anchor = unsafe.StringData(value)` and `view.Backing = uintptr(unsafe.Pointer(view.Anchor))`. The old backing then cannot be freed while the record exists, and the stale view can never match again. The capacity is already charged, so there is no new unbounded retention (at most 8 writers per owner, released at Finish). The trial patch is `builder-anchor-fix.diff`. With it applied, every reuse reproducer reports that the address was never reused, the realistic loop reports 0 false positives in 20,000 iterations, and the existing `iast/propagation`, `internal/taint/propagation`, and `internal/taint/store` suites still pass (`repro-with-fix.out.txt`).

### store-identity-gc-F2: The existing address-reuse regression test is usually vacuous (skips)
- Severity: Low
- Category: test-gap
- Location: internal/taint/store/identity_test.go:30-65 (Skip at :53)
- Claim: `TestAddressReuseDoesNotReviveFinishedOwner` calls `runtime.GC()` once, then allocates through `TaintString` and skips when the allocator does not reuse the address. On go1.26.6 it skipped in 4 of 5 runs, so it gives almost no protection for the most important identity invariant. No test covers backing reuse for builders or buffers (F1).
- Evidence: `for i in 1..5; go test -count=1 -run TestAddressReuseDoesNotReviveFinishedOwner -v ./internal/taint/store/` gave 4× `--- SKIP ... allocator did not reuse the address`, 1× PASS. My `marchTo` technique never needed to skip in any run: GOMAXPROCS(1), live neighbour objects of the same size class, one GC, then keeping all candidates alive so the allocator walks the free slots. Reuse came after 252-276 allocations for 32-byte strings and after 1 allocation for 48-byte slices.
- Fix: Use the same marching technique, turn the skip into a failure (or require a minimum hit rate), and add a builder-reuse regression test for F1.

## Checked and found correct
- **uintptr keys retain nothing.** `Key.Pointer` and `valueSlot.pointer` are plain `uintptr`s and are never turned back into pointers (`store.go:39-61,63-72`). After `Finish` a `weak.Pointer` to the managed root backing goes nil after GC, for both strings and bytes (`TestReviewStore*AddressReuseAfterFinish`: `root collected (weak pointer nil)`).
- **Strong anchors prevent reuse while the owner is live.** `rootRecord.stringAnchor` and `bytesAnchor` are set in `publishRoot` (`root.go:323-345`) and cleared only by `rollbackRoot` (`root.go:370-398`, which runs only when no slot was published) or `Finish` (`owner.go:186-201`). With the app's references dropped, repeated GC plus 50,000 allocations of the same size class never reused the root address, and the weak pointer stayed live.
- **After Finish, a reused address reads clean even while another request is active** (possibly reusing the same owner slot). A reused address was reached after 252 and 1 allocations, and `IsTaintedString` and `IsTaintedBytes` returned false. The mechanism: `Finish` CASes to `stateFinishing` (`owner.go:162`) before taking `lifecycleMu.Lock` and clearing anchors. `Lookup` requires `stateActive` and a matching `ownerGen` under the lifecycle RLock (`lookup.go:152`). It also requires `root.generation == rootGen && setGen == rootGen` under `rootsMu`, and checks again after copying (`lookup.go:162,182`). `ownerGen` is a `uint64` bumped on every Acquire (`owner.go:53`), so it cannot ABA.
- **Stale slots with the same address and owner slot are harmless.** `putWindow` reclaims stale slots (`value.go:163-170`). `Lookup` validates each candidate independently, so a stale slot and a live slot for the same key cannot mix. Resetting the root generation to 0 in `rollbackRoot` is safe because the rolled-back root never had a slot (every rollback caller runs only after `putWindow` failed).
- **Windows and mutations stay inside the anchored allocation.** `inWindow` confines derived keys to `[base, base+span)` of an anchored root (`value.go:35-49`). `PublishBytesMutation` requires the same base and span (`mutation.go:51`), so no key can land in freed memory while its root is live.
- **bytes.Buffer writer views** store `Anchor = &buf[off]`, an interior pointer that keeps the whole backing alive (`iast/propagation/writer.go:207-217`). The reproducer confirms no reuse.
- **Object bindings, writer receivers, and JSON reader refs are strongly retained.** `binding.object any` (`binding.go:33`), `writerRecord.object any` (`writer.go:37`), and `jsonbridge.readerRef.value`. Receiver and object addresses therefore cannot be reused while tracked. All are cleared by `Finish` (`owner.go:170-179,213`) or by `Unbind`.
- **jsonbridge decoder slots** are keyed by `uintptr(&dec.d)` or the `decodeState` pointer with no anchor. This is safe because `Bind` and `Unbind` are paired through `defer` in the same Decode or unmarshal frame (`iast/encoding/json/orchestrion.yml:40-43,57-60`), where the receiver is live. Passing the receiver to `any` makes it escape to the heap, so it does not move with the stack. `document.original` and `quotedLiteral.original` are compared only within that live decode. The document clone is a strong `[]byte` released at the final `Unbind`.
- **writerbridge expectation markers** (`uintptr` of `*bytes.Buffer`) live only between `Expect` and a deferred `Cancel` inside a wrapper that holds the buffer, so they cannot leak onto a reused address.
- **Memory retention by anchors is bounded and ends at Finish.** Roots are charged by size class and capped per request and process, writer receivers by the 8-writer limit, and bindings by 256 (reader graphs are uncharged, which is documented).

## Not covered / open questions
- I did not run a woven (orchestrion) build. The reproducers call the exported `iast/propagation` wrappers directly, which is what woven call sites invoke. The unwoven operations in F1 (zero assignment, method-value `Reset`, `fmt.Fprintf`, `io.WriteString`) have no aspect in `iast/propagation/orchestrion.yml` (grep found no `Fprint` or `io.WriteString` aspects and no `strings.Builder` native hook), so I expect woven behaviour to match.
- I did not measure the cost of `MayContain` hits on stale slots of the same key before lazy reclaim (digest check 24). It is a performance question only, since `Lookup` rejects those slots.
- I did not attempt stack-allocated value identity (a string whose data lives on a goroutine stack that moves). Managed roots are always heap clones or audited heap allocations, so that case cannot arise for roots.
